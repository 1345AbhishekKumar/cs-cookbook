## The Server That Fell Over at 300 Users

TravelBuddy's API had a connection pool of 25 per instance. They scaled to 12 instances. That is 300 connections to a PostgreSQL with `max_connections = 100`. Postgres did what it always does: it refused new connections and threw `FATAL: sorry, too many clients already`. The engineer's fix was to raise `max_connections` to 500. It got *slower*.

This lesson explains why, and the correct fix.

---

## Where the Memory Goes

PostgreSQL splits memory into **shared** (allocated once at startup, used by everyone) and **per-connection** (allocated as each backend needs it). The two have opposite sizing rules.

| Setting | Scope | Rule of thumb |
| :--- | :--- | :--- |
| `shared_buffers` | Shared | ~25% of RAM (up to 8–16 GB on big boxes) |
| `effective_cache_size` | Planner estimate | ~50–75% of RAM — *not* an allocation |
| `work_mem` | **Per sort/hash node, per connection** | 4–64 MB; multiply by concurrency |
| `maintenance_work_mem` | Per maintenance op | 64 MB–2 GB (`VACUUM`, `CREATE INDEX`) |
| `wal_buffers` | Shared | `-1` = auto (usually fine) |

<Callout type="error" title="`work_mem` Is a Multiplier, Not a Value">
`work_mem` is per **operation**, and a single query can run several sorts/hashes. Set it to 256 MB with 100 connections and a complex query and you can OOM the box. Size it as:

```
work_mem ≈ available_ram_for_sorts / (max_connections × avg_ops_per_query)
```

Start ~4–8 MB, raise deliberately for analytics workloads.
</Callout>

### The Five Settings That Matter

```conf
# postgresql.conf — a sane starting point for a dedicated 16 GB / 8-core server
shared_buffers              = 4GB        # ~25% RAM
effective_cache_size        = 12GB       # ~75% RAM; planner only
work_mem                    = 8MB        # per sort/hash node
maintenance_work_mem        = 512MB      # VACUUM / CREATE INDEX
max_connections             = 100        # keep LOW (see pooling below)

random_page_cost            = 1.1        # SSD (default 4.0 assumes spinning disk)
effective_io_concurrency    = 200        # SSD; number of concurrent I/Os
```

<Callout type="warn" title="`random_page_cost` Is the Most Underrated Setting">
On SSDs, the default `4.0` makes the planner wrongly prefer sequential scans over index scans. Lowering it to `~1.1` often flips plans to the index you built for exactly this query. Measure with `EXPLAIN (ANALYZE, BUFFERS)` before and after.
</Callout>

### Verify What's Actually in Effect

```sql
-- Current value and where it came from (file / ALTER SYSTEM / session)
SELECT name, setting, unit, source
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','max_connections','random_page_cost');

-- Show the ones you changed from default
SELECT name, setting, boot_val, source FROM pg_settings WHERE source <> 'default';
```

Change a setting, in order of permanence:

```sql
SET work_mem = '32MB';                    -- this session only
SET LOCAL work_mem = '32MB';              -- this transaction only
ALTER SYSTEM SET work_mem = '16MB';       -- cluster-wide (writes postgresql.auto.conf)
SELECT pg_reload_conf();                  -- apply reloadable settings (no restart)
```

| Method | Survives restart | Scope |
| :--- | :--- | :--- |
| `SET` | No | Session |
| `SET LOCAL` | No | Transaction |
| `ALTER SYSTEM` | Yes | Cluster (`postgresql.auto.conf`) |
| Edit `postgresql.conf` | Yes | Cluster (checked by config tooling) |
| `ALTER DATABASE … SET` | Yes | One database |
| `ALTER ROLE … SET` | Yes | One role's sessions |

<Callout type="info" title="`ALTER SYSTEM` vs `postgresql.conf`">
`ALTER SYSTEM` writes to `postgresql.auto.conf`, which is read **after** and overrides `postgresql.conf`. Use `ALTER SYSTEM RESET name` to remove an override. Many teams manage `postgresql.conf` with config management and let `ALTER SYSTEM` handle urgent, temporary changes only.
</Callout>

Some settings need a **restart** (e.g. `shared_buffers`); most can be reloaded:

```sql
SELECT name, pending_restart FROM pg_settings WHERE pending_restart;
```

## WAL, Checkpoints & Durability

Write-Ahead Logging makes transactions durable. Checkpoints flush dirty pages so crash recovery has a bounded starting point. Two knobs dominate:

```conf
wal_level                 = replica     # replica (default) enables replication/slot use
max_wal_size              = 4GB         # more WAL between checkpoints = fewer, bigger spikes
min_wal_size              = 1GB
checkpoint_timeout        = 15min
checkpoint_completion_target = 0.9       # spread the flush smoothly
synchronous_commit        = on           # durability: off = faster, risk losing recent commits
```

| Setting | Trade-off |
| :--- | :--- |
| `synchronous_commit = off` | ~×2 faster commits; a crash can lose the last few *committed* transactions (no corruption) |
| `max_wal_size` too small | Frequent checkpoints → spiky I/O |
| `checkpoint_completion_target` low | Checkpoint I/O burst right at the deadline |

<Callout type="tip" title="`synchronous_commit = off` Is Often Fine">
If losing a few seconds of commits after a hard crash is acceptable (analytics ingestion, logs), `off` is a legitimate throughput win with **no corruption risk**. Keep it `on` for money and bookings.
</Callout>

## Connections: Pool, Don't Multiply

PostgreSQL forks a **process** per connection. Each costs memory and has real context-switch cost. Past roughly `(2–4) × CPU cores` on an OLTP workload, adding connections *reduces* total throughput — the "connection storm" that made TravelBuddy slower after they raised the limit.

```sql
-- Who is connected, and what are they doing?
SELECT state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state;

-- Connections per database
SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname ORDER BY 2 DESC;
```

### PgBouncer: Multiplex Thousands of Clients onto Few Backends

```
App instances (100s of client connections)
      │  cheap, persistent
      ▼
   ┌─────────────┐
   │  PgBouncer  │   pools + multiplexes
   └─────────────┘
      │  few, reused server connections
      ▼
   PostgreSQL  (max_connections = 100)
```

| Pool mode | A server connection is held for | Session state across queries? | Use when |
| :--- | :--- | :--- | :--- |
| `session` | The whole client session | Preserved | Need prepared statements/advisory locks at session level |
| `transaction` | One transaction (then returned) | **Not** preserved | Default choice for most apps |
| `statement` | One statement | Not preserved | Simple autocommit workloads |

```ini
; pgbouncer.ini
[databases]
travelbuddy = host=127.0.0.1 port=5432 dbname=travelbuddy

[pgbouncer]
listen_port = 6432
listen_addr = 0.0.0.0
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

pool_mode = transaction
max_client_conn = 2000        ; clients can be many
default_pool_size = 25        ; server conns per (user,db) pair
reserve_pool_size = 5
server_idle_timeout = 600
```

<Callout type="warn" title="Transaction Mode Has Rules">
Because a client hops between server connections, these break in `pool_mode = transaction`:

- **Session-level `SET`** (must use `SET LOCAL` inside transactions) — critical for RLS tenant variables.
- **Named prepared statements** unless you use protocol-level (unnamed) prepares or PgBouncer's supported mode.
- **`LISTEN`/`NOTIFY`**, session advisory locks, `WITH HOLD` cursors.

If you rely on any of these, use `session` mode or a session-aware pooler.
</Callout>

The right app-side pattern is a **small pool per instance** talking to PgBouncer:

| Layer | Target |
| :--- | :--- |
| App pool (per instance) | 5–20 connections (not hundreds) |
| PgBouncer `default_pool_size` | ~2–4 × CPU cores |
| Postgres `max_connections` | Keep modest (100–200) |

```sql
-- Raise only if you genuinely need direct connections (e.g. admin, replication)
ALTER SYSTEM SET max_connections = 200;   -- requires restart
```

## A Worked Before/After

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `too many clients already` | Pool × instances > `max_connections` | Add PgBouncer, shrink app pools |
| Throughput dropped after raising connections | Per-process overhead, lock contention | Lower `max_connections`, pool |
| Queries spilling to disk (`Sort Method: external`) | `work_mem` too small | Raise `work_mem` for that workload/session |
| Index exists but planner ignores it | `random_page_cost` too high for SSD | Set to ~1.1 |
| Periodic latency spikes | Small `max_wal_size`, frequent checkpoints | Raise `max_wal_size`, completion target 0.9 |
| `VACUUM`/`CREATE INDEX` slow | `maintenance_work_mem` small | Raise to 512 MB–2 GB |

## Practice

```sql
-- 1. Find settings that differ from their compiled default
SELECT name, setting, boot_val, source FROM pg_settings WHERE source <> 'default';

-- 2. See the current work_mem in a fresh session, then raise it and watch a sort
SHOW work_mem;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM bookings ORDER BY total_cents DESC LIMIT 10;
SET work_mem = '128MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM bookings ORDER BY total_cents DESC LIMIT 10;   -- look at "Sort Method"

-- 3. Count connections by application so a rogue client can't hide
SELECT application_name, state, count(*)
FROM pg_stat_activity
GROUP BY application_name, state
ORDER BY 3 DESC;
```

```bash
# 4. Stand up PgBouncer against a local Postgres and connect the app through :6432
pgbouncer -d /etc/pgbouncer/pgbouncer.ini
psql -h 127.0.0.1 -p 6432 -U app_service travelbuddy -c 'SELECT 1;'
```
