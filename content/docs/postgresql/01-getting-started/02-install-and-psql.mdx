## Three Ways to Run PostgreSQL

Pick whichever suits you. They produce the same server; only the plumbing differs.

<Tabs items={['Docker (recommended)', 'Native installer', 'Cloud (no install)']}>
<Tab value="Docker (recommended)">
The fastest, cleanest option. It leaves nothing behind on your machine.

```bash
# Start a PostgreSQL 18 server named pg-learn
docker run --name pg-learn \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  -d postgres:18

# Open an interactive SQL prompt inside the container
docker exec -it pg-learn psql -U postgres

# Stop / start / remove it later
docker stop pg-learn
docker start pg-learn
docker rm -f pg-learn
```
</Tab>
<Tab value="Native installer">
Install it like any app:

- **Windows / macOS:** download the installer from **postgresql.org/download** (it bundles PostgreSQL + pgAdmin). On macOS you can also use Homebrew: `brew install postgresql@18`.
- **Debian/Ubuntu:** `sudo apt install postgresql` (or add the official PGDG repository for the newest version).
- **Fedora:** `sudo dnf install postgresql-server && sudo postgresql-setup --initdb`.

The installer creates a `postgres` superuser and a service that starts automatically.
</Tab>
<Tab value="Cloud (no install)">
Create a free managed instance at a provider such as **Neon**, **Supabase**, or **Amazon RDS**. You get a connection string that looks like:

```text
postgresql://user:password@host:5432/dbname?sslmode=require
```

Paste it into `psql` and you're connected — no local server at all.
</Tab>
</Tabs>

<Callout type="tip" title="Which Should You Pick?">
Learning locally? **Docker.** Want a GUI and Windows integration? **Native installer.** Just want to try SQL in a browser with no setup? **Cloud** (or a hosted "playground").
</Callout>

## Connecting

The client program is **`psql`**. Every modern install includes it.

```bash
# Connect by flags
psql -h localhost -p 5432 -U postgres -d postgres

# Connect by a URL (very common with cloud providers)
psql "postgresql://postgres:secret@localhost:5432/postgres"

# If you omit -d and the URL, psql defaults to your OS username and a same-named db
psql
```

If it worked, your prompt changes to something like:

```text
psql (18.0)
Type "help" for help.

postgres=#
```

| Prompt | Meaning |
| :--- | :--- |
| `postgres=#` | Connected as a **superuser** to the `postgres` database |
| `postgres=>` | Connected as a **normal** user |
| `postgres=#` with a `*` | You are inside an open transaction |

## A Tour of `psql`

`psql` understands two kinds of input:

- **SQL statements** — end with a semicolon (`;`) and are sent to the **server**.
- **Meta-commands** — start with a backslash (`\`) and are handled **by `psql` itself**.

<Callout type="error" title="The #1 Beginner Bug: Forgetting the Semicolon">
If you type `SELECT 1` and press Enter, nothing happens — the prompt changes to `postgres-#` (note the dash), waiting for more input. `psql` only sends a statement when it sees a `;`. Type it (or press `Ctrl+C` to cancel).
</Callout>

### The Meta-Commands You'll Use Daily

| Command | Does |
| :--- | :--- |
| `\l` | List all **databases** |
| `\c dbname` | **Connect** to another database |
| `\dt` | List **tables** in the current schema |
| `\dt *.*` | List tables in every schema |
| `\d tablename` | Describe a table (columns, types, indexes) |
| `\dn` | List **schemas** |
| `\du` | List **roles/users** and their privileges |
| `\df` | List **functions** |
| `\dv` | List **views** |
| `\x` | Toggle expanded (vertical) output — readable view for wide rows |
| `\copy` | Fast client-side import/export between table/query and local CSV file |
| `\timing` | Toggle timing of each query |
| `\i file.sql` | Run a SQL file |
| `\e` | Edit the current query in your editor |
| `\?` | Help on meta-commands |
| `\h SELECT` | Help on SQL syntax |
| `\q` | Quit |

```text
postgres=# \l
                                  List of databases
   Name    |  Owner   | Encoding |   Collate   |    Ctype
-----------+----------+----------+-------------+-------------
 postgres  | postgres | UTF8     | en_US.UTF-8 | en_US.UTF-8
 template0 | postgres | UTF8     | en_US.UTF-8 | en_US.UTF-8
 template1 | postgres | UTF8     | en_US.UTF-8 | en_US.UTF-8
(3 rows)
```

### Expanded Display with `\x`

When querying tables with many columns, standard horizontal table output wraps and becomes unreadable. The `\x` toggle switches output into key-value records:

```text
postgres=# \x
Expanded display is on.

postgres=# SELECT * FROM customers LIMIT 1;
-[ RECORD 1 ]---------------------------------
id         | 1
email      | ada@example.com
full_name  | Ada Lovelace
created_at | 2026-10-06 09:14:22.431+00

postgres=# \x
Expanded display is off.
```

<Callout type="info" title="`\d` Is Not SQL">
`\dt`, `\d`, `\l` and friends are **`psql` shortcuts** that run catalog queries for you. If you paste `\dt` into a Java app or a SQL file run by another tool, it will fail — the *server* has no idea what `\dt` means. When you need the underlying query, run `psql -E` to echo the real SQL.
</Callout>

## Creating a Database, a User, and a Schema

Let's build a proper workspace. Note that `CREATE DATABASE` cannot run inside a transaction block — that's why we connect between statements.

<Steps>
<Step>
### Create a user (role)

```sql
CREATE ROLE travelbuddy WITH LOGIN PASSWORD 'secret';
```

In PostgreSQL, a **role** is both a user (if it can log in) and a group (if it can't).
</Step>

<Step>
### Create a database owned by that user

```sql
CREATE DATABASE travelbuddy OWNER travelbuddy;
```
</Step>

<Step>
### Connect to it and create a schema

```sql
\c travelbuddy

CREATE SCHEMA app AUTHORIZATION travelbuddy;
```

A **schema** is a namespace of tables inside a database. Each database starts with a `public` schema.
</Step>

<Step>
### Check where you are

```sql
SELECT current_database(), current_user, current_schema();
-- travelbuddy | travelbuddy | public
```

Your **`search_path`** is the ordered list of schemas PostgreSQL looks in when you use an unqualified table name:

```sql
SHOW search_path;                     -- "$user", public
SET search_path TO app, public;       -- prefer the app schema first
```
</Step>
</Steps>

### Dropping a Database (and Why It's Catastrophic)

When cleaning up a scratch or temporary database, use `DROP DATABASE`:

```sql
-- You cannot drop the database you are currently connected to. Switch to postgres first:
\c postgres

DROP DATABASE test_sandbox;

-- In modern PostgreSQL (13+), terminate active sessions automatically:
DROP DATABASE test_sandbox WITH (FORCE);
```

<Callout type="error" title="Catastrophic Danger: Milliseconds to Wipe History">
`DROP DATABASE` has **no undo, no recycle bin, and no prompt**. It obliterates every schema, table, record, and index in a fraction of a second. In production environments:
- Never execute destructive commands from an interactive shell without verified backups.
- Never grant your web application role `SUPERUSER` or database ownership rights.
- Automated Point-in-Time Recovery (PITR) is your only safety net if an accidental drop occurs.
</Callout>

<Callout type="warn" title="Fix Your Own Schema First, Then Never Assume `public`">
By default your `search_path` starts with `"$user"` then `public`. In an app it's common to put your tables in a dedicated schema (`app`) and set `search_path` explicitly. Relying on `public` implicitly is a privilege-escalation risk — **[Stage 4](/docs/postgresql/04-administration-and-scaling/01-roles-security-and-rls)** explains why.
</Callout>

## Your First Real Table, End to End

```sql
SET search_path TO app, public;

CREATE TABLE customers (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text NOT NULL UNIQUE,
    full_name  text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO customers (email, full_name)
VALUES ('ada@example.com', 'Ada Lovelace');

SELECT id, email, full_name, created_at FROM customers;
```

```text
 id |      email      |   full_name   |          created_at
----+-----------------+---------------+-------------------------------
  1 | ada@example.com | Ada Lovelace  | 2026-10-06 09:14:22.431+00
(1 row)
```

### Break It On Purpose

The best way to understand constraints is to violate one and read the error:

```sql
INSERT INTO customers (email, full_name) VALUES ('ada@example.com', 'Someone Else');
```

```text
ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(ada@example.com) already exists.
```

The **database** refused the bad data — not your application code. That is the whole point.

## Running SQL Files

Real projects keep SQL in files.

```bash
# From the shell: run a file and exit
psql "postgresql://travelbuddy:secret@localhost:5432/travelbuddy" -f schema.sql

# From inside psql
\i schema.sql
```

<Callout type="tip" title="Useful `psql` Setups for Beginners">
- `\timing on` — see how long each query takes.
- `\x auto` — switch to vertical output automatically when rows are wide.
- `\set ON_ERROR_STOP on` — inside a script, stop at the first error instead of ploughing on.
- `psql -e` (or `\set ECHO all`) — print the actual SQL behind meta-commands, a great way to learn.
</Callout>

## Exporting & Importing CSV Data with `\copy`

While `pg_dump` takes whole-database backups, developers and data engineers constantly need to export query results or import tabular datasets (like spreadsheets or Mockaroo mock data) using CSV files.

PostgreSQL has two copy tools:

| Tool | Where it runs | Permissions needed |
| :--- | :--- | :--- |
| **`\copy`** (psql meta-command) | **Client workstation** (streams data over the network connection) | Standard user with `SELECT` or `INSERT` |
| **`COPY`** (SQL statement) | **Server filesystem** (reads/writes to database host disk directly) | Superuser or `pg_read_server_files` |

<Callout type="tip" title="Always Use `\copy` for Local Files & Cloud Databases">
Because managed databases (AWS RDS, Supabase, Neon) do not grant access to the underlying server disk, raw SQL `COPY` will fail. **`\copy` runs inside `psql` on your own machine** and works on any database connection.
</Callout>

### 1. Exporting Query Results to CSV

```text
-- Export an entire table with CSV header row
\copy customers TO 'customers_export.csv' WITH (FORMAT csv, HEADER);

-- Export specific columns from a customized query
\copy (SELECT id, email, full_name FROM customers ORDER BY id) TO 'users_list.csv' WITH (FORMAT csv, HEADER, DELIMITER ',');
```

### 2. Importing Data from CSV

Suppose you generated realistic mock data in a local file named `customers_mock.csv`:

```csv
email,full_name
jake@example.com,Jake Jones
ann@example.com,Ann Smith
```

Import it directly into your table with automatic column matching:

```text
\copy customers (email, full_name) FROM 'customers_mock.csv' WITH (FORMAT csv, HEADER);
```

PostgreSQL validates all column types, defaults, and constraints during the stream. If any row contains duplicate emails or invalid types, the command rolls back cleanly.

## The Errors You'll Meet First (and What They Mean)

| Error | Usually means |
| :--- | :--- |
| `connection refused` | The server isn't running, or the host/port is wrong |
| `role "x" does not exist` | Wrong `-U` username (or that role wasn't created) |
| `database "x" does not exist` | Wrong `-d`/URL database name |
| `password authentication failed` | Wrong password — check `PGPASSWORD`/the URL |
| `permission denied for schema/t table` | Your role lacks a `GRANT` |
| `relation "x" does not exist` | Table not created yet, or wrong `search_path` |
| `syntax error at end of input` | You forgot the `;` |
| `must be owner of ...` | Trying to change an object you don't own |

<Callout type="info" title="Connection Settings Without Retyping Them">
Every `psql` flag has an environment variable (`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`), and you can store reusable credentials in a `~/.pgpass` file. Handy for scripts; avoid `PGPASSWORD` in shared environments.
</Callout>
