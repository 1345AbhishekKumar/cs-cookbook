## Types Are a Design Decision

Two databases can store the same information while one is correct and the other quietly wrong. Data types are how you make "correct" the default.

### Numbers: Never Use Floating Point for Money

```sql
-- ❌ The classic money bug
SELECT (0.1::float8 + 0.2::float8) = 0.3::float8;   -- FALSE! (0.30000000000000004)

-- ✅ Exact arithmetic
SELECT (0.1::numeric + 0.2::numeric) = 0.3::numeric; -- TRUE
```

| Type | Size | Use it for |
| :--- | :--- | :--- |
| `smallint` | 2 B | Small counters, enums-as-ints |
| `integer` / `int` | 4 B | Ordinary whole numbers |
| `bigint` | 8 B | Large counts, **money stored as integer cents** |
| `numeric(p, s)` | variable | **Exact decimals** — prices, balances, rates |
| `real` / `double precision` | 4 / 8 B | Scientific/inexact measurements only |

<Callout type="error" title="Money Rule">
Store money as **`numeric(12,2)`** or as **integer cents** in a `bigint`. Never in `float`. TravelBuddy uses `total_cents bigint`.
</Callout>

### Text: Just Use `text`

```sql
-- These three have IDENTICAL performance in PostgreSQL:
CREATE TABLE a (x text);
CREATE TABLE b (x varchar);       -- no length
CREATE TABLE c (x varchar(255));  -- length-limited (adds a tiny check)
```

Prefer **`text`**. A `varchar(255)` adds no speed and creates a future migration the day someone needs 300 characters. If a real business limit exists, express it explicitly:

```sql
name text NOT NULL CHECK (length(name) <= 100)
```

| Type | Use it for |
| :--- | :--- |
| `text` | Almost everything |
| `char(n)` | Fixed-width codes — rarely worth it |
| `citext` (extension) | Case-insensitive text (e.g. emails), instead of `lower()` everywhere |

### Time: Default to `timestamptz`

| Type | Stores | Notes |
| :--- | :--- | :--- |
| `date` | Calendar date | Birthdays, business days |
| `time` | Wall-clock time | Schedules |
| `timestamp` (without tz) | Date + time, **no zone** | Usually a mistake |
| **`timestamptz`** | An instant, stored in UTC | **Use this for events** |
| `interval` | A duration | `'30 days'`, `'2 hours'` |

```sql
SELECT now();                                    -- 2026-10-06 09:14:22.431+00
SELECT now() AT TIME ZONE 'Europe/Madrid';        -- rendered in a zone
SELECT now() + interval '30 days' AS in_a_month;
```

<Callout type="tip" title="`timestamptz` Does Not Store a Time Zone">
`timestamptz` stores a **point in time** (internally UTC) and renders it in your session's time zone. That's exactly what you want. `timestamp` without a zone stores an ambiguous wall-clock reading — avoid it for anything that refers to "when something happened".
</Callout>

### Identifiers: `uuid` and PostgreSQL 18's `uuidv7()`

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY DEFAULT uuidv7(),   -- time-ordered, index-friendly
    -- ...
);
```

| Option | Best for |
| :--- | :--- |
| `GENERATED ALWAYS AS IDENTITY` (a `bigint`) | Internal, fast, compact keys |
| `uuid` with `gen_random_uuid()` | Public, unguessable, distributed ids |
| **`uuid` with `uuidv7()`** (PG18) | **Best of both**: globally unique *and* time-ordered, so inserts stay index-friendly |

<Callout type="info" title="Why UUIDv7 Is a Big Deal">
Random UUIDv4 ids scatter inserts across a B-tree index, causing page splits and bloat. **UUIDv7** starts with a timestamp, so new ids sort near the end and insert cleanly — while remaining globally unique. PostgreSQL 18 added the built-in `uuidv7()` function.
</Callout>

### The Types That Make PostgreSQL Special

| Type | Example | Use for |
| :--- | :--- | :--- |
| `boolean` | `true`, `false`, `NULL` | Flags |
| `jsonb` | `'{"a": 1}'::jsonb` | Semi-structured data (queryable, indexable) |
| `text[]` | `ARRAY['a','b']` | Small multi-valued fields (tags) |
| `int4range` / `tstzrange` | `'[2026-01-01, 2026-02-01)'` | Non-overlapping periods |
| `enum` | `CREATE TYPE status AS ENUM (...)` | Fixed small sets of values |
| `bytea` | binary | Small blobs |
| `inet` / `cidr` | `'10.0.0.1'` | IP addresses |
| `domain` | `CREATE DOMAIN email AS text CHECK (...)` | Reusable constrained types |

<Callout type="warn" title="Enums vs. a Lookup Table">
`enum` types are handy for a closed, rarely-changed set (`'pending'|'paid'|'cancelled'`). But removing or reordering an enum value is awkward. If the set may grow or needs attributes (a label, a sort order), use a **lookup table** with a foreign key instead. A `CHECK (status IN (...))` on a `text` column is a flexible middle ground.
</Callout>

## Designing the TravelBuddy Schema

Here is the real thing, with the reasoning behind each choice.

```sql
CREATE TABLE airlines (
    id      integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name    text NOT NULL,
    country text NOT NULL
);

CREATE TABLE flights (
    id               bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    flight_no        text        NOT NULL,
    airline_id       integer     NOT NULL REFERENCES airlines(id),
    origin           text        NOT NULL,
    destination      text        NOT NULL,
    departure_at     timestamptz NOT NULL,
    seats_available  integer     NOT NULL CHECK (seats_available >= 0),
    base_price_cents bigint      NOT NULL CHECK (base_price_cents >= 0),
    tags             text[]      NOT NULL DEFAULT '{}',
    UNIQUE (flight_no, departure_at)
);

CREATE TABLE customers (
    id         uuid        PRIMARY KEY DEFAULT uuidv7(),
    email      text        NOT NULL UNIQUE,
    full_name  text        NOT NULL,
    phone      text,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE bookings (
    id          uuid        PRIMARY KEY DEFAULT uuidv7(),
    customer_id uuid        NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
    status      text        NOT NULL DEFAULT 'pending'
                            CHECK (status IN ('pending', 'paid', 'cancelled')),
    total_cents bigint      NOT NULL CHECK (total_cents >= 0),
    created_at  timestamptz NOT NULL DEFAULT now()
);

-- PostgreSQL does NOT index foreign keys automatically. Do it yourself.
CREATE INDEX idx_bookings_customer ON bookings (customer_id);
```

## Constraints: Rules the Database Enforces

| Constraint | Guarantee |
| :--- | :--- |
| `PRIMARY KEY` | Unique + `NOT NULL`; also builds a unique index |
| `UNIQUE` | No duplicate values (one `NULL` allowed by default) |
| `NOT NULL` | The value must be present |
| `CHECK (...)` | A boolean expression must hold for every row |
| `FOREIGN KEY` | The referenced row must exist |
| `DEFAULT` | Value used when the column is omitted |
| `EXCLUDE` | No two rows may satisfy a condition (e.g. overlapping ranges) |

### Foreign Keys and Referential Actions

```sql
customer_id uuid NOT NULL REFERENCES customers(id) ON DELETE RESTRICT
```

| Action | Behavior on delete of the parent |
| :--- | :--- |
| `RESTRICT` / `NO ACTION` | Refuse (safest default) |
| `CASCADE` | Delete the children too (use carefully) |
| `SET NULL` | Null out the child's FK (column must be nullable) |
| `SET DEFAULT` | Set the child's FK to its default |

<Callout type="error" title="Always Index Your Foreign Keys">
PostgreSQL creates an index for `PRIMARY KEY` and `UNIQUE`, but **not** for `FOREIGN KEY`. Without an index on `bookings(customer_id)`, deleting a customer scans all of `bookings`, and joins filtering by customer slow to a crawl. This is the single most common missing index in beginner schemas.
</Callout>

## Generated Columns & Defaults

A **generated column** is computed from other columns. In PostgreSQL 18, the default is **virtual** (computed on read); use `STORED` when reads matter more than writes.

```sql
CREATE TABLE products (
    id    bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    price numeric(10,2) NOT NULL,
    tax   numeric(3,2)  NOT NULL DEFAULT 0.21,
    total numeric(10,2) GENERATED ALWAYS AS (price * (1 + tax)) STORED
);
```

| Kind | Computed | Stored on disk? |
| :--- | :--- | :--- |
| `GENERATED ... VIRTUAL` (PG18 default) | On read | No |
| `GENERATED ... STORED` | On write | Yes |

## Evolving a Schema with `ALTER TABLE`

Schemas change. `ALTER TABLE` changes them in place:

```sql
ALTER TABLE customers ADD COLUMN loyalty_points integer NOT NULL DEFAULT 0;
ALTER TABLE customers RENAME COLUMN full_name TO name;
ALTER TABLE customers ALTER COLUMN phone DROP NOT NULL;
ALTER TABLE customers ADD CONSTRAINT phone_len CHECK (length(phone) <= 32);
ALTER TABLE customers DROP COLUMN loyalty_points;
CREATE INDEX CONCURRENTLY idx_customers_created ON customers (created_at);
```

<Callout type="warn" title="Some `ALTER`s Lock the Table">
Adding a column with a **volatile default**, changing a column's type, or running `CREATE INDEX` without `CONCURRENTLY` can take a heavy lock that blocks all reads and writes. On a live system, prefer `CREATE INDEX CONCURRENTLY` and set `lock_timeout`. **[Stage 4](/docs/postgresql/04-administration-and-scaling)** covers safe migrations in depth.
</Callout>

## Practice

```sql
-- 1. A new table with sensible types
CREATE TABLE airport (
    code    char(3) PRIMARY KEY,        -- IATA codes are exactly 3 letters
    city    text NOT NULL,
    country text NOT NULL
);

-- 2. Insert two rows, then try to violate each constraint
INSERT INTO airport VALUES ('MAD', 'Madrid', 'Spain'), ('BCN', 'Barcelona', 'Spain');
INSERT INTO airport VALUES ('MAD', 'Duplicate', 'Nowhere');   -- unique violation
INSERT INTO airport (city, country) VALUES ('NoCode', 'Nowhere'); -- not-null violation

-- 3. Inspect what you built
\d airport
```
