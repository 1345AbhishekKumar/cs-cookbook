## Transaction Control

```sql
BEGIN;                             -- start a transaction (alias: START TRANSACTION)
COMMIT;                            -- make changes permanent
ROLLBACK;                          -- discard all changes
SAVEPOINT sp1;                     -- mark a point to return to
ROLLBACK TO SAVEPOINT sp1;         -- undo back to sp1, keep the transaction
RELEASE SAVEPOINT sp1;             -- forget the marker

BEGIN ISOLATION LEVEL SERIALIZABLE READ WRITE;
SET TRANSACTION READ ONLY;         -- hint for the whole transaction
```

| Clause | Effect |
| :--- | :--- |
| `READ ONLY` | Rejects writes; cheaper snapshot |
| `READ WRITE` | Default |
| `DEFERRABLE` | Only with `SERIALIZABLE READ ONLY`; may skip conflict checks |
| `NOWAIT` / `SKIP LOCKED` | On `SELECT ... FOR ...` — don't wait for locked rows |

<Callout type="warn" title="Autocommit Is Always On">
Outside an explicit `BEGIN`, every statement is its own transaction. There is no global "in a transaction" state to fall back on — an error mid-script can leave half your work committed. Wrap multi-statement changes in `BEGIN` … `COMMIT`.
</Callout>

## ACID at a Glance

| Property | Guarantee | Breaks when… |
| :--- | :--- | :--- |
| **Atomicity** | All-or-nothing per transaction | You treat autocommit statements as one unit |
| **Consistency** | Constraints & invariants hold | Application logic multi-writes without a txn |
| **Isolation** | Concurrent txns don't corrupt each other | You assume a level guarantees more than it does |
| **Durability** | Committed data survives a crash | `synchronous_commit = off` and the box dies |

## Isolation vs. Anomaly Matrix

| Anomaly | Read Uncommitted | Read Committed *(PG default)* | Repeatable Read *(= Snapshot)* | Serializable |
| :--- | :---: | :---: | :---: | :---: |
| Dirty read | ✗ allowed | ✗ prevented | ✗ prevented | ✗ prevented |
| Lost update | ✗ allowed | ✗ allowed | ✓ prevented | ✓ prevented |
| Non-repeatable read | ✗ allowed | ✗ allowed | ✓ prevented | ✓ prevented |
| Phantom read | ✗ allowed | ✗ allowed | ✓ prevented | ✓ prevented |
| Write skew | ✗ allowed | ✗ allowed | ✗ **allowed** | ✓ prevented |
| Serialization anomaly | ✗ allowed | ✗ allowed | ✗ allowed | ✓ prevented |

<Callout type="info" title="PostgreSQL Never Does Dirty Reads">
`READ UNCOMMITTED` is accepted but silently behaves as `READ COMMITTED`. PostgreSQL's MVCC simply has no way to read uncommitted rows.
</Callout>

| Level | Sees | Cost |
| :--- | :--- | :--- |
| `READ COMMITTED` | Snapshot **per statement** | Cheapest; retry on conflict |
| `REPEATABLE READ` | Snapshot **per transaction** | Possible `40001` serialization failures |
| `SERIALIZABLE` | Predicate-locking (SSI) over a snapshot | Most `40001`s; must retry |

Because `REPEATABLE READ` and `SERIALIZABLE` can both raise `40001` (`could not serialize access due to concurrent update`), **any** such transaction needs a retry loop.

## Write Skew, in One Picture

Two doctors both check "is the other on call?", both see yes, both go off call → zero on call. Each transaction is individually valid; the *pair* breaks the invariant.

```sql
-- The vulnerable pattern: read a rule, then write based on it
SELECT count(*) FROM shifts WHERE on_call AND dept = 'ER';
-- application decides it's safe…
UPDATE shifts SET on_call = false WHERE doctor = 'alice';
```

Fixes:

| Fix | How |
| :--- | :--- |
| `SERIALIZABLE` | Detects the read-write dependency, aborts one txn |
| Materialize the conflict | `SELECT ... FOR UPDATE` on a shared "lock row" |
| Advisory lock | `pg_advisory_xact_lock(hashtext('er-rota'))` |
| Constraint | Encode the invariant as a `CHECK`/`EXCLUDE`/trigger the DB can enforce |

## Fixing Lost Updates

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;         -- pessimistic
UPDATE accounts SET balance = balance + 100 WHERE id = 1;      -- atomic (in-database)
UPDATE t SET v = v + 1 WHERE id = 1 RETURNING v;               -- atomic + read result
```

```sql
-- Optimistic concurrency: application supplies the version it read
UPDATE accounts
   SET balance = balance + 100, version = version + 1
 WHERE id = 1 AND version = 7;      -- 0 rows updated → someone beat you, retry
```

| Approach | Cost | Use when |
| :--- | :--- | :--- |
| Atomic `SET col = col + n` | Lowest | Arithmetic that never needs the old value |
| `SELECT … FOR UPDATE` | Locks a row | You must read, decide, then write |
| Optimistic version check | Retry on conflict | Low contention, HTTP/API layer |

## Locking: Modes and Clauses

| Row lock (`SELECT …`) | Blocks |
| :--- | :--- |
| `FOR UPDATE` | Other `FOR UPDATE/NO KEY UPDATE/SHARE/KEY SHARE` and writers |
| `FOR NO KEY UPDATE` | Weaker; doesn't block `FOR KEY SHARE` |
| `FOR SHARE` | Writers and `FOR UPDATE`; shares allowed |
| `FOR KEY SHARE` | Only key-changing writes |

```sql
SELECT * FROM t WHERE id = 1 FOR UPDATE;                  -- lock now
SELECT * FROM t WHERE id = 1 FOR UPDATE NOWAIT;           -- error if locked
SELECT * FROM t WHERE id = 1 FOR UPDATE SKIP LOCKED;      -- take the next free row
```

<Callout type="tip" title="`SKIP LOCKED` Is the Job-Queue Primitive">
A worker doing `SELECT … WHERE status = 'queued' FOR UPDATE SKIP LOCKED LIMIT 1` grabs an unclaimed row without waiting on peers — the basis of a simple, correct queue table.
</Callout>

| Table lock | Use |
| :--- | :--- |
| `ACCESS EXCLUSIVE` | Implied by `ALTER TABLE`, `VACUUM FULL`, `TRUNCATE` |
| `SHARE` / `SHARE ROW EXCLUSIVE` | Manual, rarely needed |
| Default `ALTER TABLE` | Takes `ACCESS EXCLUSIVE` — blocks **everything** |

```sql
LOCK TABLE t IN ACCESS EXCLUSIVE MODE;
ALTER TABLE users ADD COLUMN bio text;   -- brief ACCESS EXCLUSIVE (fast if no default rewrite)
```

## Deadlocks, Blocking & Timeouts

```sql
SHOW deadlock_timeout;                            -- default 1s
SET lock_timeout = '5s';                          -- fail rather than wait forever
SET statement_timeout = '30s';                    -- cap any single statement
SET idle_in_transaction_session_timeout = '60s';  -- kill abandoned idle txns
```

```sql
-- Who is blocking whom?
SELECT
  blocked.pid, blocked.query AS blocked_query,
  blocker.pid, blocker.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocker
  ON blocker.pid = ANY (pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;
```

```sql
-- Targeted termination
SELECT pg_cancel_backend(pid);   -- polite: cancels the current query
SELECT pg_terminate_backend(pid);-- forceful: ends the session
```

| Strategy | Prevents |
| :--- | :--- |
| Touch tables/rows in a **consistent order** | Most deadlocks |
| Keep transactions **short** — never wait on user I/O | Lock pile-ups |
| Set `lock_timeout` on DDL/OLTP work | One stuck query blocking the queue |
| Retry on `40001` **and** `40P01` (deadlock) | User-visible errors |
| `idle_in_transaction_session_timeout` | Forgotten open transactions holding snapshots |

## Advisory Locks

```sql
SELECT pg_advisory_lock(42);                        -- session-level, manual release
SELECT pg_try_advisory_lock(42);                    -- non-blocking; returns bool
SELECT pg_advisory_xact_lock(42);                   -- released automatically at txn end
SELECT pg_advisory_lock(hashtext('nightly-etl'));   -- names, not magic numbers
SELECT pg_advisory_unlock(42);
```

Use for application-level mutual exclusion that spans more than one table. Prefer the `_xact_` variants so a crash can't leak the lock.

## MVCC, Dead Tuples & Bloat

Every `UPDATE`/`DELETE` writes a new row version and marks the old one dead. Dead tuples are reclaimed later by `VACUUM`.

```sql
VACUUM t;                 -- reclaim dead tuples (no table lock)
VACUUM (VERBOSE, ANALYZE) t;
VACUUM FULL t;            -- rewrites table, takes ACCESS EXCLUSIVE — usually avoid
REINDEX INDEX CONCURRENTLY idx_name;
ANALYZE t;                -- refresh planner statistics
```

```sql
-- Live vs. dead tuples and last (auto)vacuum
SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum,
       vacuum_count, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

```sql
-- Table bloat estimate
SELECT current_database(), relname, n_dead_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY dead_pct DESC;
```

| Setting | Guidance |
| :--- | :--- |
| `autovacuum_vacuum_scale_factor` | Lower to `0.02` for hot, fast-changing tables |
| `autovacuum_vacuum_threshold` | Absolute dead rows before vacuum |
| `autovacuum_vacuum_cost_limit` | Raise to let autovacuum work harder |
| `autovacuum_max_workers` | More parallel cleanup for many busy tables |
| Per-table override | `ALTER TABLE t SET (autovacuum_vacuum_scale_factor = 0.02);` |

<Callout type="warn" title="Long Transactions Block Vacuum">
Vacuum cannot remove a dead tuple that any open transaction might still need. A single connection that has been `idle in transaction` for hours freezes cleanup database-wide. Watch `pg_stat_activity.state` and set `idle_in_transaction_session_timeout`.
</Callout>

## Transaction-ID Wraparound

PostgreSQL's transaction IDs are 32-bit and wrap around. Vacuum "freezes" old rows so this is safe — but if freezing falls behind, PostgreSQL will refuse new writes to protect your data.

```sql
-- How much room is left before wraparound protection kicks in?
SELECT datname,
       age(datfrozenxid)                                    AS xid_age,
       current_setting('autovacuum_freeze_max_age')::bigint AS max_age,
       round(100.0 * age(datfrozenxid)
             / current_setting('autovacuum_freeze_max_age')::bigint, 1) AS pct
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

| `age(datfrozenxid)` | Meaning |
| :--- | :--- |
| < 200M | Healthy |
| ≈ 200M (`autovacuum_freeze_max_age`) | Forced anti-wraparound autovacuum kicks in |
| ≈ 1.5B | Alarms; wraparound protection near |
| 2B | **Database stops accepting writes** |

Never `VACUUM` with `FREEZE` disabled on a lagging database as a "fix"; run plain `VACUUM` (or `VACUUM FREEZE`) on the oldest tables until the age drops.

## Backup & Recovery Command Deck

```bash
# Logical — a single database, portable, SQL or custom format
pg_dump -Fc -d travelbuddy -f travelbuddy.dump         # custom (compressed, selectable)
pg_dump -Fc -n public -t bookings -d travelbuddy -f bookings.dump
pg_dump -Fp -d travelbuddy -f travelbuddy.sql          # plain SQL
pg_dumpall --roles-only -f roles.sql                   # cluster-level (roles!): no -d

# Restore
createdb travelbuddy_restore
pg_restore -d travelbuddy_restore --jobs=4 travelbuddy.dump
psql -d travelbuddy_restore -f travelbuddy.sql
pg_restore -d travelbuddy_restore --clean --if-exists travelbuddy.dump
pg_restore -l travelbuddy.dump > toc.txt               # list contents first

# Parallel dump of one database
pg_dump -Fd -j 4 -d travelbuddy -f /backups/travelbuddy.dir
```

<Callout type="tip" title="Order Matters on Cluster Restores">
`pg_dumpall` output restores roles and tablespaces *before* databases. Restore the roles dump first, then the databases, or ownership will fail.
</Callout>

```bash
# Physical base backup + continuous WAL archiving (primary)
pg_basebackup -D /backups/base -Fp -Xs -P -R
# postgresql.conf on the primary:
#   wal_level = replica
#   archive_mode = on
#   archive_command = 'test ! -f /wal/%f && cp %p /wal/%f'
```

```bash
# Point-in-Time Recovery — restore the base, then replay to a target moment
# recovery settings (postgresql.conf or recovery.signal's postgresql.auto.conf):
#   restore_command = 'cp /wal/%f %p'
#   recovery_target_time = '2026-03-14 09:31:00+00'
#   recovery_target_action = 'promote'
touch /var/lib/postgresql/data/recovery.signal      # PG12+: signal file, not recovery.conf
pg_ctl -D /var/lib/postgresql/data start
```

| Goal | Tool |
| :--- | :--- |
| One database, version-portable, selectable objects | `pg_dump` / `pg_restore` |
| Whole cluster incl. roles | `pg_dumpall` |
| Byte-for-byte cluster + PITR | `pg_basebackup` + WAL archive |
| Recover to an exact moment | Base backup + `recovery_target_time` |
| Fast failover / read scaling | Streaming replication (Stage 4) |

## The Restore Drill (Non-Negotiable)

A backup you have never restored is a hope, not a backup. Periodically:

1. **Dump** — `pg_dump -Fc -d travelbuddy -f nightly.dump`.
2. **Restore into a scratch database** — never over the original.
3. **Verify data actually arrived** — count rows, spot-check a recent booking, confirm indexes/constraints exist.
4. **Automate it** — schedule the drill and alert if it fails.
5. **Record the RTO** — how long did the restore take? That is your real recovery time objective.

```sql
-- After a restore, prove the data is there
SELECT count(*) FROM bookings;
SELECT max(booked_at) FROM bookings;              -- should be near the dump time
SELECT indexname FROM pg_indexes WHERE tablename = 'bookings';
SELECT conname FROM pg_constraint WHERE conrelid = 'bookings'::regclass;
```

## Failure-Mode Decision Table

| Symptom | Likely cause | First response |
| :--- | :--- | :--- |
| `could not serialize access` (`40001`) | Snapshot / SSI conflict | Retry the whole transaction |
| `deadlock detected` (`40P01`) | Inconsistent lock ordering | Reorder access; retry |
| Queries queue up, all idle | A long `ACCESS EXCLUSIVE` or open txn | `pg_blocking_pids`, then cancel/terminate |
| Table grows but rows don't | Bloat from dead tuples | Check `n_dead_tup`, tune autovacuum |
| Index scan slower over time | Index bloat | `REINDEX … CONCURRENTLY` |
| Autovacuum never finishes | Long-lived snapshots + too few workers | Kill idle txns, raise cost limits/workers |
| `database is not accepting commands` | Wraparound protection | Freeze oldest tables immediately |
| Restore fails on ownership | Roles missing | Restore `pg_dumpall --roles-only` first |
