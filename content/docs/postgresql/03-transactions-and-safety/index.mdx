Welcome to **Stage 3: Transactions, Concurrency & Data Safety** — the correctness core.

Fast queries are worthless if the answer is wrong or the data disappears. This stage is about the guarantees that let you trust your database: what a transaction promises, which concurrency anomalies each isolation level permits, how PostgreSQL actually keeps readers and writers out of each other's way, and how to bring everything back after a disaster.

---

## Pedagogical Philosophy

<Callout type="info" title="Concurrency Is Where Intuition Fails">
Single-threaded reasoning is reliable. The moment two transactions interleave, outcomes stop matching the code you wrote. Every anomaly — lost update, phantom, **write skew** — is a *specific* interleaving that a *specific* isolation level allows. Learn them by name and you'll spot the bug before it reaches production.
</Callout>

By the end of this stage you will be able to:

- Explain exactly what Atomicity, Consistency, Isolation and Durability each guarantee.
- Name and reproduce the classic anomalies, and pick the isolation level that forbids them.
- Describe PostgreSQL's MVCC, why dead tuples accumulate, and how to keep vacuum healthy.
- Take, restore, and test backups, and recover to a point in time.
