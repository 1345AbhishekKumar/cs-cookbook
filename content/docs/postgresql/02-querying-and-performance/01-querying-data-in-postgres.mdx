## The Shape of a Query

Every read is some arrangement of the same clauses. Note that **you write them in one order and the engine runs them in another**:

```sql
SELECT   customer_id, count(*) AS bookings     -- 5 which columns
FROM     bookings                               -- 1 which table(s)
WHERE    status = 'paid'                        -- 2 which rows
GROUP BY customer_id                            -- 3 group them
HAVING   count(*) > 1                           -- 4 filter the groups
ORDER BY bookings DESC                          -- 6 sort
LIMIT    10;                                    -- 7 take the top N
```

```mermaid
flowchart LR
    F["FROM / JOIN"] --> W["WHERE"] --> G["GROUP BY"] --> H["HAVING"] --> S["SELECT"] --> O["ORDER BY"] --> L["LIMIT"]

    style F fill:#0f172a,stroke:#38bdf8,stroke-width:2px,color:#ffffff
    style S fill:#0f172a,stroke:#34d399,stroke-width:2px,color:#ffffff
```

Two consequences fall out of that order:

- A `SELECT` alias is usable in `ORDER BY` but **not** in `WHERE`.
- `WHERE` filters rows *before* grouping; `HAVING` filters groups *after*.

## Filtering

```sql
SELECT flight_no, origin, destination, base_price_cents
FROM flights
WHERE departure_at >= '2026-07-01' AND departure_at < '2026-08-01'   -- half-open range
  AND seats_available > 0
  AND destination IN ('BCN', 'MAD', 'LIS')
  AND flight_no LIKE 'IB%';
```

| Operator | Note |
| :--- | :--- |
| `= <> != < > <= >=` | Ordinary comparisons (`<>` and `!=` both mean not-equal) |
| `BETWEEN a AND b` | Inclusive range — **avoid on timestamps** |
| `IN (...)` | Set membership |
| `LIKE` / `ILIKE` | Pattern matching: `%` matches 0+ characters; `_` matches exactly 1 character. `ILIKE` is case-insensitive. |
| `IS NULL` / `IS NOT NULL` | The only correct null test |
| `col = ANY(array)` | Membership against an array |

<Callout type="info" title="Wildcards: `%` vs. `_`">
- `'IB%'` matches `'IB'`, `'IB1'`, `'IB3412'` (any number of trailing characters).
- `'IB____'` matches `'IB3412'` (exactly four characters after `IB`), but will **not** match `'IB10'`.
</Callout>

<Callout type="warn" title="Two Traps Worth Repeating">
1. **`BETWEEN` on timestamps excludes the end of the last day.** Use `>= start AND < next_start` (a half-open range).
2. **`NOT IN` with a `NULL` returns zero rows.** Prefer `NOT EXISTS`. And `WHERE col = NULL` never matches — use `IS NULL`.
</Callout>

## Calculated Columns, Arithmetic & Safe Math

SQL queries are not limited to fetching raw table values. You can compute expressions, apply arithmetic, and alias the output using `AS`:

```sql
SELECT flight_no,
       base_price_cents,
       round(base_price_cents * 0.15) AS discount_15_pct,
       base_price_cents - round(base_price_cents * 0.15) AS promotional_price_cents
FROM flights;
```

| Operator | Action | Example |
| :--- | :--- | :--- |
| `+`, `-`, `*`, `/` | Standard arithmetic | `100 + 20` → `120`, `10 / 2` → `5` |
| `%` | Modulo (remainder) | `10 % 3` → `1` |
| `^` | Exponentiation | `2 ^ 3` → `8` |
| `\|/` | Square root | `\|/ 25` → `5` |

### Defensive Math: Avoiding Division by Zero

Dividing by zero in PostgreSQL throws a runtime error that immediately aborts your transaction:

```sql
-- ❌ Throws: ERROR: division by zero
SELECT total_cents / seats_booked FROM flight_stats;
```

Use **`NULLIF`** and **`COALESCE`** to make calculations resilient:

```sql
-- NULLIF(val, 0) turns 0 into NULL. In SQL, any division by NULL yields NULL (no crash).
-- COALESCE then provides a safe fallback:
SELECT COALESCE(total_cents / NULLIF(seats_booked, 0), 0) AS avg_seat_cents
FROM flight_stats;
```

### Fallbacks for Nullable Columns with `COALESCE`

`COALESCE` returns the first non-null argument in its list:

```sql
SELECT full_name,
       COALESCE(phone, 'Not provided') AS contact_phone
FROM customers;
```

## Date & Time Expressions: `EXTRACT`, `AGE` and Casts

PostgreSQL has the richest date and time toolkit in relational databases:

```sql
SELECT flight_no,
       departure_at,
       departure_at::date                       AS flight_date,       -- extract date only
       departure_at::time                       AS flight_time,       -- extract time only
       EXTRACT(YEAR FROM departure_at)          AS flight_year,
       EXTRACT(DOW FROM departure_at)           AS day_of_week,       -- 0 = Sunday, 6 = Saturday
       AGE(departure_at, now())                 AS time_until_flight  -- returns an interval
FROM flights;
```

| Function / Syntax | What it produces |
| :--- | :--- |
| `::date`, `::time` | Cast timestamp down to its date or time component |
| `EXTRACT(field FROM ts)` | Pulls numeric fields (`YEAR`, `MONTH`, `DAY`, `HOUR`, `DOW`, `EPOCH`) |
| `AGE(t1, t2)` | Difference as a human-readable interval (`1 year 2 mons 3 days`) |
| `AGE(ts)` | Equivalent to `AGE(current_date, ts)` — handy for customer age calculations |
| `now() +/- interval '...'` | Add or subtract durations (`interval '2 hours'`, `'30 days'`) |

## Sorting and Pagination

```sql
SELECT flight_no, departure_at, seats_available
FROM flights
ORDER BY seats_available DESC, departure_at ASC
LIMIT 20 OFFSET 40;
```

| Feature | Syntax |
| :--- | :--- |
| Asc/desc | `ORDER BY col DESC` |
| Nulls placement | `ORDER BY col DESC NULLS LAST` |
| Standard pagination | `OFFSET 40 ROWS FETCH FIRST 20 ROWS ONLY` |
| Fast deep pagination | Keyset: `WHERE (departure_at, id) < (:last_ts, :last_id)` |

<Callout type="tip" title="`OFFSET` Gets Slower the Deeper You Go">
`OFFSET 100000` makes PostgreSQL produce and discard 100,000 rows. **Keyset pagination** seeks past the last row you saw, staying fast at any depth. Use `OFFSET` only for shallow pages.
</Callout>

## Joins

A join combines rows from two tables; the **join type** decides what happens to rows with no partner.

| Join | Keeps unmatched rows from… |
| :--- | :--- |
| `INNER JOIN` | Neither (only matches) |
| `LEFT JOIN` | The left table (NULLs on the right) |
| `RIGHT JOIN` | The right table |
| `FULL OUTER JOIN` | Both |
| `CROSS JOIN` | Cartesian product |
| `LATERAL` | Correlated subquery in `FROM` |

```sql
-- Every customer with their booking count, including those with none
SELECT c.full_name, count(b.id) AS bookings
FROM customers c
LEFT JOIN bookings b ON b.customer_id = c.id
GROUP BY c.id, c.full_name
ORDER BY bookings DESC;
```

<Callout type="error" title="The LEFT JOIN → WHERE Trap">
Filtering the *right* table in `WHERE` silently converts a `LEFT JOIN` into an `INNER JOIN`:

```sql
-- ❌ customers without paid bookings are dropped
... LEFT JOIN bookings b ON b.customer_id = c.id WHERE b.status = 'paid';
-- ✅ put the condition in ON
... LEFT JOIN bookings b ON b.customer_id = c.id AND b.status = 'paid';
```
</Callout>

### "Has at least one" and "has none"

```sql
-- Semi-join
SELECT * FROM customers c WHERE EXISTS (SELECT 1 FROM bookings b WHERE b.customer_id = c.id);
-- Anti-join (NULL-safe)
SELECT * FROM customers c WHERE NOT EXISTS (SELECT 1 FROM bookings b WHERE b.customer_id = c.id);
```

## Grouping and Aggregation

```sql
SELECT status,
       count(*)                         AS bookings,
       sum(total_cents)                 AS revenue_cents,
       count(*) FILTER (WHERE total_cents > 20000) AS big_bookings
FROM bookings
GROUP BY status
HAVING sum(total_cents) > 100000          -- filter groups, not rows
ORDER BY revenue_cents DESC;
```

| Function | Returns |
| :--- | :--- |
| `count(*)` / `count(col)` | All rows / non-null values |
| `sum`, `avg`, `min`, `max` | Aggregates (empty set → `NULL`) |
| `count(DISTINCT col)` | Distinct non-null values |
| `string_agg(col, ',')`, `array_agg(col)` | Concatenate / collect |
| `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)` | Median |

<Callout type="info" title="The Golden Rule of GROUP BY">
Every column in `SELECT` must be either **aggregated** or **listed in `GROUP BY`**. PostgreSQL enforces this (unlike some databases that quietly pick a row for you).
</Callout>

## Subqueries and CTEs

```sql
-- Scalar subquery
SELECT c.full_name,
       (SELECT max(b.created_at) FROM bookings b WHERE b.customer_id = c.id) AS last_booking
FROM customers c;

-- CTE: name a step so the query reads top-to-bottom
WITH paid AS (
    SELECT * FROM bookings WHERE status = 'paid'
),
revenue AS (
    SELECT customer_id, sum(total_cents) AS total FROM paid GROUP BY customer_id
)
SELECT c.full_name, r.total
FROM revenue r JOIN customers c ON c.id = r.customer_id
ORDER BY r.total DESC;
```

`WITH RECURSIVE` traverses trees and graphs (org charts, flight connections) — always include a depth limit or cycle guard.

## Window Functions

`GROUP BY` collapses rows; a **window function** computes across related rows while **keeping every row**. This is how you do rankings, running totals, and moving averages.

```text
function() OVER (PARTITION BY group_col ORDER BY order_col frame)
```

```sql
SELECT customer_id, created_at, total_cents,
       rank()       OVER (PARTITION BY customer_id ORDER BY total_cents DESC) AS rnk,
       sum(total_cents) OVER (PARTITION BY customer_id ORDER BY created_at)   AS running_total,
       lag(total_cents) OVER (PARTITION BY customer_id ORDER BY created_at)   AS previous_booking
FROM bookings;
```

| Goal | Expression |
| :--- | :--- |
| Unique sequence | `row_number() OVER (...)` |
| Ranking | `rank()` / `dense_rank()` |
| Previous / next row | `lag(x)` / `lead(x)` |
| Running total | `sum(x) OVER (PARTITION BY g ORDER BY o)` |
| Moving average | `avg(x) OVER (ORDER BY o ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` |
| Percent of total | `100.0 * x / sum(x) OVER (...)` |

<Callout type="warn" title="Window Functions Can't Go in `WHERE`">
They are computed *after* `WHERE`. To keep only the top row per group, wrap the window in a CTE and filter the outer query:

```sql
WITH ranked AS (
    SELECT *, row_number() OVER (PARTITION BY customer_id ORDER BY total_cents DESC) AS rn
    FROM bookings
) SELECT * FROM ranked WHERE rn = 1;
```
</Callout>

## Modifying Data: Safe `UPDATE` & `DELETE`

Writing queries is only half the job. Real applications mutate existing records.

### 1. Updating Records

`UPDATE` changes specific columns in rows that match a `WHERE` filter:

```sql
-- Update single or multiple columns in one statement
UPDATE customers
SET full_name = 'Ada King-Lovelace',
    phone = '+34 600 111 222'
WHERE email = 'ada@example.com';
```

You can also compute updated values directly from existing column data:

```sql
-- Apply a 10% price bump to low-capacity flights
UPDATE flights
SET base_price_cents = round(base_price_cents * 1.10)
WHERE seats_available < 10;
```

### 2. Deleting Records

`DELETE FROM` removes rows that match your criteria:

```sql
DELETE FROM bookings
WHERE status = 'cancelled'
  AND created_at < now() - interval '90 days';
```

### The #1 Production Trap: The Missing `WHERE` Clause

<Callout type="error" title="Catastrophic Hazard: An Unfiltered UPDATE or DELETE Affects ALL Rows">
In SQL, omitting `WHERE` does not produce an error — it executes across **every single row in the table**:

```sql
-- ❌ DISASTER: overwrites every customer's name in the entire database!
UPDATE customers SET full_name = 'Ada Lovelace';

-- ❌ DISASTER: wipes every record in the table immediately!
DELETE FROM customers;
```
</Callout>

### How to Modify Data Defensively

When running manual `UPDATE` or `DELETE` statements in `psql`, wrap them in an explicit transaction block:

```sql
BEGIN;

DELETE FROM customers WHERE created_at < '2020-01-01';

-- Verify how many rows were affected and inspect the remaining table:
SELECT count(*) FROM customers;

-- If everything looks correct, make it permanent:
COMMIT;

-- If you made a mistake or deleted the wrong rows, abort cleanly:
ROLLBACK;
```

### Foreign Key Constraints on `DELETE`

If a table is referenced by another table with an `ON DELETE RESTRICT` foreign key, deleting the parent row will fail:

```sql
DELETE FROM customers WHERE id = '...';
-- ERROR: update or delete on table "customers" violates foreign key constraint "bookings_customer_id_fkey"
-- DETAIL: Key (id)=(...) is still referenced from table "bookings".
```

You must either delete or reassign the child records first (`DELETE FROM bookings WHERE customer_id = '...'`), or configure the foreign key with `ON DELETE CASCADE` (handled with extreme care in **[Stage 1](/docs/postgresql/01-getting-started/03-tables-types-and-constraints)**).

## Practice

```sql
-- 1. Revenue per destination, biggest first
SELECT f.destination, sum(b.total_cents) AS revenue
FROM booking_items bi
JOIN bookings b ON b.id = bi.booking_id AND b.status = 'paid'
JOIN flights  f ON f.id = bi.flight_id
GROUP BY f.destination
ORDER BY revenue DESC;

-- 2. The 3 largest bookings per customer (top-N per group)
WITH ranked AS (
    SELECT customer_id, id, total_cents,
           row_number() OVER (PARTITION BY customer_id ORDER BY total_cents DESC) AS rn
    FROM bookings
)
SELECT * FROM ranked WHERE rn <= 3;

-- 3. Each customer's most recent booking date
SELECT c.full_name,
       (SELECT max(created_at) FROM bookings b WHERE b.customer_id = c.id) AS last_booking
FROM customers c
ORDER BY last_booking DESC NULLS LAST;
```
