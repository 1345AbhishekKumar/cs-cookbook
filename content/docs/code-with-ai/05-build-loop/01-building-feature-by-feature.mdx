## The Vertical Slice Principle

A **vertical slice** is a feature that cuts through all layers of your stack — from UI to database — but covers exactly one user-facing behaviour. It's independently shippable. A user can interact with it. You can demo it. You can deploy it.

The test is simple: *Can a real user try this in isolation?* If yes, it's a good slice.

| ❌ Bad Slice (Too Big) | ✅ Good Slice (Shippable) |
|---|---|
| Implement all authentication | User can sign up with email + password |
| Build the dashboard | Dashboard shows the user's name and plan |
| Add email notifications | User receives welcome email on sign-up |
| Implement billing | User can enter card details on the billing page |
| Build user settings | User can change their display name |

Every bad slice on the left can be decomposed into 3–5 good slices on the right. Each good slice is one agent session. One session = one commit. One commit = one unit of reviewable, testable, shippable work.

<LessonNote variant="myth" title="Myth: Bigger tasks = less back and forth">
Giving the AI a massive task doesn't save you time — it multiplies your review burden. You end up with hundreds of lines of AI-generated code you can't fully understand, interleaved with subtle bugs, and no clear way to roll back part of it. Smaller tasks give you checkpoints, cleaner diffs, and more control.
</LessonNote>

## The PDCA Build Loop

The build loop maps directly onto the classic **Plan → Do → Check → Act** cycle, adapted for AI-assisted development.

<Steps>
  <Step>
    ### Decompose — Write a Build Ticket
    Before opening your agent, write a build ticket. This is the single-sentence task, its acceptance criteria, which files are in scope, and hard constraints ("do NOT touch the auth middleware"). This is your prompt. A build ticket forces you to think before you code.
  </Step>
  <Step>
    ### Plan — Run in Plan Mode
    Paste your build ticket into the agent running in **Plan mode** (Cursor's `⌘.` or Claude Code's `--plan` flag). Read the plan carefully. Does it touch the right files? Does the approach make sense? Reject plans that modify files outside scope or propose architectural changes you didn't ask for.
  </Step>
  <Step>
    ### Code — Switch to Act Mode
    Once the plan looks right, approve it. The agent implements. You watch but don't interfere mid-session — interrupting breaks the agent's reasoning chain. Let it finish, then review.
  </Step>
  <Step>
    ### Check — Review the Diff and Run Tests
    Read every line of the diff. Run your test suite. Check the 10-point review checklist (covered in the next lesson). If something looks wrong, don't patch over it — raise a new build ticket to fix it cleanly.
  </Step>
  <Step>
    ### Commit — Lock in the Work
    If the diff looks good and tests pass, commit with a conventional message. This creates a stable checkpoint. Your next agent session starts from a clean state.
  </Step>
  <Step>
    ### Loop — Next Slice
    Close the agent session. Open a new one. Load your `AGENTS.md` context file. Paste the next build ticket. Repeat.
  </Step>
</Steps>

## Writing a Build Ticket

The build ticket is your most important prompt. It's not a chat message — it's a structured specification. Here's the format:

```markdown
## Task
Allow a user to sign up with an email address and password.

## Context
- We are using Next.js 14 App Router with server actions.
- Drizzle ORM is configured and connected to a Neon PostgreSQL database.
- The `users` table already exists in `db/schema.ts` with fields: id, email, createdAt.
- We use `bcryptjs` for password hashing (already installed).
- Auth state is managed via `next-auth` v5 (beta) — see `auth.ts`.

## Acceptance Criteria
1. A sign-up form at `/sign-up` collects email and password.
2. Password is hashed with bcrypt before storing.
3. Duplicate email returns a user-friendly error message.
4. On success, user is redirected to `/dashboard`.
5. Form has client-side validation (email format, min 8 char password).
6. All server actions are in `app/actions/auth.ts`.

## Files to Touch (Approximate)
- `app/(auth)/sign-up/page.tsx` (create)
- `app/actions/auth.ts` (create)
- `db/schema.ts` (add passwordHash field)
- `components/ui/SignUpForm.tsx` (create)

## Do NOT
- Do not modify `auth.ts` or any existing middleware.
- Do not install new dependencies without asking first.
- Do not add any console.log statements.
```

This level of specificity isn't over-engineering — it's what separates a 20-minute agent session from a 3-hour one. The agent has everything it needs. The scope is clear. The constraints are explicit.

## Git Hygiene for AI Projects

AI moves fast. That means your git discipline needs to be iron-clad. The agent doesn't understand your repo history — **you** are the version control layer.

**The four rules:**

1. **Commit before every agent session.** Never start an agent session with uncommitted changes. If something goes wrong, you need a clean rollback point.
2. **Never let an agent modify more than 20 files per session without a review checkpoint.** Watch the file change count in your diff. If it's ballooning, stop and review.
3. **Always work on a feature branch.** Never let the agent commit directly to `main`.
4. **Write conventional commit messages.** Use the `feat:`, `fix:`, `chore:`, `refactor:` prefixes. This makes `git log` readable when you're debugging a regression.

Run this routine before every agent session:

```bash
# Make sure you're starting clean
git status

# Create a feature branch for this slice
git checkout -b feature/user-signup

# Confirm your working directory is clean
git diff --stat

# You're ready. Open your agent and paste the build ticket.
```

After the agent session, review your diff before committing:

```bash
# Review every changed file
git diff --stat
git diff

# Run tests
pnpm test

# Commit with a conventional message
git add -A
git commit -m "feat(auth): add user signup with bcrypt password hashing"
```

## Context Window Resets

Here's a habit most developers skip, and it costs them dearly: **start a fresh agent session for every build ticket.**

Context bloat is real. After a long session, the agent's earlier context is stale, its understanding of the current file state drifts, and it starts making mistakes — hallucinating APIs, referencing files that have changed, or reverting decisions it made earlier.

The reset routine:

```
1. Close your current agent chat session completely.
2. Open a new session.
3. Paste the contents of your AGENTS.md at the top.
4. Add a one-line current state note: "We just completed the sign-up feature. It's committed. Moving to the login feature."
5. Paste your next build ticket.
```

It takes 30 seconds. It saves hours of confusion.

<AnalogyCard name="Building with LEGO vs Pouring Concrete">
  <div><strong>LEGO:</strong> You place one brick at a time. Each brick is solid and well-placed before the next goes on. You can pull a brick off and reposition it. You can tear down the third floor without touching the first. Vertical slices are LEGO.</div>
  <div><strong>Concrete:</strong> Once poured, the concrete sets. You can't move what's already hardened. Mistakes are permanent and expensive to fix. Asking an AI to "build the whole app" is pouring concrete — by the time you see the shape, it's too late to change it.</div>
</AnalogyCard>

<Callout type="info">
The best AI-assisted projects ship something to real users within the first week. Not a polished product — a working slice. A sign-up form. A dashboard with real data. Something a human can touch. Vertical slices make this possible because each slice is independently deployable. Don't wait for perfection. Ship slices.
</Callout>

## Practical: Your Feature → Build Tickets

Here's the transformation process for any feature list:

```
Feature List → Vertical Slices → Build Tickets → Agent Sessions → Commits
```

If your feature list says "User Profiles," your slices might be:

1. User can view their own profile page
2. User can edit their display name
3. User can upload a profile picture
4. User profile is visible to other users (public page)
5. User can set their profile to private

Each becomes one build ticket. Each build ticket becomes one agent session. Each session produces one clean commit. That's the loop.

<Takeaway>
One agent session. One vertical slice. One clean commit. The PDCA build loop — Decompose, Plan, Code, Check, Commit — is your repeating unit of progress. Write a build ticket before every session. Reset your context between sessions. Commit before you start and after you finish. Small, steady, shippable.
</Takeaway>

<TryIt>
Take your current project's feature list. Pick any 5 features. Convert each into a build ticket using the template above — Task, Context, Acceptance Criteria, Files to Touch, Do NOT. Order them by dependency (what must exist before what). Start with ticket 1 in a fresh agent session right now. Commit the result before moving to ticket 2.
</TryIt>
