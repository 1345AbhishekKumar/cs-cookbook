<LessonIntro>
Two developers build the same SaaS app. Developer A writes a DESIGN.md on day one: exact hex codes, font stacks, border radii, shadow scales, and a list of forbidden patterns. Every Cursor session starts by reading this file. Developer B tells the agent to "make it look nice" and trusts it to be consistent. Ten sessions later, Developer A has a product that feels like a single team designed every pixel. Developer B has a Frankenstein of six different button styles, three shadow systems, and four different shades of "primary blue" — all generated by an agent doing its best with no constraints. DESIGN.md is the contract between your creative vision and your agent's execution.

## What DESIGN.md Is (and Is Not)

Before you write anything, understand where DESIGN.md fits in the trio of agent-guiding documents:

| File | Purpose | Contains |
|------|---------|---------|
| **DESIGN.md** | Visual identity contract | Color tokens, typography scale, spacing system, component patterns, forbidden CSS patterns |
| **AGENTS.md** | Behavioral and architectural rules | Coding conventions, folder structure, tech stack decisions, feature list, architecture diagrams |
| **CLAUDE.md** | Session-level rules (Claude Code) | Claude-specific instructions, tool permissions, working memory for the current project context |

<LessonNote variant="warning" title="Don't Mix These Documents">
Keep DESIGN.md focused strictly on visual design. The moment you start adding "always use server components" or "never use `any` in TypeScript" to DESIGN.md, you've polluted it. Those rules belong in AGENTS.md. Agents parse these files as context — clean separation means better, more reliable results.
</LessonNote>

## The DESIGN.md Structure

Here is a production-quality DESIGN.md for a fictional SaaS app called **Linky** — a link-shortener and analytics platform. Use this as your structural template:

```mdx
---
brand: Linky
version: 1.0
last_updated: 2025-01-15
inspiration:
  - https://saasframe.io/...
  - https://mobbin.com/apps/...
---

# DESIGN.md — Linky Visual Identity

## Design Principles

1. **Data-forward** — numbers and stats are the hero. Typography and layout exist to serve them.
2. **Dark-first** — the primary experience is dark mode. Light mode is a courtesy.
3. **Dense but breathable** — pack information tightly, but use consistent spacing so it never feels cramped.
4. **Minimal chrome** — UI furniture (borders, shadows, dividers) should be subtle. Content does the work.
5. **Confident, not loud** — one strong CTA per screen. No competing calls to action.

## Spacing System

Base unit: **4px** (Tailwind default scale is perfect).

| Context             | Value       | Tailwind Class |
|---------------------|-------------|----------------|
| Component gap       | 8px         | `gap-2`        |
| Card padding        | 16px–24px   | `p-4` / `p-6` |
| Section padding     | 64px–96px   | `py-16` / `py-24` |
| Page horizontal pad | 24px / auto | `px-6 max-w-7xl mx-auto` |

## Component Patterns

### Buttons
- **Primary:** `bg-indigo-500 hover:bg-indigo-600 text-white font-medium px-4 py-2 rounded-md transition-colors`
- **Secondary:** `bg-zinc-800 hover:bg-zinc-700 text-slate-200 border border-zinc-700 px-4 py-2 rounded-md`
- **Ghost:** `text-slate-300 hover:text-white hover:bg-zinc-800 px-3 py-1.5 rounded-md`
- **Destructive:** `bg-red-500/10 hover:bg-red-500/20 text-red-400 border border-red-500/20 px-4 py-2 rounded-md`
- Border radius: **always `rounded-md` (6px)**. Never pill, never sharp.

### Cards
- Background: `bg-zinc-900`
- Border: `border border-zinc-800`
- Padding: `p-5` or `p-6`
- Hover state (if interactive): `hover:border-zinc-700 transition-colors`
- Shadow: `shadow-sm` maximum. Never `shadow-xl` on cards.

### Inputs
- `bg-zinc-900 border border-zinc-700 text-slate-200 placeholder:text-slate-500 rounded-md px-3 py-2 focus:ring-2 focus:ring-indigo-500 focus:border-transparent`

### Modals
- Overlay: `bg-black/60 backdrop-blur-sm`
- Panel: `bg-zinc-900 border border-zinc-800 rounded-xl p-6 shadow-2xl`

## Forbidden Patterns

These patterns are explicitly banned. If you see them in generated code, remove them immediately:

- ❌ **Never** use `#000000` pure black — use `zinc-950` (`#0a0a0f`) instead
- ❌ **Never** use `#ffffff` pure white — use `slate-50` (`#f8fafc`) instead
- ❌ **Never** use `shadow-xl` or `shadow-2xl` on cards (only on modals)
- ❌ **Never** use `rounded-full` on non-circular elements (badges are ok, buttons are not)
- ❌ **Never** use inline `style=` attributes for colors or spacing — use Tailwind classes
- ❌ **Never** use more than 2 font families on one page
- ❌ **Never** use `font-bold` on body copy — only headings get `font-bold` or above
- ❌ **Never** use gradient backgrounds on cards — only on hero sections
```

## Minimal Starter DESIGN.md

Don't have time for the full version yet? Here's the minimum viable DESIGN.md for a Next.js + Tailwind project:

```mdx
# DESIGN.md

## Core Colors
| Role       | Hex       | Tailwind        |
|------------|-----------|-----------------|
| Background | #0f172a   | bg-slate-900    |
| Surface    | #1e293b   | bg-slate-800    |
| Border     | #334155   | border-slate-700|
| Primary    | #6366f1   | bg-indigo-500   |
| Text       | #f1f5f9   | text-slate-100  |
| Muted Text | #64748b   | text-slate-500  |

## Typography
- Heading: Inter, font-weight 700
- Body: Inter, font-weight 400
- Code: JetBrains Mono

## Spacing Base Unit
4px (standard Tailwind scale)

## Button Style
`bg-indigo-500 hover:bg-indigo-600 text-white rounded-md px-4 py-2 font-medium`

## Card Style
`bg-slate-800 border border-slate-700 rounded-lg p-5`

## Forbidden
- No pure black (#000) or pure white (#fff)
- No shadow-xl on cards
- No inline style attributes for colors
```

## How Agents Use DESIGN.md

Agents like Cursor and Claude Code read context from files at session start. You wire DESIGN.md in by referencing it from your `AGENTS.md` or `.cursorrules` file. Here's what that reference looks like:

```mdx
## Design System

See `DESIGN.md` in the project root for the full design token system.

**Always follow DESIGN.md when:**
- Creating any new UI component
- Modifying an existing component's visual styling
- Choosing colors, spacing, or typography values

When in doubt about a visual decision, check DESIGN.md before inventing a new value.
Do not introduce new color values, shadow scales, or border radii not listed in DESIGN.md.
```

This single paragraph in AGENTS.md is what activates DESIGN.md as an agent constraint. Without this reference, the agent may read DESIGN.md if you explicitly share it — but it won't treat it as a standing rule.

<Callout type="warn">
DESIGN.md is only as useful as it is **accurate**. If you update your Tailwind config — change your primary color, adjust your font stack, switch from `rounded-md` to `rounded-lg` globally — you must update DESIGN.md in the same commit. An outdated DESIGN.md is worse than none at all: it trains your agent to generate code that conflicts with your actual config.
</Callout>

<Takeaway>
DESIGN.md is your visual identity encoded as machine-readable text. It contains color tokens, typography scale, spacing units, component patterns, and an explicit list of forbidden CSS patterns. Reference it from AGENTS.md so your agent treats it as a standing constraint — not just a file to occasionally glance at. Update it whenever you update your Tailwind config.
</Takeaway>
