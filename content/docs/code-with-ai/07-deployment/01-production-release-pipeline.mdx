<LessonIntro>
Shipping an application to production is where theoretical software meets real-world constraints: real DNS records, strict HTTPS certificate handshakes, separate OAuth callback URLs, and live database connection pooling. Many developers get stuck on deployment because production configuration differs from their local `.env.local` files. By separating your production secrets cleanly, delegating the deployment steps to the agent, and running a disciplined post-launch smoke test, shipping becomes a repeatable, stress-free routine.
</LessonIntro>

## 1. Secrets & Environment Segregation

Never share a single database or API key between your local development environment and production. Maintain clear boundaries across three environments:

| Setting | Local Development | Staging / Preview | Production |
|---|---|---|---|
| **Database** | Local Docker / Dev branch | Preview DB Branch | Primary Production Cluster |
| **Stripe Keys** | `sk_test_...` (Test mode) | `sk_test_...` (Test mode) | `sk_live_...` (Live billing) |
| **Auth Redirect** | `http://localhost:3000/callback` | `https://preview.app.com/callback` | `https://app.com/callback` |
| **Object Storage** | `bucket-dev` | `bucket-staging` | `bucket-prod` |

---

## 2. Let the Agent Run the Deploy

Modern agentic IDEs and CLI tools can manage your deployment pipeline directly using the Vercel, Fly.io, or Cloudflare CLIs:

```bash
# Agent runs local build checks before triggering deploy:
bun run build

# Agent triggers production deployment:
vercel --prod
```

If the production build fails due to a missing environment variable or an invalid export, the agent reads the error log directly from the terminal and resolves it in context.

## Reusable Artifact: The Deployment Checklist

| Category | Item | Verified? |
|---|---|---|
| 🔐 **Production Secrets** | Production DB URL, Stripe live keys, and JWT secrets stored in cloud vault | [ ] |
| 🌐 **DNS & Custom Domain** | CNAME and A records propagated; SSL/TLS certificate active | [ ] |
| 🛡️ **Auth Callbacks** | Production domain added to Supabase/Clerk Allowed Redirect URLs | [ ] |
| 🗄️ **DB Migrations** | Schema migrations applied to production database before application restart | [ ] |
| 🔥 **Live Smoke Test** | Verified real sign-up, payment redirect, and core action on production URL | [ ] |
| 📈 **Telemetry & Errors** | Sentry / PostHog logging initialized and receiving live events | [ ] |

---

<Takeaway>
Keep your environments strictly isolated. Use the CLI to let your agent manage build-and-deploy cycles, and always verify your release with a structured post-launch smoke test.
</Takeaway>
