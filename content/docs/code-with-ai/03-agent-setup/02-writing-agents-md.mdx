<LessonIntro>
Every time you start a session with an AI agent, you are starting fresh. The agent has zero memory of your previous conversations — it doesn't know your database schema, your naming conventions, or that you decided last Tuesday to never use `any` in TypeScript. Without an AGENTS.md, you spend the first 10 minutes of every session re-explaining your project. AGENTS.md is the briefing document your agent reads before every session — it's how you compress months of project decisions into something the agent can load instantly.
</LessonIntro>

## What Goes in AGENTS.md

A great AGENTS.md has seven sections. Skip any of them and your agent will fill in the gap with guesses — often wrong ones.

### 1. Project Summary

Two to three sentences. What the app does, who uses it, and what stage it's at. The agent uses this to calibrate the level of polish it applies.

```markdown
# Project Summary
LinkSnip is a SaaS link shortener for marketing teams. Users create branded short links,
organize them in campaigns, and view click analytics by geography and device. The app is
in active development — we have paying customers on the free tier and are building toward
a Pro launch.
```

### 2. Tech Stack

A flat bulleted list of every technology in the project. Include versions for anything where behavior differs between major releases.

```markdown
## Tech Stack
- **Framework**: Next.js 15 (App Router, no Pages Router)
- **Language**: TypeScript 5.x — strict mode enabled
- **Database**: Supabase (PostgreSQL 15)
- **ORM**: Drizzle ORM
- **Auth**: Clerk
- **Payments**: Stripe
- **Styling**: Tailwind CSS v4 + shadcn/ui
- **Deployment**: Vercel
- **Package Manager**: pnpm
```

### 3. Architecture Reference

Link to your architecture diagram or describe the key data flow inline. This prevents the agent from suggesting structures that don't match your actual system.

```markdown
## Architecture
- All data fetching happens in Server Components or Server Actions — never in Client Components
- Client Components are only used for interactivity (forms, modals, drag-and-drop)
- API routes (`/api/*`) exist only for webhooks (Stripe, Clerk) — not for app data
- Supabase is accessed via the Drizzle client, never the raw Supabase JS client
```

### 4. Feature List

A checkbox list of features. Checked = shipped. Unchecked = planned. This gives the agent a map of what exists and what's coming.

```markdown
## Features
- [x] User auth (Clerk)
- [x] Create/delete short links
- [x] Campaign tagging
- [x] Click analytics (basic)
- [ ] Branded domains (in progress)
- [ ] Team workspaces
- [ ] CSV export
```

### 5. Coding Conventions

Exact rules for formatting, naming, and file structure. This is where you prevent the agent from drifting into its own style.

```markdown
## Conventions
- File naming: `kebab-case` for all files and folders
- Component naming: `PascalCase` — e.g., `LinkCard`, `CampaignTable`
- All components in `src/components/` — feature-specific in subfolders: `src/components/links/`
- Server Actions in `src/actions/` — one file per domain: `links.ts`, `campaigns.ts`
- Drizzle schema in `src/db/schema/` — one file per table
- Use `zod` for all input validation in Server Actions
- Environment variables accessed only via `src/env.ts` (T3 Env pattern)
```

### 6. Component Rules

Where components live, how they're named, and when to split a component into smaller pieces.

```markdown
## Component Rules
- shadcn/ui components live in `src/components/ui/` — never modify them directly
- Wrap shadcn primitives in `src/components/` with project-specific defaults
- A component file should not exceed 150 lines — split into sub-components if it does
- Co-locate component-specific types in the same file, not in a separate `types.ts`
```

### 7. Do/Don't Rules

Explicit behavioral guardrails. The agent will follow these verbatim.

```markdown
## Rules
### DO
- Use server components for all data fetching
- Use `next/image` for all images
- Use Drizzle transactions for multi-step DB operations
- Run `pnpm typecheck` before marking any task complete

### DON'T
- Never use `any` in TypeScript — use `unknown` and narrow
- Never put business logic in UI components
- Never use `useEffect` for data fetching — use Server Components
- Never commit `.env.local` — use `.env.example` for reference
- Never use the Supabase JS client directly — always use Drizzle
```

## A Real AGENTS.md Example

Here's a full, production-quality AGENTS.md for LinkSnip. Copy it, adapt it to your project, and commit it to your root directory.

```markdown
# AGENTS.md — LinkSnip

> This file is loaded by all AI agents at the start of every session.
> Keep it up to date as the project evolves.

---

## Project Summary
LinkSnip is a B2B SaaS link shortener for marketing teams. Users create branded short
links, organize them in campaigns, and view click analytics. Stack is Next.js 15 App
Router + Supabase + Clerk + Stripe. Deployed on Vercel.

---

## Tech Stack
- **Framework**: Next.js 15 (App Router only — no Pages Router)
- **Language**: TypeScript 5.x (strict mode)
- **Database**: Supabase (PostgreSQL 15) via Drizzle ORM
- **Auth**: Clerk (userId is the FK for all user-scoped data)
- **Payments**: Stripe (Products, Prices, Subscriptions)
- **Styling**: Tailwind CSS v4 + shadcn/ui
- **Deployment**: Vercel (Edge Functions for the redirect handler)
- **Package Manager**: pnpm

---

## Architecture
- Server Components fetch data — Client Components handle interactivity only
- `/api` routes exist only for: Stripe webhooks, Clerk webhooks, and the redirect handler
- Drizzle schema is source of truth — never write raw SQL outside migrations
- All env vars accessed via `src/env.ts` (validated with T3 Env + Zod)

### Key Data Flow
User → Clerk Auth → Middleware → Server Component → Drizzle → Supabase

---

## Database Schema (abbreviated)
- `users` — synced from Clerk via webhook (clerk_id, email, plan)
- `workspaces` — one per user for now (workspace_id, user_id, name, slug)
- `links` — (link_id, workspace_id, slug, destination_url, campaign_id, created_at)
- `campaigns` — (campaign_id, workspace_id, name)
- `clicks` — (click_id, link_id, country, device, referrer, created_at)

---

## Features
- [x] User auth (Clerk)
- [x] Create / edit / delete short links
- [x] Campaign tagging
- [x] Click count per link
- [x] Stripe billing (Free / Pro)
- [ ] Click analytics dashboard (in progress)
- [ ] Branded custom domains
- [ ] Team workspaces
- [ ] CSV export

---

## File Structure
src/
  app/           # Next.js App Router pages
  actions/       # Server Actions (links.ts, campaigns.ts, billing.ts)
  components/
    ui/          # shadcn/ui primitives (do not edit)
    links/       # Link-specific components
    campaigns/   # Campaign-specific components
    shared/      # Layout, nav, shared UI
  db/
    index.ts     # Drizzle client
    schema/      # One file per table (links.ts, campaigns.ts, clicks.ts)
    migrations/  # Generated by drizzle-kit
  lib/           # Pure utilities (no DB, no auth)
  env.ts         # T3 Env config

---

## Coding Conventions
- File naming: kebab-case everywhere (`link-card.tsx`, `create-link.ts`)
- Component naming: PascalCase (`LinkCard`, `CampaignBadge`)
- Server Action files: one per domain, verb-named exports (`createLink`, `deleteLink`)
- Zod schemas in the same file as the Server Action that uses them
- Tailwind only — no inline styles, no CSS Modules

---

## Rules

### DO
- Use Server Components for data fetching
- Use `next/image` for all images with explicit `width` and `height`
- Wrap DB mutations in Drizzle `.transaction()`
- Validate all Server Action inputs with Zod before touching the DB
- Check RLS policies when adding new tables to Supabase

### DON'T
- Never use `any` — use `unknown` and narrow with Zod or type guards
- Never fetch data inside Client Components (no `useEffect` + fetch)
- Never import from `@supabase/supabase-js` directly — use Drizzle
- Never put business logic in React components
- Never hardcode environment variables — always use `env.ts`
```

## AGENTS.md vs CLAUDE.md vs .cursorrules

Different agents and IDEs read different files. Here's how to think about the ecosystem:

| File | Scope | Read By | Recommended Use |
|---|---|---|---|
| `AGENTS.md` | Universal | Claude Code, Cursor, Windsurf, Copilot, custom agents | **Master file** — all project context |
| `CLAUDE.md` | Claude Code only | Claude Code CLI | Reference AGENTS.md, add Claude-specific commands |
| `.cursorrules` | Cursor IDE only | Cursor | Reference AGENTS.md, add Cursor-specific rules |

<AnalogyCard name="The Employee Handbook">
  <div><strong>The Handbook:</strong> A company has one master employee handbook (the source of truth), plus department-specific addendums that reference it and add role-specific details.</div>
  <div><strong>Your Agent Setup:</strong> AGENTS.md is your master handbook. CLAUDE.md and .cursorrules are department addendums — they say "read AGENTS.md first, then apply these extra rules specific to this tool."</div>
</AnalogyCard>

The pattern for CLAUDE.md and .cursorrules is simply:

```markdown
# CLAUDE.md
See AGENTS.md for full project context and conventions.

## Claude-Specific Commands
- `/grill-with-docs` — run the Matt Pocock requirements interview
- `/to-spec` — compress context into a spec document
- `/implement` — implement a spec with test-first approach
```

## The Matt Pocock Methodology

Matt Pocock (TypeScript educator and tooling author) developed a three-phase workflow for using AI agents on real projects. AGENTS.md is the output of phase one.

| Phase | Command | What Happens |
|---|---|---|
| **1. Grill with Docs** | `/grill-with-docs` | Agent interviews you about the project, reads your docs, asks clarifying questions |
| **2. To Spec** | `/to-spec` | Agent compresses the interview output into a concise technical spec |
| **3. To Tickets** | `/to-tickets` | Agent breaks the spec into ordered, implementable tasks |
| **4. Implement** | `/implement` | Agent implements one ticket at a time with tests |

Install Pocock's skills to get these slash commands in Claude Code:

```bash
npx skills@latest add mattpocock/skills
```

The `/grill-with-docs` command is particularly valuable for generating your first AGENTS.md. Run it on a new project and the agent will ask you 10–15 targeted questions, then produce a draft AGENTS.md from your answers.

<LessonNote variant="myth" title="Myth: AGENTS.md is just a README">
A README describes your project to human developers. AGENTS.md is optimized for machine consumption — it's opinionated, explicit, and rule-heavy. A README says "we use Tailwind CSS." AGENTS.md says "use Tailwind CSS only — no inline styles, no CSS Modules, no styled-components. All custom values go in `tailwind.config.ts`." The specificity is the whole point.
</LessonNote>

## Keeping AGENTS.md Alive

AGENTS.md is a **living document**. Treat it like code — it should be reviewed and updated whenever your project evolves.

Update your AGENTS.md when you:
- Add a new table to the database (update the schema section)
- Change a coding convention (update the conventions section)
- Add a new third-party service (update tech stack and rules)
- Remove a feature from scope (update the feature list)
- Establish a new pattern that the agent keeps getting wrong

<Callout type="warn">
**Stale AGENTS.md is worse than no AGENTS.md.** If your AGENTS.md says you use Drizzle but you migrated to Prisma three weeks ago, the agent will confidently generate Drizzle code for every task. Wrong context is more dangerous than no context because the agent has no reason to question it. Add a "Last Updated" date to your AGENTS.md header and review it monthly.
</Callout>

A good habit: at the end of every major development sprint, spend 10 minutes reviewing your AGENTS.md and bringing it in sync with the current state of the project.

---

<Takeaway>
AGENTS.md is your single most important investment in AI-assisted development. It eliminates the repetitive re-briefing that kills session momentum, prevents the agent from applying wrong conventions, and gives every future session an immediate understanding of your project. Write it once, maintain it as you build, and your agent becomes progressively more accurate as the project grows.
</Takeaway>
