## The AI Project Trap

Here is the insidious thing about coding with AI: generation is so fast that it feels like complexity is free. You ask Cursor to scaffold a multi-tenant SaaS and it generates 40 files in 90 seconds. The illusion is complete — until you try to make those 40 files work together, handle edge cases, pass security reviews, and actually deploy.

Complexity does not scale linearly with features. It scales **exponentially**. Each new feature adds integration points, edge cases, and debugging surface area that multiply against everything that already exists.

| Scope | Realistic Timeline | What Fits |
|---|---|---|
| **Small App** | 1 week | One core feature, no auth, local storage or a single table, Vercel deploy |
| **Medium App** | 1 month | Auth, 3–5 features, one database, basic CRUD, simple billing or sharing |
| **Large App** | 3+ months | Multi-tenant auth, complex data models, payments, roles/permissions, admin panel |
| **Platform** | 6+ months | Multi-product, team features, API, integrations, compliance concerns |

If it is your first AI-assisted project, target the **Small App** column. Ship something. Learn the deployment pipeline. Feel the satisfaction of a real URL you can share. Then scale up.

## The Four Good Project Templates

These four categories represent the highest-success-rate first projects. They are small enough to ship, complex enough to teach real patterns, and immediately useful.

### 1. SaaS Micro-tool

**Examples:** Link shortener, invoice generator, QR code generator, email signature builder, open graph image generator

| | |
|---|---|
| **Core Feature** | One transformation: input → output |
| **Auth Needed** | Optional (anonymous works for v1) |
| **Database** | Single table or key-value store |
| **Complexity** | Low — one API route, one UI form |
| **Ship Timeline** | 2–4 days |

### 2. Personal Dashboard

**Examples:** Fitness tracker, habit tracker, reading log, budget tracker, daily journal

| | |
|---|---|
| **Core Feature** | Log entries + view history |
| **Auth Needed** | Yes (it's personal data) |
| **Database** | 2–3 tables (user, entries, categories) |
| **Complexity** | Medium — auth + CRUD + simple charts |
| **Ship Timeline** | 1–2 weeks |

### 3. Content / Community App

**Examples:** Personal blog, link aggregator, public changelog, newsletter archive, bookmarks list

| | |
|---|---|
| **Core Feature** | Create + display content |
| **Auth Needed** | Admin-only auth (public read) |
| **Database** | Posts, tags, optional comments |
| **Complexity** | Medium — markdown rendering, RSS |
| **Ship Timeline** | 1–2 weeks |

### 4. AI-Powered Tool

**Examples:** AI resume builder, writing assistant, email rewriter, meeting summarizer, code reviewer

| | |
|---|---|
| **Core Feature** | Text in → AI-processed text out |
| **Auth Needed** | Yes (to track API usage / limits) |
| **Database** | User table + history table |
| **Complexity** | Medium-high — streaming, rate limiting, cost management |
| **Ship Timeline** | 2–3 weeks |

## Writing Your One-Page Spec

This is the most valuable 15 minutes you will spend before writing a single line of code. A one-page spec is not a PRD (Product Requirements Document) — those are 40-page corporate artifacts. A spec is a **single-page north star** that keeps you and your agent aligned.

More importantly: **this spec becomes the first message you send to your coding agent.** It gives Claude Code or Cursor's Composer the full context of your project in one shot.

Here is a real spec for a Link Shortener SaaS:

```markdown
# Project Spec: SnapLink — Link Shortener SaaS

## Problem
Developers and marketers need short, trackable links without paying $29/mo for Bitly.

## Target User
Solo developers and small marketing teams who want simple analytics on shared links.

## Core Features
1. Paste a long URL → get a short URL (e.g., snplnk.io/abc123)
2. Click tracking: total clicks, last clicked, country breakdown
3. User accounts: create/manage personal links
4. Custom slug support: snplnk.io/my-custom-name
5. Link expiration: optional date after which link returns 404

## Out of Scope (v1)
- Team workspaces / shared link pools
- A/B testing or redirect rules
- API access / webhooks
- Mobile app
- White-label / custom domains

## Tech Stack
Next.js 15, TypeScript, Supabase (DB + Auth), Drizzle ORM, Tailwind CSS, Vercel

## Success Metric
A user can sign up, create a short link, share it, and see click data — in under 60 seconds.
```

<Callout type="info">
**This spec is your agent's System Prompt.** Before any coding session, paste this spec at the top of your first message to Claude Code or Cursor. It eliminates the most common agent failure: implementing the right feature for the wrong project.
</Callout>

## Feature Listing Strategy

Once you have your spec, list every feature you might ever want — then ruthlessly prioritize using the **MoSCoW method**: Must-have, Should-have, Could-have, Won't-have (for now).

Here is the feature table for SnapLink:

| Feature | MoSCoW | Reason |
|---|---|---|
| Paste URL → short URL | **Must** | Core value proposition |
| Click count tracking | **Must** | Minimum useful analytics |
| User sign-up / login | **Must** | Required for personal link management |
| Custom slug | **Should** | High value, low complexity |
| Link expiration | **Should** | Frequently requested, one DB column |
| Country breakdown | **Could** | Adds value but not day-one critical |
| QR code export | **Could** | Nice to have, small library add |
| Team workspaces | **Won't** | Requires multi-tenant DB schema overhaul |
| API access | **Won't** | Separate product surface; adds auth complexity |
| A/B redirect testing | **Won't** | Feature creep for v1 |

Your agent works best on **Must-have features first**, in order of dependency. Auth before features that require auth. Core data model before features that read it.

<LessonNote variant="myth" title="Build Something Unique to Succeed">
The most common trap for first-time builders: "My project has to be original or it's not worth building." Wrong. There are already hundreds of link shorteners, habit trackers, and AI writing assistants. Building another one is not a failure — it is the fastest way to genuinely learn how they work. The goal of your first AI-assisted project is to **finish it and ship it**, not to disrupt an industry. Uniqueness does not matter for learning. Completion does.
</LessonNote>

<Takeaway>
Scope ruthlessly. Your first AI-assisted project should fit in the "Small App" column — one core feature, ship in under two weeks. Write a one-page spec before writing any code: Problem, Target User, Core Features, Out of Scope, Stack, and Success Metric. Use MoSCoW to enforce feature discipline. The spec is not bureaucracy — it is the context your agent needs to stay on target across every session.
</Takeaway>

<TryIt>
Set a 15-minute timer. Write a one-page spec for your own project idea using the template above. You must include:

1. A one-sentence **Problem** statement
2. A one-sentence **Target User** description
3. Exactly **5 Core Features** — numbered, verb-first ("User can...")
4. At least **3 items explicitly Out of Scope**
5. Your intended **Tech Stack** (even if uncertain — commit to something)
6. A **Success Metric** — one specific thing a user can do that proves v1 works

When the timer goes off, stop. If you are not done, cut features until you are. This constraint is the exercise.
</TryIt>
