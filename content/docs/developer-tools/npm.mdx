## Why do we need npm?

      

In this course we write our styles in a CSS preprocessor called **Sass**.
         Sass is widely used because you can write styles more quickly and efficiently than in pure CSS.

      

The only problem: **browsers cannot read Sass files**. They only understand plain CSS.
         So the Sass has to be *compiled* — converted — into CSS before it can be used.

      

In a real-world development environment you would normally use a build tool to do that conversion
         for you. In this course we use **Gulp**, and to install and run Gulp we need
         **npm**.

      

<Callout type="info">
**The chain of dependencies**
        Sass → needs compiling → Gulp does the compiling → Gulp is installed with npm.
</Callout>

      

npm is a huge part of the JavaScript ecosystem these days, so it is definitely a good skill
         set to have.

    

    
    
      

## What is npm?

      

**npm** stands for *Node Package Manager*. It is:

      

- The main package manager for **Node.js**.
- A huge repository of mostly **open-source software**.
- Free to use by anyone.

      

### The car analogy

      

Imagine you want to build a car. You *could* make every single part yourself — mining the
         metal, melting and casting it, hammering it into shape on an anvil… all while trying not to set
         yourself on fire. It would take a very long time and be very expensive.

      

Most people don't do that. They start by getting all the **pre-built parts** they
         need and assemble those into a complete working car.

      

npm works the same way. Instead of writing every line of code yourself, you rely on pre-built
         code that other people have written:

      

1. An author writes the code for their package.
2. They **publish** it to the npm registry.
3. You **install** it onto your computer using the npm CLI (command line interface).

      

### Packages come in all sizes

      

| Package | What it does | Size |
| --- | --- | --- |
| `chalk` | Sets different colours in your console log messages | ~26 KB |
| `tailwindcss` | A framework for building websites | 30+ MB |

    

    
    
      

## Installing Node.js & npm

      

To use npm on your own computer you first have to install **Node.js**, the JavaScript
         runtime environment.

      

1. Go to `nodejs.org`.
2. Download the version for your operating system.
3. Run the installer — it installs **Node and npm at the same time**.

      

Then verify everything worked by opening your terminal and running:

      
```bash
node -v
npm -v
```

      

Each command should print the version number that was installed, for example:

      
```bash
v20.11.1
10.2.4
```

      

<Callout type="tip">
**Tip**
        If you see "command not found", close and reopen your terminal — the installer updates your
        PATH and a fresh terminal session picks it up.
</Callout>

    

    
    
      

## Local vs. global installs

      

There are two ways to install packages: **locally** and **globally**.

      

### Local installs (the default)

      

Generally you want to install packages locally, *inside the project folder* that needs
         the package. This ensures that when you deploy your project it will include all the necessary
         packages. A local package is only accessible from that specific project folder — other projects
         each have their own set of local packages.

      
```bash
# navigate to your project folder, then:
npm install chalk
```

      

### Global installs

      

Some packages can — and should — be installed globally. This means the package's functions are
         accessible from *any* directory on your computer. Usually you only install packages
         globally when they are meant to be run on the command line from anywhere.

      

The **Gulp CLI** is a classic example: it needs to run whenever you type
         `gulp`, no matter where you are.

      
```bash
npm install -g gulp-cli
```

      

| - | Local | Global |
| --- | --- | --- |
| **Command** | `npm install <package>` | `npm install -g <package>` |
| **Available from** | That project folder only | Any directory |
| **Use for** | Libraries your project code imports | Command-line tools you run yourself |
| **Included in deploy?** | Yes | No |

      

<Callout type="warn">
**Watch out**
        Global packages are not recorded in your project's `package.json`, so
        a teammate cloning your repo will not get them. Anything your *build* depends on should
        be local.
</Callout>

    

    
    
      

## The package.json file

      

If you use multiple packages in a project, one way to keep track of which ones you have
         installed is the `package.json` file. It can also store information
         about your project: name, version, author, GitHub repo, and more.

      

It is super useful, especially if other people want to clone your project and need all the
         specific packages you used. If they run `npm install` in a folder that
         has a `package.json`, npm reads the file and installs everything
         listed — all at once. This comes in handy with deployments too, because the server can install
         the packages right when you deploy.

      

### Creating the file

      

One of the first things you should do when starting a project is create your
         `package.json`:

      
```bash
npm init
```

      

npm will ask you some questions about your project (name, description, etc.) and then create the
         JSON file. If you don't want to answer the questions manually, you can skip them:

      
```typescript
npm init -y
```

      

This makes npm immediately create the file and set all fields to a default value. You can always
         change the information in the future.

      

### What it looks like

      
```json
{
  "name": "responsive-design-course",
  "version": "1.0.0",
  "description": "A responsive website built with HTML, SCSS and JS",
  "author": "Your Name",
  "license": "MIT",
  "scripts": {
    "start": "gulp"
  },
  "dependencies": {
    "chalk": "^5.3.0"
  },
  "devDependencies": {
    "gulp": "^4.0.2",
    "gulp-sass": "^5.1.0"
  }
}
```

      

<Callout type="tip">
**dependencies vs. devDependencies**
        Packages your code needs at runtime go in `dependencies`. Build tools
        and compilers you only need while developing go in `devDependencies`
        (install them with `npm install --save-dev 

`).
</Callout>

    

    
    
      

## What installing a package actually does

      Let's say you have a brand-new project and you need the `chalk`
         package. You type:

      
```bash
npm install chalk
```

      

When it's done, two things happen:

      

1. In `package.json`, `chalk` is now listed
            as a **dependency**. This means you are going to use functions from the chalk
            package in your code, and if you didn't have it, something would probably break.
2. A new folder called `node_modules` is created. This is where npm
            stores all the package files that get installed.

      

### Why are there so many folders?

      

Inside `node_modules` you'll see a folder for
         `chalk` — which makes sense — but also a bunch of other folders with
         different names. Why?

      

Because of the **dependency nature** of npm. You install packages to use other
         people's code, making your project dependent on those packages — and each of those packages is
         also using code from *even more* packages.

      
```bash
chalk
├── ansi-styles
│   └── color-convert
│       └── color-name
└── supports-color
    └── has-flag
```

      

You can see this yourself by opening the `package.json` inside the
         chalk folder — it lists `ansi-styles` and
         `supports-color` as dependencies. Open *their* files and the
         chain continues.

      

To quickly display a list of all installed packages and their versions, run:

      
```bash
npm list
```

      

Keep in mind that chalk is a *relatively small* package. Imagine how many dependencies
         larger packages like webpack or Tailwind require — and you start to understand why the
         `node_modules` folder is often referred to as
         *"the densest matter in the known universe."*

      

<Callout type="info">
**Never commit node_modules**
        Because it can be rebuilt from `package.json` and
        `package-lock.json`, you should always add
        `node_modules/` to your `.gitignore`.
</Callout>

    

    
    
      

## Semantic versioning

      

Like most software, npm packages get updated over time to fix bugs and roll out new features.
         Sounds good, right? Well, these updates are actually one of the biggest sources of headaches
         when working with npm packages.

      

Every package has its own author, so packages get bug fixes and updates independently from one
         another. But because packages are so dependent on each other, this can sometimes cause conflicts
         and errors. It's important to understand how versioning works — and how to update safely so you
         don't break stuff.

      

### Listing versions

      
```bash
npm view chalk versions
```

      

This returns a list of every version of chalk from the beginning. For more detail on each
         version, check out the release page of the package's GitHub repository.

      

### Reading a version number

      

The first public release is generally version `1.0.0`, and each
         release after that goes up in number — but *not* like decimal numbers. npm packages
         follow **semantic versioning**: three digits separated by dots.

      
```bash
2  .  10  .  4
   │        │       │
   │        │       └── PATCH — small bug fixes, backwards compatible
   │        └────────── MINOR — new features, backwards compatible
   └─────────────────── MAJOR — big changes, NOT backwards compatible
```

      

| Digit | Name | Meaning | Safe to update? |
| --- | --- | --- | --- |
| 1st | Major | Big, breaking, non-backwards-compatible changes | ⚠️ Likely to break your code |
| 2nd | Minor | New features that are backwards compatible | ✅ Usually safe |
| 3rd | Patch | Small bug fixes that don't break anything | ✅ Safe |

      

### A real-world breaking change

      

When chalk moved from version 2 to version 3, it removed a property called
         `enabled` and replaced it with a new property
         `level`. Any code using chalk version 2 would have to migrate to the
         new syntax in order to be compatible with version 3. That's why a major bump deserves caution.

      

### The reset rule

      

When a new version is released, the digits to the *right* reset back to zero.

      
```bash
# Current version: 1.9.15
# A MAJOR update  →  2.0.0   (minor + patch reset)
# A MINOR update  →  1.10.0  (patch resets, minor goes up)
# A PATCH update  →  1.9.16
```

      

<Callout type="warn">
**Not decimal numbers!**
        Unlike regular decimals which only range from 0 to 9, there is no limit to how high each digit
        can go. A version number of `3.28.45` is perfectly valid.
</Callout>

    

    
    
      

## Updating packages safely

      

When you first install an npm package locally, npm installs the newest public release. Over
         time you may want to update those packages to get the newest bug fixes and features — but you
         need to be careful not to accidentally update to a new **major** version that
         could break your code.

      

Fortunately npm has safeguards that give you more control over which versions you update to.

      

### The caret symbol `^`

      

By default, when you install a package, npm saves the version number in
         `package.json` prefixed with a caret:

      
```json
"dependencies": {
  "chalk": "^2.4.2"
}
```

      

The caret allows npm to update to the latest **minor** and
         **patch** version *within the currently installed major version*.

      
```bash
# With "^2.4.2" installed, this grabs the newest 2.x.x release
npm update

# But if chalk 5.0.0 is released, npm update will NOT install it
```

      

### Installing a specific major version

      

Let's say version 5 does come out and you want it. You can manually update to the newest
         version on the command line:

      
```bash
npm install chalk@latest
```

      

You can also specify a version number directly. This works for older versions too, which is
         sometimes necessary when the latest version of a dependent package isn't compatible with your
         other dependencies:

      
```bash
# Install major version 5
npm install chalk@5

# Install the latest major version of 2 (e.g. 2.4.2)
npm install chalk@2
```

      

### The tilde symbol `~`

      

Aside from the caret, you can use the tilde to limit updates to
         **patches within the current minor version**.

      
```bash
# With chalk 2.2.0 installed, get the latest patch within 2.2.x
npm install chalk@~2.2
```

      

### Version range symbols at a glance

      

| Symbol | Example | Allows | Blocks |
| --- | --- | --- | --- |
| `^` caret | `^2.4.2` | 2.4.3, 2.9.0, 2.99.1 | 3.0.0 |
| `~` tilde | `~2.2.0` | 2.2.1, 2.2.7 | 2.3.0 |
| exact | `2.4.2` | nothing — pinned | everything else |
| `@latest` | `chalk@latest` | newest published version | — |

    

    
    
      

## package-lock.json

      

When you're installing packages you may have noticed that npm creates a
         `package-lock.json` file.

      

This file records the **actual, specific versions** of each package and dependency
         that you have installed on your local computer. It exists because of compatibility issues that
         can arise when using a `package.json` file from a different
         environment.

      

### The problem it solves

      

Let's say you've cloned a GitHub repo that has a `package.json` file,
         and you run `npm install` to install all the packages on your own
         computer.

      

But remember the caret symbol npm prefixes each version with. If a dependent package has been
         updated between the time the original author created their
         `package.json` and when you run it on your computer, you could
         actually be installing a **different minor and patch version** than what was used
         in the original repository.

      

And if that newer version has compatibility issues with the other dependent packages you're
         using, it could potentially break your project.

      

### The solution

      

If you run `npm install` and there is a
         `package-lock.json` file in addition to the
         `package.json` file, npm will install the **exact** major,
         minor and patch versions recorded in the lock file.

      
```bash
# Installs the exact versions from package-lock.json
npm install
```

      

This ensures that the packages in your local environment will exactly match the original
         author's.

      
```json
{
  "name": "responsive-design-course",
  "lockfileVersion": 3,
  "packages": {
    "node_modules/chalk": {
      "version": "2.4.2",
      "resolved": "https://registry.npmjs.org/chalk/-/chalk-2.4.2.tgz"
    }
  }
}
```

      

| - | package.json | package-lock.json |
| --- | --- | --- |
| **Written by** | You (`npm init`) | npm, automatically |
| **Stores** | Version *ranges* (`^2.4.2`) | Exact versions (`2.4.2`) |
| **Commit to git?** | Yes | Yes |

      

<Callout type="tip">
**Rule of thumb**
        Commit *both* files. `package.json` describes what you want;
        `package-lock.json` guarantees everyone gets exactly the same thing.
</Callout>

    

    
    
      

## Cheat sheet

      

Everything from this course in one place.

      
```bash
node -v                  # check Node version
npm -v                   # check npm version
npm init                  # create package.json (interactive)
npm init -y               # create package.json with defaults
```

      
```bash
npm install chalk                # local install
npm install -g gulp-cli          # global install
npm install --save-dev gulp      # dev dependency
npm install                      # install everything from package.json
```

      
```bash
npm list                         # list installed packages
npm view chalk versions         # all versions of a package
npm outdated                     # see which packages have updates
```

      
```bash
npm update                       # safe update within ranges
npm install chalk@latest        # newest published version
npm install chalk@5             # major version 5
npm install chalk@2             # latest major version 2
npm install chalk@~2.2          # patches within 2.2.x
```

      

### Key takeaways

      

- npm lets you assemble projects from pre-built code instead of writing everything yourself.
- Install packages **locally** by default; use `-g` only for command-line tools.
- `package.json` tracks version *ranges*; `package-lock.json` pins exact versions.
- Semantic versioning is **major.minor.patch** — major bumps can break your code.
- The caret `^` allows minor + patch updates; the tilde `~` allows patch updates only.
- Never commit `node_modules` — always commit both JSON files.
