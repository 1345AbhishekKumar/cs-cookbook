## Why GitHub? The share-code problem

Imagine you just finished a side project on your laptop. It works. Now you want three things:

1. A **backup** that survives a dead hard drive.
2. A **link** you can send to a friend or employer.
3. A way for two people to **edit the same code** without emailing `project-final-v3-ZIP.zip` back and forth.

You *could* keep copying folders, diffing by hand, and pasting fixes over chat. That works once, then breaks the moment two edits touch the same file.

Most developers don't do that. They push **git commits** to **GitHub**:

1. You commit locally with git.
2. You **push** those commits to a repository on `github.com`.
3. Others **clone**, **pull**, branch, and propose changes via **pull requests**.

```bash
git init -b main
git add .
git commit -m "First commit"
git remote add origin https://github.com/YOU/demo.git
git push -u origin main
```

<Callout type="info">
**The chain of collaboration**
Local git → tracks snapshots offline → GitHub hosts the remote → your team clones, pushes, pulls, and reviews.
</Callout>

If you already know `add / commit / log / branch` from [Learning Git](/docs/developer-tools/git), this lesson is the missing second half: how that local history becomes teamwork.

## What is GitHub?

**GitHub** is a *host for git repositories* plus collaboration tools. It is:

- A cloud home for your `.git` history at `github.com/OWNER/REPO`.
- A web UI + permissions layer: who can read, push, review, merge.
- Pull requests, Issues, Actions, Pages, and Codespaces built on top of git.

### Git vs. GitHub

| Concept | What it is | Example |
| --- | --- | --- |
| **Git** | Distributed version control you run locally | `git commit`, `git log`, `git branch` in `.git/` |
| **GitHub** | Company / platform that hosts git repos | `https://github.com/octocat/hello-world` |
| **Remote** | GitHub-side copy your local repo pushes to / pulls from | `origin → https://github.com/YOU/demo.git` |
| **Pull request** | Proposed merge + review thread (GitHub-only, not a git command) | `fix-login → main`, 2 approvals, squash-merge |

<Callout type="warn">
**Git is not GitHub**
Git works fully offline. GitHub without git is just file storage. If someone says "push it to git", they mean "push it to GitHub".
</Callout>

Mental model: **local repo ↔ remote repo**. Git tracks snapshots. GitHub publishes them so others can `fetch` and `pull`.

## Repositories: create, clone, link

A **repository** ("repo") on GitHub is a hosted project folder: code + full git history + Issues + PRs + settings.

### Create from the web

`+ (top right) > New repository` asks for:

- **Name:** `hello-world` — short, lowercase, hyphens.
- **Description:** one line, optional but searchable.
- **Visibility:** public vs private (below).
- **Add a README file:** front-page docs.
- **Add .gitignore:** ignore template (Python, Node, Windows).
- **Choose a license:** MIT / Apache-2.0 / GPL-3.0.

Best practice for learning: tick **Add README** for a brand-new empty idea. **Do NOT tick anything** when you already have local code to push — an initialized remote and your local history diverge and your first push is rejected.

### Create from the CLI

```bash
gh repo create demo --public --clone
gh repo create demo --private --clone
gh repo create ORG/demo --public --clone
gh repo create demo --public --source=. --push  # push existing folder, skip web
```

### Public vs. private

| Visibility | Who can see | Fork behavior |
| --- | --- | --- |
| **Public** | Anyone can view and fork | Public forks stay linked to the network |
| **Private** | Only you + collaborators | Forks stay private; deleting upstream can delete private forks |
| **Internal** | Enterprise members only | Enterprise-only option |

No license still means default copyright — visible does not mean reusable. Pick a license early (more in Guardrails).

### Clone: download + link in one step

```bash
git clone https://github.com/OWNER/REPO.git
# does: mkdir REPO + git init + add remote origin + download all commits + checkout main

gh repo clone OWNER/REPO
```

Verify any repo you work in:

```bash
git status
git remote -v
```

## The one rule: push to a remote, never email ZIPs

A bare `git commit` only saves locally. Until you `push`, nobody — not even GitHub — has your work.

```bash
git remote add origin https://github.com/YOU/demo.git
git remote -v
# origin  https://github.com/YOU/demo.git (fetch)
# origin  https://github.com/YOU/demo.git (push)

git push -u origin main  # first time: -u sets upstream, then bare `git push` works
```

| Do this | Not this | Why |
| --- | --- | --- |
| `git push -u origin main` first time | `git push` with no upstream | Tells local `main` which remote branch to track |
| Create **empty** remote for existing code | Init remote with README, then push old history | Avoids divergent histories and `non-fast-forward` rejection |
| `git pull` before `push` on shared branches | Force-push to "fix" rejection | Remote is ahead — merge it first, don't overwrite teammates |

<Callout type="tip">
**`origin already exists?`**
You ran `git remote add` twice. Don't re-add — repoint: `git remote set-url origin https://github.com/YOU/demo.git`.
</Callout>

## Authentication: HTTPS vs SSH

GitHub removed password auth. Every `clone / push / pull` to a private repo must authenticate as *you*.

```text
HTTPS: https://github.com/OWNER/REPO.git
SSH:   git@github.com:OWNER/REPO.git
```

### Option A: GitHub CLI + credential helper (recommended for beginners)

```bash
gh auth login
# → GitHub.com → HTTPS → Yes to "authenticate to Git with GitHub credentials"
```

This stores an HTTPS credential via **Git Credential Manager** (bundled with Git for Windows, `brew install --cask git-credential-manager` on macOS). It uses browser OAuth + 2FA, saves in the OS keychain, and you never paste tokens by hand.

Cached wrong password? On Windows delete the `git:https://github.com` entry in Credential Manager and login again.

### Option B: Personal Access Token (PAT)

When Git prompts for a password over HTTPS, paste a **token**, not your login password:

```bash
git clone https://github.com/USERNAME/PRIVATE-REPO.git
# Username: YOUR-USERNAME
# Password: YOUR-PERSONAL-ACCESS-TOKEN
```

Create at `Profile > Settings > Developer settings > Personal access tokens`:

- **Fine-grained PAT (prefer):** scoped to specific repos + granular permissions (`Contents: read/write`, `Pull requests: read/write`). Expires in 1–366 days, may need org approval.
- **Classic PAT:** broad `repo` scope = all repos you can access. Needed for some legacy APIs. Always set an expiration.

### Option C: SSH keys

```bash
ssh-keygen -t ed25519 -C "you@example.com"
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
# Windows (admin PowerShell):
# Get-Service -Name ssh-agent | Set-Service -StartupType Manual
# Start-Service ssh-agent
# ssh-add c:/Users/YOU/.ssh/id_ed25519
ssh -T git@github.com  # expect: Hi YOU! You've successfully authenticated
```

Then `GitHub > Settings > SSH and GPG keys > New SSH key`, paste the `.pub` file.

Switch a repo between URL types anytime:

```bash
git remote set-url origin https://github.com/OWNER/REPO.git
git remote set-url origin git@github.com:OWNER/REPO.git
```

<Callout type="warn">
**Two auth errors you will see**
`Authentication failed` over HTTPS = you typed your password, not a PAT — use `gh auth login` or a token. `Permission denied (publickey)` over SSH = no key on GitHub — generate one or switch that remote to HTTPS.
</Callout>

## Remotes: origin and upstream

A **remote** is just a named URL in `.git/config`. `fetch` downloads from it, `push` uploads to it.

```bash
git remote -v                                    # list
git remote add origin https://github.com/YOU/REPO.git
git remote set-url origin git@github.com:YOU/REPO.git
git remote rename origin destination
git remote rm destination  # only unlinks locally, does not delete the server repo

# fork collaboration:
git remote add upstream https://github.com/ORIGINAL-OWNER/REPO.git
git fetch upstream  # creates upstream/main remote-tracking branch
```

Convention: `origin` = your copy (read + write), `upstream` = the original you forked from (fetch to stay fresh).

## Daily workflow: fetch, pull, push

```bash
git fetch origin          # download origin/* without merging — safe to run anytime
git pull origin main      # = fetch + merge into current branch; commit first
git push origin main      # upload your commits
git merge --abort         # bail out of a conflicted pull/merge
```

`ERROR: non-fast-forward updates were rejected` means the remote moved ahead while you worked. Fix: `git pull` (or `fetch + merge`), resolve, then `push` again.

Never commit secrets. Check `git status` before every commit, and never `add` `.env`, `node_modules/`, `__pycache__/`, or credentials.

## Branches + pull requests: the team loop

Never commit directly to `main` in a team repo. One fix = one short-lived branch = one pull request.

```bash
git checkout -b fix-login-bug
# ... edit ...
git add -A
git commit -m "Fix login redirect loop"
git push -u origin fix-login-bug
# → GitHub shows: Compare & pull request
```

Keep it fresh while review drags on:

```bash
git fetch origin
git merge origin/main
```

### Open a PR

Web: `Pull requests > New > base: main ← compare: fix-login-bug > Title + Description > Create Pull Request` (or `Create Draft` for work-in-progress).

```bash
gh pr create
gh pr create --base main --head fix-login-bug --title "Fix login redirect" --body "Fixes #12"
gh pr create --draft
gh pr create --web  # open the web form from CLI
```

Good PR habits: small diff, clear title (`Add login validation`, not `fixed stuff`), screenshots/tests, link the issue with `Fixes #123` — GitHub auto-closes it on merge.

### Review and merge

`Files changed > Review changes > Comment / Approve / Request changes`, inline threads, `Resolve conversation`, request reviewers in the sidebar.

```bash
gh pr list --author "@me"
gh pr list --label bug
gh pr merge 123 --squash --delete-branch
```

| Merge method | What happens | Use when |
| --- | --- | --- |
| **Merge commit** | Preserves every commit + a merge commit | Full history matters |
| **Squash and merge** | Compresses PR to one clean commit | Feature branch was messy |
| **Rebase and merge** | Replays commits linearly, rewrites SHAs | You want linear history |

You can't merge a draft until `Ready for review`. Don't merge with `Changes requested` outstanding. Delete the head branch after merge to stay tidy.

## Forks: contribute without write access

| Path | Where it lives | Use when |
| --- | --- | --- |
| **Branch** | Inside the same repo | You have write access |
| **Fork** | Separate repo copy under your account, linked to upstream | Open-source / no write access |

Fork PR flow:

```bash
# 1. Click Fork on GitHub, then:
gh repo fork ORIGINAL-OWNER/REPO --clone
cd REPO
git remote -v  # origin = your fork, upstream = original (added by gh)

git checkout -b fix-typo
git commit -am "Fix typo in README"
git push -u origin fix-typo
gh pr create --base ORIGINAL-OWNER:main --head YOU:fix-typo
```

Tick **Allow edits from maintainers** so upstream can push fixes to your branch.

### Sync your fork

Web: `Your fork > Sync fork > Update branch`. CLI + git (syncs all branches, not just one):

```bash
gh repo sync YOU/REPO -b main
# or manually:
git fetch upstream
git checkout main
git merge upstream/main
git push origin main
```

<Callout type="warn">
**Stale-fork trap**
Opening a PR from a month-old `main` shows a giant diff. `Sync fork` + `git pull` first, then branch.
</Callout>

## Issues, Projects, Discussions: where work lives

| Tool | Use for | Example |
| --- | --- | --- |
| **Issues** | Actionable task: bug, feature, chore | `Login loops on Safari #12`, assignee + label + milestone |
| **Pull request** | Proposed code that fixes an issue | `Fix login redirect #13 — Fixes #12` |
| **Discussion** | Open question, idea, announcement | `Should we support passkeys?` |
| **Project** | Kanban / table / roadmap over Issues + PRs | `Sprint 4 board` |

```bash
gh issue create
gh issue list --repo OWNER/REPO
gh issue list --assignee "@me"
```

Rule of thumb: **Discussion = question, Issue = task, PR = code**.

## Guardrails: .gitignore, LICENSE, README, protected branches

### `.gitignore` — never commit build output

```bash
touch .gitignore
# commit it so the whole team shares the rules
git rm --cached .env  # untrack a file you already committed, then ignore it
```

- Per-repo (shared): `/.gitignore` — commit it.
- Global (yours only): `~/.config/git/ignore`.
- Local-only: `.git/info/exclude`.
- Templates: `github/gitignore` repo or `gitignore.io`. Pick at repo creation.

<Callout type="warn">
**Adding a rule doesn't delete history**
`.gitignore` only ignores *untracked* files. Already committed? `git rm --cached FILE` + recommit, then push.
</Callout>

### `LICENSE` — visible is not reusable

No license = default copyright. People can view and fork per ToS, but not legally reuse. Beginner picks:

- **MIT:** permissive, one page — default for most tutorials.
- **Apache-2.0:** permissive + patent grant.
- **GPL-3.0:** copyleft — derivatives must stay open.

Helper: `choosealicense.com`. File at `/LICENSE` + one line in README. The picker only shows at creation — later, add the file by hand.

### `README.md` — the front page

Shown on the repo home (truncated past ~500 KiB). Minimum viable:

```bash
echo "# demo" >> README.md
git add README.md && git commit -m "Add README"
git push --set-upstream origin HEAD
```

Include: what + why, quickstart install/use, help link, maintainers. Add `CONTRIBUTING.md` and `CODE_OF_CONDUCT.md` when outsiders join.

### Protected branches + CODEOWNERS

`Settings > Branches > Add rule`: block force-push/delete on `main`, require PR reviews (N approvals, dismiss stale on new push), require status checks, require conversation resolution, require linear history.

`/.github/CODEOWNERS` auto-requests reviewers:

```text
*.js @js-owner
/docs/ @doctocat
/.github/CODEOWNERS @owner
```

Last match wins. Combine with "Require review from Code Owners" to block merges until owners approve.

## GitHub CLI essentials

```bash
gh auth login
gh repo view OWNER/REPO --web
gh repo clone OWNER/REPO
gh repo create --source=. --public --push
gh issue list --repo OWNER/REPO
gh pr create
gh pr list
gh pr merge 123 --squash --delete-branch
gh status
```

Mention-only: **Codespaces** (cloud Ubuntu container from browser / `gh codespace create`, free quota for personal accounts) and **GitHub Desktop** (GUI clone/commit/push + `Preview Pull Request`, best if CLI feels scary).

## Core commands & what they mean

| Task | Command | What it actually does |
| --- | --- | --- |
| Set identity | `git config --global user.name "YOU"` | Labels your commits with your name on every repo |
| Set email | `git config --global user.email "you@example.com"` | Links commits to your GitHub account |
| Start repo | `git init -b main` | Creates local `.git/` history with `main` as default branch |
| Login | `gh auth login` | Authenticates CLI + Git via browser OAuth, stores HTTPS credential |
| Make SSH key | `ssh-keygen -t ed25519 -C "you@example.com"` | Generates public/private key pair for SSH auth |
| Test SSH | `ssh -T git@github.com` | Verifies GitHub recognizes your SSH key |
| New repo + push | `gh repo create demo --public --source=. --push` | Creates GitHub repo from local folder and pushes in one step |
| List remotes | `git remote -v` | Shows `origin/upstream` URLs for fetch vs push |
| Link remote | `git remote add origin URL` | Names a GitHub URL `origin` for push/pull |
| Track fork source | `git remote add upstream URL` | Names original repo `upstream` to fetch updates from a fork |
| Copy repo | `git clone URL` / `gh repo clone OWNER/REPO` | Downloads all commits + auto-adds `origin` + checks out `main` |
| Safe download | `git fetch origin` | Downloads `origin/*` branches without merging — always safe |
| Download + merge | `git pull origin main` | `fetch` + `merge` remote `main` into current branch |
| Upload | `git push -u origin main` | Uploads commits; `-u` sets tracking so next time bare `push` works |
| New branch | `git checkout -b fix-login-bug` | Creates + switches to feature branch for one fix |
| Open PR | `gh pr create --base main --head fix-login-bug` | Proposes merging your branch into `main` with review thread |
| List PRs | `gh pr list` | Lists open PRs in current repo |
| Merge PR | `gh pr merge 123 --squash --delete-branch` | Merges PR #123 as one commit and deletes the head branch |
| Fork + clone | `gh repo fork ORIGINAL/REPO --clone` | Copies repo to your account, clones it, adds `upstream` automatically |
| Sync fork | `gh repo sync YOU/REPO -b main` | Updates your fork's `main` from upstream without manual merge |
| Manual sync | `git fetch upstream; git merge upstream/main; git push origin main` | Same as above in raw git: fetch original → merge locally → push to your fork |
| New issue | `gh issue create` | Opens a tracked task/bug with title, body, labels |
| List my issues | `gh issue list --assignee "@me"` | Filters Issues assigned to you |
| Untrack without delete | `git rm --cached FILE` | Stops tracking a committed file (e.g. `.env`) but keeps it on disk |

## Cheat sheet

```bash
git config --global user.name "YOU"       # identity once
git config --global user.email "you@example.com"
git init -b main                          # start local repo
```

```bash
gh auth login                             # authenticate (preferred)
ssh-keygen -t ed25519 -C "you@example.com" # SSH alternative
ssh -T git@github.com                     # test SSH
```

```bash
gh repo create demo --public --source=. --push  # new remote from local folder
git remote -v                           # verify origin/upstream
git remote add origin https://github.com/YOU/demo.git
git remote add upstream https://github.com/ORIGINAL/REPO.git
git clone https://github.com/OWNER/REPO.git
```

```bash
git push -u origin main                   # first push + track
git fetch origin                          # safe download
git pull origin main                      # fetch + merge
git checkout -b fix-login-bug             # feature branch
git push -u origin fix-login-bug
gh pr create --base main --head fix-login-bug --title "Fix login" --body "Fixes #12"
gh pr merge 123 --squash --delete-branch
```

```bash
gh repo fork ORIGINAL/REPO --clone        # outsider contribution
git fetch upstream; git checkout main; git merge upstream/main; git push origin main
gh repo sync YOU/REPO -b main             # sync fork shortcut
gh issue create; gh issue list --assignee "@me"
```

### Key takeaways

- Git tracks snapshots locally; GitHub publishes them so a team can fetch, pull, and review.
- Authenticate with `gh auth login` (or GCM) — passwords are dead, PATs expire, SSH needs a key on GitHub.
- `origin` is your copy, `upstream` is the original you forked — `fetch` often, `pull` before `push`.
- One branch per fix, one PR per branch — link with `Fixes #123`, squash when messy, delete after merge.
- `.gitignore` + `LICENSE` + `README` on day one — `git rm --cached` if you ignored too late.
- Never commit secrets or push directly to protected `main` — fork or branch, request review, then merge.

<Callout type="info">
**The bigger picture**
Git remembers *what changed*. GitHub remembers *why and who agreed*: Issues frame the problem, PRs propose the fix, reviews record the decision. Learn `clone → branch → push → PR → merge → pull` once, and every team workflow — forks, Codespaces, Actions — becomes a variation on the same loop.
</Callout>
