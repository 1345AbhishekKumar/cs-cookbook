## Why Deno? The story behind the runtime

To understand **Deno**, you have to know a little bit about the history of **Node.js**.

In 2009, software engineer **Ryan Dahl** created Node.js. It took Google's **V8 JavaScript engine** (the same engine that powers Google Chrome) and brought it to servers and command-line scripts. Node.js revolutionized web development: suddenly front-end developers could write server-side code without learning another language like PHP, Java, or Ruby.

However, JavaScript in 2009 was very different from JavaScript today:
- Promises did not exist yet (everything used error-first callbacks).
- ECMAScript Modules (`import` / `export`) did not exist yet (Node had to invent `require()` and CommonJS).
- Web standard APIs like `fetch()`, `crypto`, and `ReadableStream` did not exist on servers.
- The concept of ambient host security was largely overlooked in developer tooling.

In 2018 at JSConf EU, Ryan Dahl took the stage to deliver a famous talk: **"10 Things I Regret About Node.js"**.

<Callout type="info">
**Ryan Dahl's Key Regrets About Node.js:**
1. **No security sandbox:** Any imported npm package has full, unrestricted access to your file system, network, and environment secrets.
2. **The build system & TypeScript friction:** Running modern TypeScript requires complex pipelines—`tsconfig.json`, Babel, Webpack, Vite, or `ts-node`.
3. **`node_modules` and package resolution:** Fragile nested directory algorithms, massive disk usage, and non-standard module loading.
4. **Deviation from browser web standards:** Node invented proprietary APIs (`Buffer`, `http.createServer`, `EventEmitter`) before browser standards existed.
5. **Tooling fragmentation:** Every project requires configuring separate dependencies for formatting (Prettier), linting (ESLint), testing (Jest/Vitest), and tasks.
</Callout>

Instead of trying to bend Node.js backward and break millions of existing projects, Ryan Dahl and the Deno team started from scratch. The result is **Deno** (an anagram of *Node*).

## What is Deno?

**Deno is a modern, secure JavaScript and TypeScript runtime built on the V8 engine and Rust.**

Just like Node.js and Bun, Deno executes JavaScript code on your machine, server, or cloud edge. But Deno is engineered from the ground up as a **complete, batteries-included developer platform**.

| Component | In the Node.js World | In Deno |
| :--- | :--- | :--- |
| **Runtime** | Node.js (V8 + C++ / libuv) | **Deno (V8 + Rust / Tokio)** |
| **TypeScript Execution** | `tsc`, `ts-node`, `tsx`, `esbuild` | **Built-in zero-config execution** |
| **Security Sandbox** | None (full machine access) | **Secure by default (`--allow-*` flags)** |
| **Standard APIs** | Node-specific (`fs`, `path`, `http`) | **W3C/WHATWG Web Standards (`fetch`, `Request`, `Response`)** |
| **Code Formatter** | Prettier | **`deno fmt` (built-in)** |
| **Code Linter** | ESLint | **`deno lint` (built-in)** |
| **Test Runner** | Jest, Vitest, Mocha | **`deno test` (built-in)** |
| **Benchmark Suite** | Benchmark.js, tinybench | **`deno bench` (built-in)** |
| **Binary Compiler** | pkg, nexe | **`deno compile` (single standalone binary)** |
| **Task Runner** | npm scripts | **`deno task` (built-in cross-platform runner)** |
| **Doc Generator** | TypeDoc, JSDoc | **`deno doc` (built-in)** |
| **Registry & Packages** | npm registry | **JSR (JavaScript Registry) + npm support** |

```bash
deno --version
# deno 2.x.x (v8, x86_64-pc-windows-msvc)
```

## Under the Hood: V8, Rust & Tokio

Three fundamental technologies give Deno its speed, safety, and reliability:

```bash
┌────────────────────────────────────────────────────────┐
│                   JavaScript / TypeScript              │
│                (Your Application & Scripts)            │
├────────────────────────────────────────────────────────┤
│           V8 JavaScript Engine (Google / C++)          │
├────────────────────────────────────────────────────────┤
│              Rust Core & Tokio Event Loop              │
├────────────────────────────────────────────────────────┤
│           Operating System (Windows, macOS, Linux)     │
└────────────────────────────────────────────────────────┘
```

### 1. Google V8 JavaScript Engine
Deno uses the exact same production-proven engine that powers Chrome and Node.js. It features just-in-time (JIT) compilation, high-performance garbage collection, and immediate support for the latest ECMAScript language specifications.

### 2. Rust
While Node's core bindings were written in C++, Deno is written in **Rust**. Rust provides:
- **Memory safety without garbage collection** for the runtime core.
- Protection against data races and null pointer exceptions.
- Extreme runtime efficiency and tight operating system abstractions.

### 3. Tokio
For asynchronous I/O (handling network sockets, file descriptors, and timers), Deno relies on **Tokio**, the de facto asynchronous runtime for Rust. Tokio delivers predictable concurrency and scalable event handling.

## The Security-First Architecture: Sandboxed by Default

In Node.js or Python, whenever you install and execute a package from the internet, that package can quietly read your `~/.ssh/id_rsa`, inspect your `.env` secrets, or send your system data to a remote server. You have to trust that thousands of transitive dependencies are not compromised.

**Deno changes this completely: by default, Deno scripts run inside a sandbox with zero access to the outside world.**

```bash
# Running a script that tries to read a file without permission:
deno run script.ts
```

If `script.ts` attempts to read a file, Deno blocks it and asks for permission in the terminal:
```
┌ ⚠️  Deno requests read access to "./secret.txt".
├ Requested by `Deno.readTextFile()` API.
├ Run again with --allow-read to bypass this prompt.
└ Allow? [y/n/A] (y = yes, n = no, A = allow all)
```

If you pass `--no-prompt` in automated environments (like CI/CD), the operation immediately throws a `Deno.errors.NotCapable` exception.

### Granular Permission Flags

Instead of granting unlimited access, Deno lets you restrict access to specific folders, domains, or environment variables:

| Permission Flag | Purpose | Granular Example |
| :--- | :--- | :--- |
| `--allow-read` | Grant file read access | `deno run --allow-read=/data,/tmp app.ts` |
| `--allow-write` | Grant file write access | `deno run --allow-write=./logs app.ts` |
| `--allow-net` | Grant network access | `deno run --allow-net=api.github.com:443,localhost:8000 app.ts` |
| `--allow-env` | Grant environment variable reads | `deno run --allow-env=PORT,DATABASE_URL app.ts` |
| `--allow-run` | Grant spawning sub-processes | `deno run --allow-run=git,ffmpeg app.ts` |
| `--allow-sys` | Grant OS system metric inspection | `deno run --allow-sys=hostname,osRelease app.ts` |
| `--allow-ffi` | Grant native C/Rust library loading | `deno run --allow-ffi app.ts` |
| `-A` / `--allow-all` | Disable sandbox completely | `deno run -A app.ts` *(Equivalent to Node.js)* |

### Deny Flags Override Allow Flags

Deno allows you to grant broad permissions while carving out explicit restricted areas using `--deny-*`:

```bash
# Allow reading the whole project EXCEPT the secrets folder
deno run --allow-read=. --deny-read=./secrets app.ts
```

<Callout type="tip">
**Rule of Thumb:**
`--deny-*` flags always take strict precedence over `--allow-*` flags.
</Callout>

### Declarative Permission Sets in `deno.json`

Typing long CLI flags every time can be tedious. In modern Deno, you can define named **permission sets** right inside your `deno.json` file:

```json title="deno.json"
{
  "permissions": {
    "server": {
      "net": ["0.0.0.0:8000"],
      "env": ["PORT", "NODE_ENV"],
      "read": ["./static", "./templates"]
    }
  },
  "tasks": {
    "start": "deno run -P=server main.ts"
  }
}
```

Now running `deno task start` runs your server with strictly defined boundaries.

## Native TypeScript and JSX: Zero-Config Execution

One of Deno's biggest productivity superpowers is native TypeScript support.

In traditional Node.js:
1. You install `typescript`, `@types/node`, `tsx` or `ts-node`.
2. You configure a `tsconfig.json`.
3. You set up a build step (`tsc` or `esbuild` or `vite`).
4. You wrestle with `moduleResolution`, `.js` vs `.ts` import extensions, and CommonJS/ESM mismatches.

**In Deno, none of this is needed.**

Create a file named `hello.ts`:

```typescript title="hello.ts"
interface User {
  id: number;
  name: string;
  role: "admin" | "member";
}

const user: User = {
  id: 1,
  name: "Sarah Connor",
  role: "admin",
};

console.log(`Hello, ${user.name}! Your role is: ${user.role}`);
```

Run it directly:

```bash
deno run hello.ts
# Hello, Sarah Connor! Your role is: admin
```

### How TypeScript Execution Works in Deno

- **Fast SWC Transpiler:** Under the hood, Deno uses **SWC** (written in Rust) to transpile TypeScript to JavaScript in milliseconds.
- **Fast Startup vs. Strict Checking:** By default, `deno run` strips types for maximum startup speed.
- **Type Checking On Demand:**
  - Run `deno check hello.ts` to perform full type validation using the official TypeScript engine.
  - Or run `deno run --check hello.ts` to type-check before executing.
- **First-Class JSX/TSX:** Deno natively executes `.jsx` and `.tsx` files without bundlers.

## Web Standards as First-Class Citizens

When building web applications, why should server code use completely different APIs than browser code?

In Node.js, for over a decade, you had to use `http.createServer()`, `node-fetch`, `buffer.Buffer`, and custom stream implementations.

**Deno adopted W3C and WHATWG browser standards from day one:**

```typescript title="web-standards.ts"
// 1. Top-Level Await is supported out of the box
// 2. Global fetch() without importing any package
const res = await fetch("https://api.github.com/users/denoland");
const data = await res.json();
console.log(`Deno repos: ${data.public_repos}`);

// 3. Web Crypto API
const uuid = crypto.randomUUID();
console.log(`Generated UUID: ${uuid}`);

// 4. URL and URLPattern
const pattern = new URLPattern({ pathname: "/users/:id" });
const match = pattern.exec("https://example.com/users/42");
console.log(`User ID: ${match?.pathname.groups.id}`);

// 5. Streams and Text Encoders
const encoder = new TextEncoder();
const bytes = encoder.encode("Hello Deno!");
console.log("Encoded byte length:", bytes.length);
```

Run with network access:
```bash
deno run --allow-net=api.github.com web-standards.ts
```

<Callout type="info">
**Standard Web APIs available globally in Deno:**
- `fetch()`, `Headers`, `Request`, `Response`, `FormData`
- `WebSocket`
- `ReadableStream`, `WritableStream`, `TransformStream`
- `crypto.subtle` and `crypto.randomUUID()`
- `URL`, `URLSearchParams`, `URLPattern`
- `AbortController`, `AbortSignal`
- `TextEncoder`, `TextDecoder`
- `Blob`, `File`
- `Worker`, `performance.now()`
</Callout>

Because Deno adheres to web standards, code written for Deno runs effortlessly in modern browsers, Cloudflare Workers, and serverless edge functions.

## Modern Package Management: JSR, npm & Deno 2

One of the biggest historical pain points with Deno 1.x was the transition away from npm. **Deno 2** solved this by unifying three package management approaches:

```bash
┌────────────────────────────────────────────────────────┐
│                   Deno Dependency Model                │
├──────────────────────────┬─────────────────────────────┤
│   JSR (Modern TypeScript)│ jsr:@std/path               │
│   npm Compatibility      │ npm:express, npm:zod        │
│   URL Imports            │ https://esm.sh/...          │
│   package.json / npm CLI │ deno install, deno add      │
└──────────────────────────┴─────────────────────────────┘
```

### 1. JSR (The JavaScript Registry)

**JSR** (`jsr.io`) is an open-source, modern package registry designed specifically for TypeScript and ECMAScript Modules by the Deno team.

- **TypeScript Native:** Authors publish raw TypeScript. JSR automatically creates documentation, type definitions (`.d.ts`), and npm-compatible distributions.
- **Audited Standard Library:** The official Deno Standard Library is published on JSR under `@std/*`.

```bash
# Add standard library modules to your project
deno add jsr:@std/path jsr:@std/assert jsr:@std/fs
```

Using JSR modules in code:

```typescript title="std-example.ts"
import { join } from "jsr:@std/path";
import { ensureDir } from "jsr:@std/fs";
import { assertEquals } from "jsr:@std/assert";

const targetPath = join("dist", "reports", "annual.pdf");
console.log("Constructed path:", targetPath);

assertEquals(1 + 1, 2);
```

### 2. Direct `npm:` Specifiers

Need an npm package? You don't even need to run `npm install` first. Just use the `npm:` specifier:

```typescript title="npm-specifier.ts"
import chalk from "npm:chalk@^5.3.0";
import { z } from "npm:zod@^3.24.0";

const Person = z.object({
  name: z.string(),
  age: z.number().min(0),
});

const result = Person.safeParse({ name: "Alex", age: 28 });

if (result.success) {
  console.log(chalk.green(`✓ Valid person: ${result.data.name}`));
}
```

Run directly:
```bash
deno run npm-specifier.ts
```

Deno automatically downloads, caches, and compiles the npm dependency into a central global cache without cluttering your local directory with gigabytes of duplicate `node_modules` folders.

### 3. Full Node.js & `package.json` Compatibility (Deno 2)

If you have an existing Node.js project with a `package.json` file, Deno 2 works with it out of the box:

```bash
# Installs dependencies listed in package.json
deno install

# Add a package to package.json or deno.json
deno add express

# Run scripts from package.json
deno task dev
```

## Built-In Developer Tooling

With Node.js, setting up a new repository usually involves installing dozens of development dependencies. Deno bakes the entire developer toolchain into the runtime executable:

```bash
# All of these are built into Deno — zero npm dependencies needed:
deno test        # Fast test runner
deno fmt         # Blazing fast code formatter
deno lint        # Built-in TypeScript/JavaScript linter
deno bench       # Micro-benchmarking suite
deno compile     # Compiles to a single standalone .exe / binary
deno doc         # JSDoc documentation viewer & HTML generator
deno task        # Cross-platform task runner
deno check       # Standalone type checker
```

### 1. `deno test` — Built-in Test Runner

Deno has a built-in testing harness supporting test steps, snapshot testing, and code coverage:

```typescript title="math_test.ts"
import { assertEquals, assertThrows } from "jsr:@std/assert";

function divide(a: number, b: number): number {
  if (b === 0) throw new Error("Cannot divide by zero");
  return a / b;
}

Deno.test("Math Operations", async (t) => {
  await t.step("divides positive numbers", () => {
    assertEquals(divide(10, 2), 5);
  });

  await t.step("throws on division by zero", () => {
    assertThrows(() => divide(10, 0), Error, "Cannot divide by zero");
  });
});
```

Run the tests:
```bash
deno test
# Or generate code coverage reports:
deno test --coverage=cov_profile
deno coverage cov_profile
```

### 2. `deno fmt` — Built-in Code Formatter

Formats JavaScript, TypeScript, Markdown, JSON, CSS, and HTML files in seconds:

```bash
# Format all files in the current project
deno fmt

# Check formatting in CI without modifying files
deno fmt --check
```

### 3. `deno lint` — Built-in Linter

Scans your code for bad practices, syntax errors, and TypeScript anti-patterns:

```bash
deno lint
```

### 4. `deno bench` — Native Benchmarking

Measure performance differences right inside your codebase:

```typescript title="string_bench.ts"
const text = "Deno is fast!";

Deno.bench("RegExp.test", () => {
  /fast/.test(text);
});

Deno.bench("String.includes", () => {
  text.includes("fast");
});
```

Run benchmarks:
```bash
deno bench
```

### 5. `deno compile` — Standalone Executables

Want to distribute your command-line tool or web server to someone who doesn't have Deno installed? `deno compile` packages your code, its dependencies, and the Deno engine into a **single standalone executable binary**:

```bash
# Compile server.ts into a standalone executable with network permissions
deno compile --allow-net server.ts -o my-server

# You now have a single file (my-server.exe on Windows or my-server on Linux/Mac)
./my-server
```

You can even cross-compile for other operating systems:
```bash
# Compile for Linux x64 from Windows
deno compile --target x86_64-unknown-linux-gnu --allow-net server.ts -o my-server-linux
```

## High-Performance Web Services with `Deno.serve`

In modern Deno, building an HTTP server is simple, elegant, and blazing fast. The `Deno.serve` API is backed by **Rust's Hyper** engine and handles HTTP/1.1 and HTTP/2 automatically.

### Example: Complete REST API with `URLPattern`

Here is a full REST API with in-memory state, CORS headers, and route matching:

```typescript title="server.ts"
interface Todo {
  id: string;
  title: string;
  completed: boolean;
}

const todos: Map<string, Todo> = new Map([
  ["1", { id: "1", title: "Learn Deno basics", completed: true }],
  ["2", { id: "2", title: "Build an API with Deno.serve", completed: false }],
]);

const TODO_ITEM_ROUTE = new URLPattern({ pathname: "/api/todos/:id" });

const corsHeaders = {
  "Access-Control-Allow-Origin": "*",
  "Access-Control-Allow-Methods": "GET, POST, DELETE, OPTIONS",
  "Access-Control-Allow-Headers": "Content-Type",
};

Deno.serve({ port: 8000 }, async (req: Request): Promise<Response> => {
  const url = new URL(req.url);

  // Handle CORS Preflight
  if (req.method === "OPTIONS") {
    return new Response(null, { headers: corsHeaders, status: 204 });
  }

  // GET /api/todos - List all items
  if (req.method === "GET" && url.pathname === "/api/todos") {
    const list = Array.from(todos.values());
    return Response.json(list, { headers: corsHeaders });
  }

  // GET /api/todos/:id - Get single item
  const match = TODO_ITEM_ROUTE.exec(url);
  if (req.method === "GET" && match) {
    const id = match.pathname.groups.id!;
    const item = todos.get(id);
    if (!item) {
      return Response.json({ error: "Item not found" }, { status: 404, headers: corsHeaders });
    }
    return Response.json(item, { headers: corsHeaders });
  }

  // POST /api/todos - Create new item
  if (req.method === "POST" && url.pathname === "/api/todos") {
    try {
      const body = await req.json();
      if (!body.title) {
        return Response.json({ error: "Title is required" }, { status: 400, headers: corsHeaders });
      }
      const newTodo: Todo = {
        id: crypto.randomUUID(),
        title: body.title,
        completed: false,
      };
      todos.set(newTodo.id, newTodo);
      return Response.json(newTodo, { status: 201, headers: corsHeaders });
    } catch {
      return Response.json({ error: "Invalid JSON payload" }, { status: 400, headers: corsHeaders });
    }
  }

  // 404 Fallback
  return new Response("Not Found", { status: 404, headers: corsHeaders });
});
```

Run with explicit network permission:
```bash
deno run --allow-net=0.0.0.0:8000 server.ts
# Server listening on http://localhost:8000/
```

### Real-Time WebSockets with `Deno.upgradeWebSocket`

Deno also makes WebSockets trivial by upgrading standard HTTP requests:

```typescript title="ws_server.ts"
Deno.serve({ port: 8080 }, (req) => {
  if (req.headers.get("upgrade") === "websocket") {
    const { socket, response } = Deno.upgradeWebSocket(req);

    socket.onopen = () => console.log("WebSocket client connected!");
    socket.onmessage = (event) => {
      console.log(`Received: ${event.data}`);
      socket.send(`Echo from Deno: ${event.data}`);
    };
    socket.onclose = () => console.log("Client disconnected");

    return response;
  }

  return new Response("Please connect using the WebSocket protocol", { status: 426 });
});
```

## Configuring Deno: `deno.json`

The `deno.json` (or `deno.jsonc` with comments) file is the central configuration file for a Deno project. It configures import maps, task scripts, formatting, linting, and compiler rules:

```json title="deno.json"
{
  "$schema": "https://deno.land/x/deno/cli/schemas/config-file.v1.json",
  "name": "@my-project/api-server",
  "version": "1.0.0",
  "tasks": {
    "dev": "deno run --watch --allow-net=0.0.0.0:8000 server.ts",
    "start": "deno run --allow-net=0.0.0.0:8000 server.ts",
    "test": "deno test --allow-read",
    "lint": "deno lint",
    "fmt": "deno fmt --check",
    "compile": "deno compile --allow-net server.ts -o dist/api-server"
  },
  "imports": {
    "@std/assert": "jsr:@std/assert@^1.0.8",
    "@std/path": "jsr:@std/path@^1.0.8",
    "@std/fs": "jsr:@std/fs@^1.0.6",
    "zod": "npm:zod@^3.24.0"
  },
  "compilerOptions": {
    "strict": true,
    "jsx": "react-jsx"
  },
  "lint": {
    "rules": {
      "tags": ["recommended"]
    }
  },
  "fmt": {
    "useTabs": false,
    "lineWidth": 100,
    "indentWidth": 2,
    "singleQuote": false
  }
}
```

Running tasks:
```bash
# Runs the dev script defined in tasks
deno task dev
```

## Node.js vs. Bun vs. Deno: The Definitive Comparison

All three runtimes execute JavaScript, but their design priorities and internal architectures cater to different engineering needs:

| Criterion | Node.js (v22+) | Bun (v1.2+) | Deno (v2.x) |
| :--- | :--- | :--- | :--- |
| **Engine** | Google V8 (C++) | JavaScriptCore (WebKit / Zig) | **Google V8 (Rust)** |
| **I/O Subsystem** | `libuv` (C) | Custom Zig event loop | **Tokio (Rust)** |
| **TypeScript** | Needs transpiler or experimental strip | Native (transpiles on the fly) | **Native + Built-in `deno check`** |
| **Security Sandbox** | ❌ No sandbox (full machine access) | ❌ No sandbox (full machine access) | **✅ Sandboxed by default (`--allow-*`)** |
| **Web Standards** | Partial / Gradual adoption | High + custom APIs (`Bun.serve`) | **Strict 100% Web Standards First** |
| **Package Management** | npm, pnpm, yarn | Built-in `bun install` | **JSR + npm specifiers + `deno install`** |
| **Built-in Tooling** | None (requires npm packages) | Test, Bundler, Package Manager | **Test, Lint, Fmt, Bench, Doc, Compile, Task** |
| **Single Binary Executable** | Requires `pkg` or external tool | `bun build --compile` | **`deno compile` (Cross-compilation ready)** |
| **Cold Starts** | 60–120ms+ | 8–20ms | **40–60ms** |
| **Philosophy** | Backward compatibility & stability | Maximum speed & drop-in replacement | **Security, Web standards & modern DX** |

## When to Choose Deno

<Callout type="tip">
**When Deno is the ideal choice:**
1. **Security-Sensitive Environments:** If your application processes untrusted user code, handles sensitive customer secrets, or operates in compliance-heavy industries (fintech, healthcare), Deno's sandbox is unmatched.
2. **Modern TypeScript Microservices & APIs:** When you want to write clean TypeScript without managing `tsconfig.json`, `node_modules`, or complex Webpack/Vite build configurations.
3. **Edge and Serverless Deployments:** Because Deno strictly adheres to standard Web APIs (`fetch`, `Request`, `Response`, `Streams`), code written for Deno runs seamlessly across Deno Deploy, Cloudflare Workers, and modern edge networks.
4. **Standalone CLI Tool Distribution:** When you want to write a utility in TypeScript and compile it into a single `.exe` or Linux binary with pre-authorized permissions for non-technical users.
5. **Zero-Configuration Teams:** When you want your entire team to have identical formatting (`deno fmt`), linting (`deno lint`), and testing (`deno test`) without maintaining 15 configuration files.
</Callout>
