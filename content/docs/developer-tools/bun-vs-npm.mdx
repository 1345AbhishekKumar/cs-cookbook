## Why are there so many?

      

There's npm. Then there's pnpm. Then there's Yarn. And now there's Bun. It's a fair
         question: *what are all these things? Are they different? Are they the same? Why do
         they all exist when npm already exists?*

      

Nobody really sits down and explains this clearly, so people stay confused. The goal of
         this course is simple: after reading it, you should feel fully confident about all four.
         If you see a YouTuber using npm, or Yarn, or pnpm, or Bun, you should be completely
         comfortable following along.

      

<Callout type="info">
**The short version**
        All four are *package managers*. They do the same fundamental job — install,
        update, and manage your project's dependencies. They differ in **how** they
        do it, **how fast** they do it, and **what else** they bundle
        alongside.
</Callout>

      

One thing that stands out immediately: **Bun is the odd one out** in this
         list. Why is a runtime sitting next to three package managers? Because Bun *also*
         ships a built-in package manager. It's a runtime that happens to include one.

    

    
    
      

## What is a package manager?

      

You don't want to write all your JavaScript yourself. You *could* — nobody's
         stopping you — but it would take forever. Say you need to create JSON Web Tokens. Or do
         cryptography. Or build modules. Or sort data. There are hundreds of things you'll need to
         do that **someone else has already done** and published as a package.

      

So imagine a package sitting out there in the world. It contains all the code you need.
         You can copy it into your project and start using it. Most of these packages are open
         source, so you can read the source code and see what the community is doing.

      

### What a package manager does for you

      

- **Installs** — downloads the package and puts it in your project.
- **Updates** — keeps dependencies current.
- **Configures** — wires everything up so your ecosystem knows the package
            is available and you can use it out of the box.
- **Manages versions** — tracks which version you installed and records it
            safely in a `package.json` file.

      

Yes, you could manually go to GitHub, download the source code, and drop it into your
         project. Nothing wrong with that. But a package manager does all of it for you: *"I'll
         go get that package, store it properly, and tell your whole ecosystem it's available."*

      

That's why they're also called **dependency managers**. And in the JavaScript
         ecosystem, there are four big players right now:

      

| Package Manager | Created by | Known for |
| --- | --- | --- |
| **npm** | npm, Inc. / GitHub | Being the default |
| **Yarn** | Facebook / Meta | Parallel installs, workspaces |
| **pnpm** | Community (Zoltan Kochan) | Disk efficiency, strictness |
| **Bun** | Oven (Jarred Sumner) | Speed and all-in-one toolkit |

    

    
    
      

## npm — the default

      npm · Node Package Manager

      

npm is the one everyone starts with. Its full name is **Node Package Manager**,
         though npm's own website playfully says *"our name isn't actually Node Package
         Manager — call it whatever you want."* Programmers have their own sense of humour.

      

### The key thing: it's pre-installed

      

The most interesting fact about npm is that it's the **default**. The moment
         you install Node.js, npm comes along with it, pre-installed and ready to go. You don't
         have to do anything.

      
        
          

#### ✅ Advantages

          

- Default — ships with Node.js, zero setup
- Huge ecosystem — the entire npm registry
- Highly supported everywhere
- Constantly improved — updates keep coming
- Best stability and official support
- Works out of the box when deploying

        
        
          

#### ❌ Disadvantages

          

- Slower compared to its competitors
- `node_modules` folder gets very large
- Bloat increases as projects grow
- Weaker monorepo support

        
      

      

### Why people still use it

      

If you look at stability, official support, and zero-setup, npm wins — and it's not close.
         It has the widest range of support. It just works out of the box. If you're deploying a
         project anywhere in production, chances are npm will be there and it will run.

      

That's why companies stick with it. Companies care less about fancy features and more
         about stability, support, and the confidence that it will run. That's why npm is used
         most.

      

<Callout type="tip">
**Why tutorials use npm**
        Most tutorials (including the ones in this series) default to npm — not because it's the
        best, but because it's the least confusing. If you switch to Yarn or pnpm or Bun, beginners
        get worried that something advanced is happening. npm keeps the fear away.
</Callout>

      

### The node_modules problem

      

You've created a `node_modules` folder. We all have, many times.
         With npm, its size gets **very large**. As you build bigger and bigger
         projects, the bloat starts growing rapidly. That's a well-known fact about npm.

      
```bash
npm init                    # create package.json
npm install express         # install a dependency
npm install mongoose        # install another
npm run dev                 # run a script
```

    

    
    
      

## Yarn — Facebook's answer

      Yarn · Created by Facebook / Meta

      

Surprisingly, a lot of people don't know that Facebook — now Meta — works heavily in the
         open-source ecosystem. Yarn is one of their creations. Facebook looked at npm and said:
         *"This is a bit bloated. Let's actually make it faster."*

      

### How Yarn makes it faster: parallelism

      

Facebook's trick is **parallel execution**. Yarn runs many tasks at the same
         time, so it feels noticeably faster than npm.

      

### Support and drop-in replacement

      

Yarn's support has grown widely — it works on Vercel, Netlify, and many other platforms.
         It's essentially a **drop-in replacement** for npm.

      
```bash
# npm
package.json
package-lock.json

# Yarn
package.json
yarn.lock          # Yarn's own lock file
```

      

<Callout type="warn">
**Don't mix them**
        It's not as simple as "sometimes I use npm, sometimes Yarn." Pick one and stick with it.
        Use Yarn's lock file *or* npm's lock file — not both. Mixing them causes deployment
        problems later.
</Callout>

      

### Workspaces — the standout feature

      

Yarn gives you something big: **workspaces**. A workspace is what gives you
         **out-of-the-box monorepo support**.

      

If workspaces didn't exist, monorepos would be a nightmare — bad enough that it wouldn't
         even make sense to build one. Yarn solves that.

      

### Yarn versions matter

      

Yarn has significant version differences. There was **Yarn v1** (Classic),
         and then a major update called **Yarn Berry** (v2+). The two are quite
         different. If you're using Yarn, at least read up on which version you're on.

      

If you install Yarn today by default, you get the latest version and it works out of the
         box. Both versions support monorepos and large-scale applications.

      

### Dependency linking

      

Yarn also handles dependencies well. Instead of installing the same package in ten places,
         it uses a concept called **dependency linking**. Because of this, your
         `node_modules` folder stays somewhat under control and feels less
         bloated when you're building many applications.

      
        
          

#### ✅ Advantages

          

- Faster than npm via parallel execution
- Drop-in replacement — easy migration
- Workspaces → excellent monorepo support
- Dependency linking keeps things tidy
- Wide platform support (Vercel, Netlify…)

        
        
          

#### ❌ Disadvantages

          

- Two very different major versions (v1 vs Berry)
- Internally complex — "its own circus"
- Lock file confusion if mixed with npm

        
      

      

So if you want a monorepo, or you just want faster installs, Yarn is a solid drop-in
         replacement for npm — just be careful with that lock file.

    

    
    
      

## pnpm — the performance one

      pnpm · Performant npm

      

pnpm is arguably the most interesting of the group — and for many developers, the
         favourite. There's no officially written-out full form that everyone recognises, but the
         accepted meaning is **Performant npm**. (Naming things well is a skill all
         these projects seem to share.)

      

### Why pnpm exists

      

pnpm was built for two reasons:

      

1. **Save disk space**
2. **Speed up installs**

      

### The content-addressable store

      

pnpm saves a huge amount of disk space because it stores your
         `node_modules` folders differently. The concept is called a
         **content-addressable store**.

      

Here's how it works: your packages are *not* installed into each project folder
         separately. If you're working in multiple places, the same package is not duplicated. You
         know how with npm, if you have ten projects, `node_modules` just
         keeps filling up? pnpm avoids that.

      

Instead of filling ten places, pnpm stores the package **once** in the
         content-addressable store. Whenever a project needs the same package, it's pulled from
         there.

      

### Symlinking

      

If you've studied operating systems at all, you've come across the concept of a
         **symlink**. pnpm installs packages globally and uses symlinks to make them
         appear inside each project.

      
```bash
# Visually, it looks like the package is installed here:
my-project/node_modules/express

# Actually, the real files live in the global store:
~/.local/share/pnpm/store/...

# And a symlink connects the two.
```

      

Updating packages is a little trickier with this model, but it's manageable.

      

### Strict dependency resolution

      

pnpm's dependency resolution is **stricter** than npm's. You get better,
         more correct versions — packages can only access what they actually declared.

      
        
          

#### ✅ Advantages

          

- Noticeably faster
- Huge disk space savings
- Strict, correct dependency resolution
- Best-in-class workspace & monorepo support
- Symlinking means one global copy

        
        
          

#### ❌ Disadvantages

          

- Not universally supported out of the box
- Occasional issues on Netlify, Vercel, etc.
- Deployment needs extra configuration
- Symlink model can surprise the Node structure

        
      

      

### The deployment caveat

      

pnpm can't be described as "works everywhere out of the box." Most of the time it does,
         but on platforms like Netlify and Vercel it sometimes causes issues. If you're planning to
         deploy and you built with pnpm, expect a bit of extra configuration work.

      

<Callout type="warn">
**The symlink problem in deployment**
        When your project deploys, everything expects `node_modules` to
        be *right there*, inside the project. But with symlinking, the actual
        `node_modules` content lives elsewhere on the machine — it only
        *looks* like it's there. This is the "flat structure" that Node expects, and breaking
        it causes deployment issues. If your lock file gets mixed up even slightly, your project
        will blow up during deployment.
</Callout>

      

### Workspaces — where pnpm shines

      

This is pnpm's best feature. It gives you the **best workspace concept** of
         any package manager. And if you have workspaces, you get monorepos.

      

Building a monorepo with pnpm is shockingly easy. It's a 5–10 minute job. You'll be
         surprised: *"Wait, that's it? I thought this was a big deal?"* And you'll
         actually understand how the monorepo works — all thanks to pnpm's workspaces. It's
         genuinely well designed.

      

<Callout type="tip">
**Personal preference**
        For monorepos specifically, pnpm is the preferred choice for many developers. Not because
        Yarn is bad — it isn't — but because pnpm's workspace and monorepo combination is just that
        easy. Everyone has their own reasons; this is a common one.
</Callout>

    

    
    
      

## Bun — the all-in-one

      Bun · Runtime + toolkit

      

Bun is the most interesting — and the most controversial — of the four. You could make an
         entire dedicated video about it.

      

Bun is considered a potential **faster replacement for Node.js**, the same way
         Deno is considered a possible Node replacement. But if you think Bun is *only* a Node
         replacement, you're missing the point. Bun is much more.

      

### It's not just a runtime

      

Obviously Bun runs Node.js code. But it also bundles a lot more:

      

- **A built-in package manager** — you don't need separate npm installs;
            Bun handles it.
- **A built-in bundler** — no Webpack needed.
- **AWS SDK support out of the box**
- **And more** — with things like SQLite integration on the roadmap.

      

Because Bun does a thousand different things, it's not fair to call it "just a Node
         replacement." It's a magical tool in its own right. Its founder, Jarred Sumner, is
         genuinely a state-of-the-art developer — worth following on Twitter.

      

### Speed

      

Bun claims ~99% compatibility with existing packages, and it's *fast*. Saying it's
         just "fast" actually undersells it — it's the fastest of the group. If you've ever
         installed a package with npm and then done the same with Bun, you'll be stunned. It feels
         like nothing happened. That's how magically fast it is.

      

<Callout type="info">
**The one real problem**
        Bun is **new**. And that raises serious questions about its maturity: how many
        places will it work? How is compatibility with older packages? With newer packages? What
        happens if it fails somewhere? Is it battle-tested or not?
</Callout>

      
        
          

#### ✅ Advantages

          

- Fastest installs by a wide margin
- All-in-one: runtime, package manager, bundler
- ~99% package compatibility claimed
- Works great with basic, widely-used packages
- Actively developed by a top-tier team

        
        
          

#### ❌ Disadvantages

          

- Very new — maturity is questioned
- Not battle-tested at scale yet
- Compatibility edge cases unclear
- Risky for production-critical systems

        
      

      

### When Bun is a good fit

      

If speed is your only goal, and you stick to basic packages — Mongoose, Express, no fancy
         dependencies — Bun is extraordinary. Things like JWT, crypto, and bcrypt have been around
         for years and are basic packages. Bun doesn't fail on those, and the speed it delivers
         there is incredible.

      

For everything else, be cautious until it matures further.

      
```bash
bun install express      # instead of npm install
bun run dev              # run a script
bun build ./src/index.ts --outfile ./dist/bundle.js  # bundle
```

    

    
    
      

## Side-by-side comparison

      

| Feature | npm | Yarn | pnpm | Bun |
| --- | --- | --- | --- | --- |
| **Installed by default?** | ✅ Yes (with Node) | ❌ No | ❌ No | ❌ No |
| **Speed** | Slowest | Fast (parallel) | Faster | Fastest |
| **Disk usage** | High (bloat) | Moderate (linking) | Lowest (store) | Low |
| **Lock file** | `package-lock.json` | `yarn.lock` | `pnpm-lock.yaml` | `bun.lockb` |
| **Workspaces / monorepo** | Basic | Good | Best | Emerging |
| **Ecosystem support** | Best | Wide | Mostly good | ~99% claimed |
| **Stability** | Highest | High | High | Unproven |
| **Deployment ease** | Effortless | Easy | Needs config | Varies |
| **Extras** | — | — | — | Runtime + bundler + more |

      

<Callout type="info">
**Notice the pattern**
        Each new tool trades *stability and universal support* for *speed, efficiency, or
        extra capability*. That's the fundamental trade-off across all four.
</Callout>

    

    
    
      

## The lock file warning

      

This is the single most common mistake with package managers, and it's worth its own
         lesson.

      

### Nothing is default except npm

      

Remember: **none of these are installed by default** except npm. You won't
         get pnpm automatically. You won't get Yarn automatically. Both have to be installed
         separately.

      

### Never mix lock files

      

Each package manager generates its own lock file. These lock files are what record the
         exact dependency tree. If you mix them, you're heading for trouble.

      
```bash
# ❌ BAD: different lock files for different packages
my-app/package-lock.json       # npm
my-lib/yarn.lock               # Yarn
my-tools/pnpm-lock.yaml        # pnpm

# ✅ GOOD: one package manager throughout
my-app/package-lock.json
my-lib/package-lock.json
my-tools/package-lock.json
```

      

If you deploy and your system finds npm files in one place and Yarn files in another,
         that's where the issues start. And it's not a small problem:

      

<Callout type="info">
**It will break badly**
        If your lock file or `package.json` files are even slightly mixed
        up between package managers, your project will break during deployment in ways you'll
        remember for a long time. Pick one package manager and commit to it.
</Callout>

      

Whichever tool you pick — npm, Yarn, or pnpm — use it consistently across your entire
         project. Don't switch back and forth.

    

    
    
      

## Which one should you use?

      

There's no single correct answer for everyone. It depends on your goal. Here's a practical
         guide:

      
        
          

#### Just starting out?

          

Use **npm**. It's pre-installed, universally supported, and every
             tutorial assumes it.

        
        
          

#### Want faster installs?

          

Use **Yarn**. Parallel execution makes it feel noticeably quicker, and
             it's a drop-in replacement.

        
        
          

#### Building a monorepo?

          

Use **pnpm**. Its workspace support is the best of any package manager,
             and it saves serious disk space.

        
        
          

#### Chasing maximum speed?

          

Use **Bun** — if you're on basic packages and can accept the maturity
             risk.

        
        
          

#### Deploying to production?

          

Use **npm**. Companies trust its stability, support, and out-of-the-box
             reliability.

        
        
          

#### Stuck on disk space?

          

Use **pnpm**. Its content-addressable store means packages exist once,
             not ten times.

        
      

      

### The summary

      

| Package Manager | Best described as |
| --- | --- |
| **npm** | No headaches, everything out of the box. Slightly larger node_modules. Weak for                 monorepos. |
| **Yarn** | Comparatively better. Facebook made real upgrades. Workspaces and the monorepo                 concept are included. |
| **pnpm** | Everyone's favourite. Saves disk space. Uses symlinking — requires some care. The                 workspace concept is mind-blowingly good. |
| **Bun** | A magical all-in-one tool. Fastest, but new. Great for basic packages when speed                 is the only goal. |

      

<Callout type="tip">
**Practical advice**
        Learn all four conceptually — you now do. Then pick one as your daily driver. Most
        developers start with npm, move to pnpm for monorepos, and experiment with Bun for
        speed-critical projects.
</Callout>

    

    
    
      

## Cheat sheet

      
```bash
npm init                     # create package.json
npm install                  # install all deps
npm install express          # add a dependency
npm install -D nodemon        # add a dev dependency
npm run dev                  # run a script
```

      
```bash
yarn init                    # create package.json
yarn                         # install all deps
yarn add express             # add a dependency
yarn add -D nodemon         # add a dev dependency
yarn dev                      # run a script
```

      
```bash
pnpm init                    # create package.json
pnpm install                 # install all deps
pnpm add express             # add a dependency
pnpm add -D nodemon         # add a dev dependency
pnpm dev                      # run a script
pnpm store path              # find the global store
```

      
```bash
bun init                     # create package.json
bun install                  # install all deps
bun add express              # add a dependency
bun add -D nodemon          # add a dev dependency
bun run dev                  # run a script
```

      

### Key takeaways

      

- A **package manager** installs, updates, and configures your dependencies — also called a dependency manager.
- **npm** is the default: ships with Node, best support, most stable — but slow and bloaty.
- **Yarn** was built by Facebook for parallel, faster installs. Great workspaces and monorepo support.
- **pnpm** uses a content-addressable store and symlinks to save disk space. Best workspaces by far.
- **Bun** is a full toolkit — runtime, package manager, and bundler — and it's the fastest, but it's new.
- **Never mix lock files.** Pick one package manager and use it consistently everywhere.
- For monorepos, pnpm is the common favourite. For production stability, npm. For raw speed, Bun.

**The real goal**
        The point isn't to memorise every command — it's to never be confused again. When you see
        a YouTuber using npm, Yarn, pnpm, or Bun, you'll know exactly what they're doing and why.
        That's the whole story.
</Callout>
