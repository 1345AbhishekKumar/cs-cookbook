## Why pip? The shared-code problem

Imagine you want to build a web scraper. You *could* write your own HTTP client, HTML parser, date handling, and retry logic from scratch. That would take weeks, and your version would have more bugs than the battle-tested libraries thousands of developers already maintain.

Most developers don't do that. They reuse **pre-built packages**:

1. An author writes reusable Python code.
2. They **publish** it to the Python Package Index (PyPI).
3. You **install** it with pip and `import` it.

```bash
python -m pip install requests
```

```python
import requests
res = requests.get("https://api.github.com/users/python")
print(res.json()["public_repos"])
```

<Callout type="info">
**The chain of dependencies**
Python itself → ships pip → pip installs from PyPI → your code imports packages → packages depend on more packages.
</Callout>

pip is a huge part of the Python ecosystem — every tutorial, StackOverflow answer, Docker image, and CI runner assumes it. Even if you later switch to `uv`, you need to understand pip first.

## What is pip?

**pip** is the *package installer for Python*. It is:

- The standard installer that ships with CPython (via `ensurepip`).
- A command-line client for the **Python Package Index (PyPI)** at `pypi.org` (~600k+ projects).
- Free, PyPA-maintained, and pre-installed in every virtual environment.

### pip vs. PyPI

| Concept | What it is | Example |
| --- | --- | --- |
| **PyPI** | Central public repository storing files | `https://pypi.org/project/requests/` |
| **pip** | Client that downloads + installs from PyPI | `python -m pip install requests` |
| **Package** | Versioned bundle (`wheel` or `sdist`) | `requests-2.32.3-py3-none-any.whl` |

<Callout type="warn">
**`pip search` is dead**
PyPI disabled the old XML-RPC search API years ago. Don't try `pip search` — search in your browser at `pypi.org/search`, or check versions with `python -m pip index versions requests`.
</Callout>

## The one rule: always use `python -m pip`

On most machines there are multiple Pythons (system Python, Microsoft Store Python, `pyenv` Python, venv Python). A bare `pip` may point at a different interpreter than `python`.

```bash
python -m pip --version
# pip 25.x from .../site-packages/pip (python 3.12)
```

| Do this | Not this | Why |
| --- | --- | --- |
| `python -m pip install requests` | `pip install requests` | Guarantees install goes to *that* `python` |
| `py -m pip install requests` (Windows launcher) | `pip install requests` | Picks correct Windows Python |
| `.venv/bin/python -m pip install -r requirements.txt` | activating then `pip install` | Works without activation, no PATH mistakes |

### Installing and upgrading pip itself

```bash
python -m pip --version              # check if pip exists
python -m ensurepip --upgrade        # bootstrap from stdlib
python -m pip install --upgrade pip  # upgrade to latest
```

On Debian/Ubuntu you may see a distro package instead:

```bash
sudo apt install python3-pip python3-venv
```

Prefer the distro-independent pip inside a venv for lessons — distro pip is often months old and patched.

## Virtual environments: never install globally

Without isolation, two projects needing different versions of the same library collide, and you risk breaking OS tools that depend on system Python.

A **venv** is a disposable per-project folder with its own interpreter + `site-packages`. Never commit it to git, never move it — recreate it.

```bash
python -m venv .venv
```

```bash
# macOS / Linux
source .venv/bin/activate
# Windows PowerShell
.venv\Scripts\Activate.ps1
```

```bash
deactivate
```

Inside an active venv, `python -m pip install ...` goes to the venv automatically — no `sudo`, no `--user`.

```bash
python -m venv --upgrade-deps .venv  # create with latest pip
python -m venv --clear .venv         # wipe and recreate
python -m venv --system-site-packages .venv  # inherit global (rare)
```

<Callout type="warn">
**PEP 668: Externally Managed Environments**
Modern Debian, Ubuntu, Fedora, and Arch mark system Python as `EXTERNALLY-MANAGED`. Plain `pip install` errors out. That's intentional — create + activate a venv instead. Don't bypass with `--break-system-packages`, and never `sudo pip install`.
</Callout>

## Core CLI commands

| Task | Command |
| --- | --- |
| Install latest | `python -m pip install requests` |
| Install exact | `python -m pip install "requests==2.32.3"` |
| Upgrade | `python -m pip install --upgrade requests` |
| Upgrade aggressively | `python -m pip install --upgrade --upgrade-strategy=eager requests` |
| Install extras | `python -m pip install "requests[security]"` |
| Editable local project | `python -m pip install -e .` |
| From file | `python -m pip install -r requirements.txt` |
| Uninstall | `python -m pip uninstall requests` |
| Snapshot env | `python -m pip freeze > requirements.txt` |
| Human list | `python -m pip list` |
| What can upgrade | `python -m pip list --outdated` |
| Details | `python -m pip show requests` |
| Verify deps | `python -m pip check` |
| Offline fetch | `python -m pip download -d ./wheels -r requirements.txt` |

### `install` modifiers you'll actually use

```bash
python -m pip install --no-deps requests        # skip dependencies
python -m pip install --force-reinstall requests # reinstall even if satisfied
python -m pip install --ignore-installed requests # ignore current env
python -m pip install --dry-run --ignore-installed -r requirements.txt  # resolve only
python -m pip install --only-binary :all: requests  # wheels only, no builds
python -m pip install --no-binary :all: requests    # build from source
python -m pip install --pre requests                 # allow pre-releases
```

<Callout type="tip">
**Quote version specifiers in the shell**
`python -m pip install "requests>=2,<3"` needs quotes — otherwise `>` becomes shell redirection. Inside `requirements.txt` no quotes are needed.
</Callout>

## The `requirements.txt` workflow

`requirements.txt` is a declarative, repeatable environment: a plain list of `pip install` arguments.

```text title="requirements.txt"
requests==2.32.3
"django>=4.2,<5.0"
rich~=13.7.0
-r other.txt
-c constraints.txt
SomePkg @ git+https://github.com/org/repo.git@sometag
pywin32 ; sys_platform == "win32"
```

```bash
python -m pip freeze > requirements.txt   # snapshot current env
python -m pip install -r requirements.txt # recreate env elsewhere
```

| Directive | Meaning |
| --- | --- |
| `-r other.txt` | Include another requirements file |
| `-c constraints.txt` | Version limits *without* forcing install |
| `--index-url / --extra-index-url` | Custom package index |
| `--find-links ./wheels` | Local wheel folder (offline installs) |

<Callout type="info">
**`freeze` pins everything**
`pip freeze` writes `==` pins for *all* transitive dependencies. Great for deploys, noisy for libraries. For libraries, hand-write loose bounds in `pyproject.toml` instead of freezing.
</Callout>

Modern alternatives you should know by name: `pyproject.toml [project.dependencies]` + `pip install -e .`, dependency groups (`pip install --group docs`, pip 25.1+), and `pylock.toml` (`pip install -r pylock.toml`, experimental). `pip-tools` compiles hashes: `pip-compile requirements.in -o requirements.txt`.

## Version specifiers (PEP 440)

Comma means AND. `>=1.0, <2.0` = at least 1.0 and below 2.0.

| Operator | Meaning | Example |
| --- | --- | --- |
| `==` | Exact (`==1.1` equals `==1.1.0`) | `requests==2.32.3` |
| `== x.*` | Prefix match | `==3.1.*` = any `3.1.x` |
| `!=` | Exclusion | `!=1.3.4.*` |
| `>=`, `<=` | Inclusive bound | `>=1.0, <2.0` |
| `>`, `<` | Exclusive bound | `>2.0` |
| `~=` | Compatible release (`~=1.4.5` = `>=1.4.5, ==1.4.*`) | `~=2.2` = `>=2.2, ==2.*` |
| `;` | Environment marker | `pywin32 ; sys_platform=="win32"` |

Pre-releases (`1.0a1`, `2.0rc1`, `2.0.dev1`) are **excluded by default** unless your specifier mentions one or you pass `--pre`.

## Wheels vs. sdists

| Format | File | What happens on install |
| --- | --- | --- |
| **sdist** | `pkg-1.0.tar.gz` | Raw source, must be *built* (slow, may need C compiler) |
| **wheel** | `pkg-1.0-py3-none-any.whl` | Pre-built ZIP, just copied into `site-packages` (fast) |

Filename tags tell compatibility: `cp312-cp312-manylinux_2_28_x86_64` = CPython 3.12 on Linux, `py3-none-any` = pure-Python universal.

pip prefers wheels and falls back to building sdists. Controls:

```bash
python -m pip install --only-binary :all: -r requirements.txt  # never compile
python -m pip install --prefer-binary requests                   # prefer wheel
python -m pip wheel --wheel-dir=./wheels -r requirements.txt    # build locally
python -m pip install --no-index --find-links=./wheels -r requirements.txt  # offline
```

<Callout type="tip">
**Always publish both**
If you publish a package, upload one sdist + wheels for each platform. Eggs (`.egg`) are obsolete — PyPI rejects them.
</Callout>

## Dependency resolution: the 2020 resolver

Before pip 20.3, the resolver was greedy first-found-wins: it could silently install a broken combo (e.g. `six<1.12` alongside a package requiring `six>=1.12`).

The current resolver is strict + backtracking: it picks the latest versions satisfying *all* constraints, and on conflict emits `ResolutionImpossible` with a `The conflict is caused by:` chain.

Teach yourself these fixes:

```bash
python -m pip check                  # verify no broken deps after install
python -m pip install --upgrade pkg1 pkg2  # let pip re-resolve stale pins
```

- Loosen pins (`pkg1 pkg2`, not `==` both) and add lower bounds.
- Use `-c constraints.txt` to cap a bad transitive version without installing it.
- Lock deploys with `pip-tools` / `pip freeze`.
- `--no-deps` disables resolution entirely (advanced, breaks guarantees).

## Custom indexes and config

Default index is `https://pypi.org/simple`. For private mirrors:

```bash
python -m pip install --index-url https://my.repo/simple/ SomePkg
python -m pip install --extra-index-url https://my.repo/simple SomePkg
python -m pip install --no-index --find-links=/local/dir/ SomePkg
python -m pip config list
python -m pip config debug
python -m pip cache purge
```

Precedence (low → high): global → user → site (`$VIRTUAL_ENV/pip.conf`) → `PIP_CONFIG_FILE` → `PIP_<OPTION>` env var → CLI flag.

<Callout type="warn">
**Dependency confusion risk**
`--extra-index-url` for private packages can pull an attacker-owned same-name package from public PyPI. Prefer a single `--index-url` or hash-checking for private feeds.
</Callout>

## Security: hash-checking mode

By default pip only checks download corruption + TLS — not tamper-proof, and it can run arbitrary build code.

Hardened deploys pin + hash every artifact:

```text
requests==2.32.3 \
  --hash=sha256:2cf24dba... \
  --hash=sha256:486ea462...
```

```bash
python -m pip hash dist/*
python -m pip install --require-hashes -r requirements.txt
python -m pip install --only-binary :all: -r requirements.txt  # avoid compiling sdists
```

Rules: all-or-nothing — one `--hash` enables the mode globally, then *all* requirements + dependencies need hashes and `==` pins.

## pip vs. the modern stack: `uv`, `pip-tools`, `poetry`

| Dimension | pip (+ venv + pip-tools) | uv |
| --- | --- | --- |
| Install | Ships with Python | Rust single binary |
| Speed | Baseline, serial | 6–12x cold, up to 30–100x warm |
| Declaring deps | `requirements.in` / manual `pyproject.toml` | `pyproject.toml` via `uv add` |
| Lockfile | `requirements.txt` via `pip-compile`, per-platform | `uv.lock` universal TOML |
| Env handling | Manual `python -m venv` + activate | Auto `.venv` + `uv sync` / `uv run` |
| Best for | Zero-install, teaching, legacy | New projects, CI, monorepos |

- **`pip-tools`:** minimal lockfile only — `requirements.in` → `pip-compile` → pinned `requirements.txt` → `pip-sync`. Keep if deploy expects plain `requirements.txt`.
- **`poetry`:** full manager with `poetry.lock`, great packaging backend, slower pure-Python resolver. Keep if working.
- **`uv pip`:** drop-in — `uv pip install -r requirements.txt`, `uv pip compile`, `uv pip sync`, `uv venv` work on existing pip files for instant speedup.

<Callout type="tip">
**When pip is the ideal choice:**
1. **Universality:** ships with every Python — locked-down runners, minimal Docker images.
2. **Tutorials:** every guide assumes `pip install -r requirements.txt`.
3. **Legacy compatibility:** exotic indexes, old `setup.py` flows, permissive handling uv rejects.
4. **Minimal surface:** deploy expects plain `requirements.txt`, no all-in-one magic.
5. **Stability:** PyPA governance, decades of support — leave working setups alone.
</Callout>

### Key takeaways

- Always invoke as `python -m pip` — never bare `pip`, never `sudo pip`, never `import pip`.
- Always work in a venv — PEP 668 blocks global installs on modern distros for a reason.
- `requirements.txt` is universal but flat — `freeze` for deploys, hand-write bounds for libraries.
- PEP 440 specifiers (`==`, `>=`, `~=`, `;`) + wheels-vs-sdists explain 90% of install behavior.
- The 2020 resolver is strict — read `ResolutionImpossible`, then loosen pins or add constraints.
- pip wins on universality and teaching; `uv pip` is a drop-in when you need speed, `uv.lock` when you need universal reproducibility.

<Callout type="info">
**The bigger picture**
pip isn't the fastest installer — it's the *common language* every Python tool speaks. Learn pip's venv + requirements + specifier model once, and `uv`, `poetry`, and `pip-tools` all become small variations on the same idea.
</Callout>
