# It's Objects, Not *Text*

A shell that hands you objects instead of lines of text changes which questions you can ask. This lesson starts at the prompt and assumes nothing: what a command is, why the pipeline matters, the commands you will use every day, and then scripts, errors, and other people's machines.

**PowerShell 7.6 LTS · 25 commands · 6 parts + appendices.**

## Part 01 — Before You Type Anything

### You have to type at your own computer

Let's say you have been handed a Windows machine to look after. Nothing dramatic — somebody needs to know what is on it, what is running on it, and they need the same small job done again next week. Clicking through Settings and File Explorer works right up until the moment it doesn't: you cannot repeat a hundred clicks, you cannot write them down, and you cannot ask a question like *which of these four thousand files have not been touched in a year?*

So you open a **shell**. A shell is a program where you type instructions as text instead of pointing at things. You type a line, press `Enter`, and it answers. That is the entire interaction model, and it never changes.

**PowerShell** is Microsoft's shell. The name covers two things, and the difference matters on Windows:

| Name | Program | Where it comes from |
| --- | --- | --- |
| `Windows PowerShell 5.1` | `powershell.exe` | Built into Windows. Old, still everywhere, missing modern syntax |
| `PowerShell 7` | `pwsh.exe` | A separate install. Current LTS is 7.6. This lesson targets it |

They install side by side and do not interfere with each other. If you want the modern one, one line gets it on a current Windows machine:

```powershell
# in an ordinary command prompt or PowerShell 5.1 window
winget install --id Microsoft.PowerShell
```

Then open **PowerShell 7** from the Start menu, or `pwsh` in Windows Terminal. You will get something like this, and it is waiting for you:

```text
PS C:\Users\you>
```

That is the **prompt**. `PS` tells you which shell this is; `C:\Users\you` tells you where you currently are, the way a file manager window shows a folder. The cursor sits at the end doing nothing until you type something and press Enter.

### Four habits worth having before command one

- `Tab` completes names. Type `Get-Ch` and press Tab; the shell fills in `Get-ChildItem`. Press it again to cycle through alternatives. You will type less and spell nothing.
- `↑` walks back through what you already typed, so a long pipeline is four seconds of key presses away from being repeated.
- `Ctrl`+`C` stops whatever is running. It is the panic button, and it is safe.
- `cls` clears the screen. Nothing you ran is undone — it just tidies the window.

Now the habit that actually matters. You will be tempted to memorize commands, and that is the wrong instinct, because there are thousands of them and most do not exist until you install something. The shell ships with its own index and its own manual. Think of it as a librarian standing next to you rather than a filing cabinet you have to learn the shape of: *ask what commands look like this*, and *ask what this one does*.

### 01 · `$PSVersionTable` — which PowerShell is this?

```powershell
$PSVersionTable
```

Prints the version, edition, and platform of the shell you are currently typing in. It looks like a command, but it is a **variable** — a named place where the shell keeps a value, and the name starts with a dollar sign. Typing a variable's name prints its contents. This is the first thing to run on any machine, because half the answers you will find online are wrong for the version you are on.

```text
PS> $PSVersionTable
Name                           Value
----                           -----
PSVersion                      7.6.6
PSEdition                      Core
GitCommitId                    7.6.6
OS                             Microsoft Windows 10.0.26100
Platform                       Win32NT
PSCompatibleVersions           {1.0, 2.0, 3.0, 4.0…}
PSRemotingProtocolVersion      2.4
SerializationVersion           1.1.0.1
WSManStackVersion              3.0
```

Look at the shape of that answer rather than the numbers. It is a stack of **named rows**, not a sentence and not a stream of lines to be carved up. Each row has a name on the left and a value on the right, and that structure is the single most important thing about this shell. It is why the rest of this lesson works.

<Callout type="info">
If `PSVersion` says `5.1` and `PSEdition` says `Desktop`, you opened Windows PowerShell, not PowerShell 7. Close it, and start `pwsh` instead. Almost everything in this lesson still works on 5.1, but the modern shortcuts do not.
</Callout>

*What happens when you press Enter: (1) you type text — the only text in the whole sequence; (2) PowerShell reads the line, splits it up, and sees a pipeline; (3) the commands run and hand objects to each other; (4) the surviving objects are drawn as a table to fit your window — a rendering made for your eyes and thrown away the moment it is printed. **Text in, text out, objects in between.***

### 02 · `Get-Help` — the manual that is always installed

```powershell
Get-Help <command> [-Examples] [-Full] [-Online] [-ShowWindow]
```

Explains any command without leaving the shell or opening a browser. Nobody remembers a thousand commands. What you need is the ability to ask about the one in front of you, and the shape of the answer is genuinely good: a synopsis, a description, the syntax, and then one example per scenario.

```text
PS> Get-Help Get-ChildItem -Examples
NAME
    Get-ChildItem

SYNOPSIS
    Gets the items and child items in one or more specified locations.

    ----------  Example 1: Get child items in the current directory  ----------
    Get-ChildItem

    This command gets the child items in the current directory. If the
    directory has no child items, the command doesn't return anything.
```

Four ways to ask:

| You type | You get |
| --- | --- |
| `Get-Help <cmd>` | The synopsis, syntax, and parameter list |
| `-Examples` | Just the examples — usually the fastest path to a working command |
| `-Full` | Everything, including parameter details and notes |
| `-Online` | Opens the vendor's documentation page in your browser |

Help also covers *concepts*, not just commands. Anything beginning with `about_` is a short essay on part of the language — `Get-Help about_Quoting_Rules`, `about_Comparison_Operators`, `about_Pipelines`. When you do not know what to search for, start there.

<Callout type="tip">
On a fresh machine the help text is a stub. Run `Update-Help -Scope CurrentUser` once and you get the full offline manual for every command you have installed — worth the two minutes, and it works without administrator rights.
</Callout>

### 03 · `Get-Command` — find the command you have forgotten

```powershell
Get-Command [[-Name] <string[]>] [-Verb <string[]>] [-Noun <string[]>] [-Module <string>]
```

Searches everything installed on the machine, by name, verb, or noun. Every command name in PowerShell is two pieces: a **verb** saying what happens, and a **noun** saying what it happens to. `Get-Service`, `Stop-Service`, `New-Service`. That convention exists so you can guess, and `Get-Command` is how you check the guess and find its neighbours.

```text
PS> Get-Command *service*
CommandType     Name                Version    Source
-----------     ----                -------    ------
Cmdlet          Get-Service         7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          New-Service         7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          Restart-Service     7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          Resume-Service      7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          Set-Service         7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          Start-Service       7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          Stop-Service        7.0.0.0    Microsoft.PowerShell.Management
Cmdlet          Suspend-Service     7.0.0.0    Microsoft.PowerShell.Management
```

You did not have to know that `Suspend-Service` existed. Knowing the noun is enough to list the verb family, and knowing the verb is enough to list what you can do to a thing. That is a much smaller thing to learn than a vocabulary of commands.

The verbs you will meet immediately:

| Verb | Means | Example |
| --- | --- | --- |
| `Get` | read something, change nothing | `Get-Process` |
| `Set` | change something that exists | `Set-Content` |
| `New` | create something | `New-Item` |
| `Remove` | delete something | `Remove-Item` |
| `Start` / `Stop` | begin or end something running | `Start-Service` |
| `Test` | answer yes or no | `Test-Path` |
| `Invoke` | carry out an action, often a remote or web one | `Invoke-RestMethod` |
| `ConvertTo` / `ConvertFrom` | change one data format into another | `ConvertTo-Json` |
| `Export` / `Import` | write to, or read from, a file | `Export-Csv` |

One hand-written command plus one convention is the whole of part one. Everything else is what those commands hand to each other.

## Part 02 — The Idea That Changes Everything

### You asked for one column and got a wall of text

Here is the job. You want the five processes using the most memory, by name and size. You type `Get-Process`, and the screen fills with a table of every process on the machine.

The obvious next move — the one every other shell trained you to make — is to treat that table as text. Search it, cut the columns you want with a regular expression, and hope the layout holds. In PowerShell that instinct leads straight into a wall.

**Why the wall is there.** What you are looking at is a **rendering**. The shell measured your window, decided how wide each column could be, and drew the values to fit. That has consequences you will hit within a week:

- A long value is cut short and shown as `…` — the data was never truncated, only the drawing.
- Column widths shift as the values change, so anything you write to parse column 3 breaks on another machine.
- Numbers get thousands separators and are right-aligned, so `838 860 800` is not a number you can add up.
- Dates follow your locale. The same command on a colleague's laptop prints `9/26/2026`; on yours it might print `26/09/2026`.
- If the list is long, the shell may print a header, some rows, and `<n> more objects`.

Every one of those is a property of the printing, not of the data. You are trying to read a receipt through a magnifying glass while the till's database is sitting right there.

Because that is what actually came back. `Get-Process` did not hand you lines of text; it handed you a set of **objects**, one per process, each carrying named pieces of data. PowerShell calls those pieces **properties**. The table on screen is drawn *from* them, and then discarded. And the pipe — the `|` character — passes those objects along, whole, to whatever comes next. Not text about the objects. The objects.

*Left: the receipt — what you saw, a drawing with truncation, separators, and alignment. Right: the database — the real object, full values, exact types, nothing dropped. **The pipe hands over the right-hand thing, not the left one.***

### 04 · `Get-Member` — what am I actually holding?

```powershell
<anything> | Get-Member [-MemberType <Property | Method | …>]
```

Tells you the type of an object and every property and method on it. This is the command to reach for when you do not know what you are working with — which is most of the time, including when the output looked fine. Pipe anything into it.

```text
PS> Get-Process | Get-Member
   TypeName: System.Diagnostics.Process

Name               MemberType     Definition
----               ----------     ----------
Kill               Method         void Kill(), void Kill(bool entireProcessTree)
WaitForExit        Method         bool WaitForExit(int milliseconds)
CloseMainWindow    Method         bool CloseMainWindow()
Handles            Property       int Handles {get;}
Id                 Property       int Id {get;}
ProcessName        Property       string ProcessName {get;}
WorkingSet64       Property       long WorkingSet64 {get;}
```

Two things are going on here, and they answer two different questions. The first line names the **type**: every process you were handed is a `System.Diagnostics.Process`. The table below it is the complete list of what you can ask that object for.

| MemberType | What it is | How you use it |
| --- | --- | --- |
| `Property` | data the object holds | `$process.WorkingSet64` |
| `Method` | an action the object can perform | `$process.Kill()` |

That is the difference between reading and doing, and it is worth noticing that the action lives on the object rather than in some separate command. You will mostly use properties; methods are how you will eventually stop a process inside a script.

<Callout type="tip">
`Get-Member` shows a shortened list by default. Add `-Force` to see the members inherited from the base type, and `-MemberType Property` when you only want the data and the list is drowning in methods.
</Callout>

### 05 · `Select-Object` — choose the columns

```powershell
… | Select-Object [-Property] <string[]> [-First <n>] [-Last <n>] [-Skip <n>] [-Unique] [-ExpandProperty <string>]
```

Keeps the properties you name and drops the rest, or takes the first or last few objects. Now the original question is one line: name the properties you want, sort by the one that matters, keep the top five. Note that there is still no parsing anywhere — you are naming data, not cutting text.

```powershell
PS> Get-Process |
>>     Select-Object ProcessName, Id, WorkingSet64 |
>>     Sort-Object WorkingSet64 -Descending |
>>     Select-Object -First 5
```

```text
ProcessName      Id WorkingSet64
-----------      -- ------------
Code          12004   1262485504
chrome        22000    981254144
msedge         8892    620756992
pwsh           4416    128974848
OneDrive       6120     96276480
```

`WorkingSet64` is a raw byte count with no separators and no rounding, which is exactly why you can sort by it: it is a number, not a piece of formatted text. Whether that is *good* to look at is a separate question, and the next trick answers it.

**Making a column that does not exist yet.** You can ask for a property that the object does not have, as long as you say how to compute it. This is called a calculated property, and it turns an unreadable byte count into something you would actually show somebody:

```powershell
PS> Get-Process | Sort-Object WorkingSet64 -Descending |
>>     Select-Object -First 5 ProcessName, Id,
>>       @{Name='RAM (MB)'; Expression={[math]::Round($_.WorkingSet64/1MB, 1)}}
```

```text
ProcessName      Id RAM (MB)
-----------      -- --------
Code          12004   1203.8
chrome        22000    935.8
msedge         8892    592.0
pwsh           4416    123.0
OneDrive      6120     91.8
```

The `@{ }` is a hashtable — a set of name-and-value pairs you can build on one line — and `$_` means *the object currently being handled*. Read it as: for each object, make a column called RAM (MB), computed by dividing its working set by one megabyte and rounding to one decimal. This pattern is everywhere in real scripts, and it is worth copying exactly.

<Callout type="warn">
Never pipe `Format-Table` or `Format-List` into anything that does real work. Those two commands turn objects into display text, and once that has happened `Select-Object`, `Where-Object`, `Sort-Object` and `Export-Csv` all receive text instead of data. Format last, or format never.
</Callout>

### Now filter and sort what you have

You have the columns. The next thing you want is *fewer objects*: only the services that are stopped, only the files from last year, only the processes over a threshold. The property names from `Get-Member` are the vocabulary you filter with.

### 06 · `Where-Object` — keep only the objects that match

```powershell
… | Where-Object [-Property] <name> [-Comparison] <value>
… | Where-Object <script block>
```

Tests each object against a condition and passes on the ones that pass. There are two spellings and you should recognise both, because you will see each of them in other people's scripts. The short one reads like a sentence; the long one can express anything.

```powershell
PS> Get-Service | Where-Object Status -eq Stopped
PS> Get-Service | Where-Object { $_.Status -eq 'Stopped' }
```

```text
Status   Name               DisplayName
------   ----               -----------
Stopped  AppXSvc            AppX Deployment Service (AppXSVC)
Stopped  BITS               Background Intelligent Transfer Service
Stopped  ClipSVC            Client License Service (ClipSVC)
Stopped  MapsBroker         Downloaded Maps Manager
Stopped  WSearch            Windows Search
```

Both lines do the same thing. The first is the **simplified syntax**, added so that the common case stays readable. The second is a **script block** — the code between braces — which is run once per object with `$_` set to that object. The script block is the general form; anything you cannot say in the short version, you can say in the long one.

The comparison operators, and the trap among them:

| Operator | Means | Example |
| --- | --- | --- |
| `-eq` / `-ne` | equals / not equals | `$_.Status -eq 'Stopped'` |
| `-gt` `-ge` `-lt` `-le` | greater, greater-or-equal, less, less-or-equal | `$_.CPU -gt 50` |
| `-like` / `-notlike` | matches a wildcard pattern | `$_.Name -like '*svc*'` |
| `-match` / `-notmatch` | matches a regular expression | `$_.Name -match '^Win'` |
| `-in` / `-contains` | is a member of a list | `$_.Name -in $allowed` |

Two things surprise everyone. First, comparison uses `-eq`, and a bare `=` means *assign this variable* — which is why a condition that always seems to be true is usually a typo. Second, comparisons are written *value first*: `$_.Status -eq 'Stopped'`, not the other way around, which is the reverse of how most people say it out loud.

<Callout type="info">
Case does not matter in comparisons. `-eq` matches `stopped` and `Stopped` alike; use `-ceq` or `-clike` when the difference actually matters.
</Callout>

### 07 · `Sort-Object` — put them in order

```powershell
… | Sort-Object [-Property] <string[]> [-Descending] [-Unique]
```

Rearranges objects by one or more properties, ascending by default. Sorting is the cheapest way to make a list answer a question. The alphabetical order of services is useless; sorted by status, the stopped ones are all in one place. Sorted descending by memory, the biggest problem is the first line of the output rather than something you find by scrolling.

```text
PS> Get-Service | Sort-Object Status, Name | Select-Object -First 4
Status   Name               DisplayName
------   ----               -----------
Running  AaronGuest         AaronGuest
Running  AdobeARMservice    Adobe Acrobat Update Service
Stopped  AppXSvc            AppX Deployment Service (AppXSVC)
Stopped  BITS               Background Intelligent Transfer Service
```

Naming two properties sorts by the first and breaks ties with the second. `-Descending` flips the whole thing, and `-Unique` removes duplicates — a handy way to ask *what are the distinct values in this property?* without knowing the word "distinct".

*A four-stage pipeline: `Get-Process` emits 214 objects → `Where-Object` reduces that to 12 → `Sort-Object` reorders the same 12 → `Select-Object -First 5` keeps 5. Each step receives objects and hands back objects. **Filtering changes the count** (Where-Object is the only stage that can make the stream shorter, and it never edits an object); **sorting and selecting do not** — they move objects around or reshape what each one looks like, and the next command never knows the difference. Learning PowerShell is largely learning which of these three shapes a command has.*

### Now do something to each one

So far every command has been read-only. Filtering finds the twelve files you care about; it does not rename them, move them or delete them. For that you need a command that runs *your* instructions once per object, and it has the ugliest name in the language.

### 08 · `ForEach-Object` — do something to each one

```powershell
… | ForEach-Object [-Process] <script block> [-Begin <block>] [-End <block>] [-Parallel]
```

Runs a block of instructions once for every object arriving through the pipe. Inside the braces, `$_` is the object currently in your hands — you met it in `Where-Object`, where it was being tested. Here it is being acted on. Start with something small enough to predict:

```text
PS> 1..3 | ForEach-Object { "line $_" }
line 1
line 2
line 3
```

`1..3` is a **range**: it produces the numbers 1, 2 and 3 as three separate objects, which is a convenient way to make a loop out of nothing. Then the braces ran three times.

Now the same shape on something real, where the work is done for you by other commands:

```powershell
PS> Get-ChildItem -Path . -Filter *.log |
>>     ForEach-Object { Rename-Item -Path $_.FullName -NewName ($_.BaseName + '.log.old') }
```

Read that as a sentence: list the `.log` files here, and for each one, rename it to its own base name plus `.log.old`. The properties `FullName` and `BaseName` came off the file objects and are being handed to `Rename-Item` as parameters — objects in, objects referenced, work done.

Three members you will use constantly:

| Inside the braces | Is |
| --- | --- |
| `$_` | the current object (also spelled `$PSItem` when you want it to be obvious) |
| `$_.Property` | one property of the current object |
| `$_.Method()` | an action on the current object, from `Get-Member` |

On PowerShell 7 you can also add `-Parallel` to run the block on several objects at once, which is a real speed-up for slow work like copying files over a network. Do not start there: get it correct in order first, and remember that `$_` inside a parallel block is a private copy.

### 09 · `Measure-Object` — how many, how much

```powershell
… | Measure-Object [-Property <string[]>] [-Sum] [-Average] [-Maximum] [-Minimum] [-Line] [-Word] [-Character]
```

Counts objects, and adds up or averages any property that is a number. This is the command that converts a list into an answer. You had a table of processes; what you wanted was a number.

```text
PS> Get-Process | Measure-Object WorkingSet64 -Sum -Average -Maximum
Count             : 214
Average           : 184320000.5
Sum               : 39444480107
Maximum           : 1262485504
Minimum           :
StandardDeviation :
Property          : WorkingSet64
```

Some genuinely useful sentences come out of this once you combine it with filtering. *How much memory is this browser using in total?* Filter to the browsers, then sum. *Are any of these logs long enough to matter?* Measure the lines:

```text
PS> Get-Content -Path .\app.log | Measure-Object -Line -Word -Character
Lines Words Characters Property
----- ----- ---------- --------
14208 98411     771238
```

That last one works because `Get-Content` hands out one string per line of the file, and text has properties a command can count. It is also a good demonstration of the whole idea: nobody wrote a loop. You handed a stream of objects to a command that knows how to summarise a stream of objects.

## Part 03 — Working on a Real Machine

### The commands you'll live in

Files, folders, and the thing you did not expect: the filesystem is only one of the places this shell can stand.

You have almost certainly typed `dir` already, and it worked. That is the first trap. `dir`, `cd`, `copy`, `type`, `del` and `cls` are all **aliases** — short names the shell accepts so that people arriving from `cmd.exe` and Linux feel at home. They hide the real command names, and the real names are the ones that come with syntax you can look up, parameters you can discover, and siblings you can guess.

| Alias | Real command |
| --- | --- |
| `dir`, `ls`, `gci` | `Get-ChildItem` |
| `cd`, `chdir` | `Set-Location` |
| `cat`, `type` | `Get-Content` |
| `rm`, `del`, `erase` | `Remove-Item` |
| `cls`, `clear` | `Clear-Host` |
| `?` | `Where-Object` |
| `%` | `ForEach-Object` |

Aliases are fine to type for speed. They are terrible to write into anything you want to keep, because they can be redefined by a profile or a module and then your script does something else. `Get-Alias dir` tells you which real command a short name is standing in for.

### 10 · `Get-ChildItem` — everything in a folder, and below it

```powershell
Get-ChildItem [[-Path] <string[]>] [-Filter <string>] [-Recurse] [-File] [-Directory] [-Force] [-Depth <n>]
```

Lists the items in a location, optionally recursing into subfolders and optionally filtered. This is the most-typed command in the language, and it is worth reading its help once, because the switches are what turn a listing into an answer. `-File` drops folders from the result; `-Recurse` walks down the tree; `-Filter` is applied by the filesystem itself and is much faster than filtering afterwards; `-Force` includes hidden items.

```powershell
PS> Get-ChildItem -Path C:\Logs -Filter *.log -Recurse -File |
>>     Select-Object -First 4 Name, Length, LastWriteTime
```

```text
Name             Length LastWriteTime
----             ------ -------------
app-20260921.log  71238 9/21/2026 4:02:11 AM
app-20260922.log  69884 9/22/2026 4:01:58 AM
app-20260923.log  74102 9/23/2026 4:02:07 AM
app-20260924.log  70511 9/24/2026 4:02:04 AM
```

Now look at those column names, because they are the reason this shell is worth the afternoon. `Length` and `LastWriteTime` are properties, so the question from the first section — which files have not been touched in a year? — is a filter over the objects that came back:

```powershell
PS> Get-ChildItem -Path C:\Logs -File -Recurse |
>>     Where-Object LastWriteTime -lt (Get-Date).AddYears(-1) |
>>     Sort-Object Length -Descending |
>>     Select-Object -First 10 Name, Length, LastWriteTime
```

No parsing, no `findstr`, no guessing at column positions, and no dependency on how the listing happens to be laid out on screen. `(Get-Date).AddYears(-1)` is a date object a year ago, and the comparison happens between real values.

### 11 · `Set-Location` — move around

```powershell
Set-Location [[-Path] <string>] [-PassThru] [-StackName <string>]
```

Changes where you are, then reports it back with `Get-Location`. The prompt from section one comes back to life here: `Set-Location` changes the directory the prompt is showing you. `Get-Location` prints it, and tab completion works on the path, so you rarely type a full one.

```text
PS> Set-Location C:\Logs
PS C:\Logs> Get-Location

Path
----
C:\Logs
```

Here is the part that surprises everybody. That path is not a folder path in the usual sense — it is a **drive**, and the filesystem is only one of them. The same navigation commands work everywhere:

```text
PS> Get-PSDrive
Name           Used (GB)     Free (GB) Provider      Root
----           ---------     --------- ------      ----
C                 412.44        511.02 FileSystem    C:\
Cert                                     Certificate   \
Env                                      Environment
HKCU                                     Registry      HKEY_CURRENT_USER
HKLM                                     Registry      HKEY_LOCAL_MACHINE
Variable                                 Variable
```

Go into `Env:` and you are standing in your environment variables, where `Get-ChildItem` lists them and `$env:PATH` still works. Go into `Cert:` and you are standing in the certificate stores. This is the **provider** model: one set of commands — navigate, list, read, create, delete — pointed at several different kinds of store.

*Drives are places, not disks: `C:` · FileSystem, `HKLM:` · Registry, `Cert:` · Certificate, `Env:` · Environment — `Set-Location Env:` then the ordinary `Get-ChildItem` lists your environment variables. Nine commands you learn once work against the filesystem, the registry, the certificate stores and your environment variables, because they all expose the same provider interface.*

### 12 · `Get-Content` — read a file

```powershell
Get-Content [-Path] <string[]> [-Raw] [-Tail <n>] [-TotalCount <n>] [-Wait]
```

Hands you the contents of a file, one line per object. By default this returns *one string per line*, which is the useful default: it means the output is a collection you can filter, count and search with the same commands you have been using all along, and processing a large log file does not need to hold the whole thing in memory.

```text
PS> Get-Content -Path .\app.log -Tail 3
2026-09-24 04:02:01 INFO  worker 4121 finished batch 8841 in 3.2s
2026-09-24 04:02:04 WARN  worker 4121 retry 1 of 3 for batch 8842
2026-09-24 04:02:07 ERROR worker 4121 batch 8842 failed: timeout

PS> Get-Content -Path .\app.log | Where-Object { $_ -match 'ERROR' } | Measure-Object -Line
Lines Property
----- --------
   14
```

That second pipeline is worth pausing on. Each line is a string, so `$_ -match 'ERROR'` tests it with a regular expression, and the survivors are counted. This is the one place where working with text is correct rather than a workaround — you are searching text because the file *is* text.

Two switches to know: `-Raw` returns the entire file as a single string, which is what you want when the structure matters across lines, like JSON. `-Tail 20` reads only the last twenty lines, so watching a log does not mean reading a gigabyte.

### 13 · `Set-Content` — write a file

```powershell
Set-Content [-Path] <string[]> [-Value] <object[]> [-Encoding <encoding>] [-NoNewline]
```

Writes strings to a file, replacing what was there. `Add-Content` appends instead.

```powershell
PS> Get-Process | Sort-Object WorkingSet64 -Descending |
>>     Select-Object -First 10 ProcessName, Id |
>>     Export-Csv -Path .\top-processes.csv -NoTypeInformation

PS> Set-Content -Path .\status.txt -Value "checked at $(Get-Date)"
PS> Add-Content -Path .\status.txt -Value 'run finished'
```

Notice the two different choices on those lines. `Export-Csv` is for *data* — it takes objects and writes their properties as columns, with a header, and it can be read back into objects later by `Import-Csv`. It is the format to reach for when another program, or future you, needs to read the file.

`Set-Content` is for *text*. It writes whatever you give it, and the `$( )` in the middle of that string is a subexpression: everything inside is evaluated first, then dropped into the string. That is how you get today's date into a log line.

<Callout type="info">
There is a third way to write a file, `Out-File`, and the difference matters. `Out-File` runs its input through the display formatter, so it writes what you would have seen on screen — padding, truncation and all. Use `Export-Csv` or `ConvertTo-Json` for data, `Set-Content` for text, and `Out-File` only when you genuinely want a copy of the screen.
</Callout>

### 14 · `Test-Path` — does it exist?

```powershell
Test-Path [-Path] <string[]> [-PathType <Any | Leaf | Container>]
```

Answers true or false, which is what a script needs before it does anything destructive.

```text
PS> Test-Path -Path C:\Logs\app.log
True
```

```powershell
PS> if (Test-Path -Path .\outbox -PathType Container) {
>>     Copy-Item -Path .\report.csv -Destination .\outbox
>> } else {
>>     Write-Warning 'no outbox folder - nothing copied'
>> }
```

This is the smallest complete script in the lesson: a condition, an action, and a branch for when the condition is false. `if` is followed by a test in parentheses and a block in braces, exactly as in the `Where-Object` script blocks you have already been writing.

Commands that answer a yes-or-no question are named `Test-`, and they all work this way. When you are about to do something irreversible, this is the check you put in front of it.

### 15 · `Remove-Item` — delete something

```powershell
Remove-Item [-Path] <string[]> [-Recurse] [-Force] [-WhatIf] [-Confirm]
```

Deletes files, folders, registry keys, and anything else a provider offers.

```powershell
PS> Remove-Item -Path .\app-20260101.log

PS> Get-ChildItem -Path C:\Logs -Filter *.log |
>>     Where-Object LastWriteTime -lt (Get-Date).AddYears(-1) |
>>     Remove-Item -WhatIf
```

```text
What if: Performing the operation "Remove File" on target "C:\Logs\app-20240911.log".
What if: Performing the operation "Remove File" on target "C:\Logs\app-20240912.log".
```

That second command is the single most important habit in this lesson. `-WhatIf` runs the whole pipeline, prints exactly what it *would* delete, and deletes nothing. Every command that changes something supports it. Write the dangerous pipeline, append `-WhatIf`, read the list, and only then remove the flag. `-Confirm` is the other option, asking you about each item one at a time.

<Callout type="warn">
`Remove-Item` does not use the Recycle Bin. The files are gone, and there is no undo command. The combination `-Recurse -Force` on a folder is the one to be slowest with — check the path with `Get-ChildItem` first, since the length of a path is no indication of what it points at.
</Callout>

### The machine is doing things you didn't start

Task Manager shows you the same information this section is about. It is a good tool and it fails the same way the GUI always fails: you cannot ask it a question with a threshold in it, you cannot run it on the machine you are not sitting at, and you cannot schedule it for three in the morning.

### 16 · `Get-Process` — what is running

```powershell
Get-Process [[-Name] <string[]>] [-Id <int[]>] [-IncludeUserName]
```

Returns one object per running process, with memory, CPU and handles on each. You have been using this since the second section as raw material, so here is what it actually is. `Get-Process` asks the operating system for every running process and hands back one `System.Diagnostics.Process` object each. `-Name` accepts wildcards, which is how you talk about a family of processes rather than one.

```text
PS> Get-Process -Name pwsh, chrome | Measure-Object WorkingSet64 -Sum
Count             : 7
Sum               : 2217443328
Property          : WorkingSet64
```

```powershell
PS> Get-Process | Where-Object CPU -gt 100 |
>>     Sort-Object CPU -Descending |
>>     Select-Object -First 5 ProcessName, Id, CPU
```

That first line answers a question Task Manager cannot: *how much memory is my browser and my shell using together?* Nobody wrote a loop; a filter selected objects and a measurement summarised them.

### 17 · `Stop-Process` — end one

```powershell
Stop-Process [-Name] <string[]> | [-Id] <int[]> [-Force] [-WhatIf] [-Confirm]
```

Ends a running process by name or id, without asking it politely first.

```powershell
PS> Stop-Process -Name notepad

PS> Get-Process -Name chrome |
>>     Where-Object WorkingSet64 -gt 2GB |
>>     Stop-Process -WhatIf
```

The second command is the shape you want to internalise: a condition that describes the problem, not a name you guessed. *Close the browser tabs using more than two gigabytes each* is a rule that still means the same thing tomorrow; `Stop-Process -Name chrome -Force` is a hammer that takes the whole browser with it.

There is a gentler option and it is worth knowing about: the process objects have a method for asking an application to close itself, `CloseMainWindow()`, which lets a program save its work first. `Stop-Process` is the equivalent of pulling the plug, and it is the right tool when the process has stopped responding anyway.

### 18 · `Get-Service` — the services Windows runs

```powershell
Get-Service [[-Name] <string[]>] [-DisplayName <string[]>]
Start-Service <name> | Stop-Service <name>
```

Lists the background services and their state; `Start-Service` and `Stop-Service` change that state.

```text
PS> Get-Service | Where-Object Status -eq Stopped | Select-Object -First 3 Name, DisplayName
Name    DisplayName
----    -----------
AppXSvc AppX Deployment Service (AppXSVC)
BITS    Background Intelligent Transfer Service
ClipSVC Client License Service (ClipSVC)

PS> Start-Service -Name Spooler -WhatIf
What if: Performing the operation "Start service" on target "Spooler (Print Spooler)".
```

Services are where the interesting failures live: something is wrong with a machine, and the cause is a background service that is stopped when it should be running, or running when it should have been stopped. The two commands that own that state are the ones in the syntax line, and they come with `-WhatIf` like everything else.

<Callout type="warn">
Starting and stopping services changes the machine that everyone is using, and most services require an elevated shell — one opened with *Run as administrator* — or they will fail with a permissions error. Test with `-WhatIf`, and check whether the service is set to start automatically before you decide a stopped one is a fault.
</Callout>

### 19 · `Invoke-RestMethod` — call a web API

```powershell
Invoke-RestMethod [-Uri] <uri> [-Method <Get|Post|Put|Delete>] [-Headers <hashtable>] [-Body <object>] [-UserAgent <string>]
```

Fetches a URL and, when the reply is JSON or XML, hands you the parsed objects instead of text. Every other shell gives you a downloader here. You get JSON as text, then you write a parser, then you write tests for the parser. PowerShell makes the same choice it made in section two: the reply is data, so you receive data.

```text
PS> $repo = Invoke-RestMethod -Uri 'https://api.github.com/repos/PowerShell/PowerShell' -UserAgent 'lesson'

PS> $repo.full_name
PowerShell/PowerShell

PS> $repo | Select-Object full_name, stargazers_count, open_issues_count
full_name             stargazers_count open_issues_count
---------             ---------------- -----------------
PowerShell/PowerShell            55516              1591
```

Nothing was parsed by hand. The JSON arrived, was converted into objects with properties named after the JSON keys, and now behaves exactly like a process or a file: filter it, sort it, select from it, or feed it to `Export-Csv`. The numbers above were true on the day this was written; the values move daily, and the shape they arrive in does not. Nested objects stay nested, so `$repo.owner.login` reaches into a child object.

This is also the command that makes PowerShell a scripting language for other people's systems. Almost everything you would want to automate has an API behind it: deployment hooks, ticketing systems, chat notifications, cloud provider control planes. The pattern is always the same two lines — call it, then work with the objects that came back.

## Part 04 — Making It Repeatable

### You're retyping this every morning

You have a pipeline that does the job, and you are pasting it from a note every day. The obvious next step is to put it in a file so you can run the file. That is when PowerShell stops you for the first time, with a message about execution policies that sounds far more alarming than it is.

### First, the three things a script needs from you

**Variables** give a name to a value so you can use it twice. They do not need declaring, they start with `$`, and the value keeps its type — a date stays a date:

```powershell
PS> $cutoff = (Get-Date).AddYears(-1)
PS> $logs = Get-ChildItem -Path C:\Logs -File -Recurse
PS> $old  = $logs | Where-Object LastWriteTime -lt $cutoff
PS> $old.Count
318
```

**Quoting** is the number one beginner trap, and it is worth learning properly now because it will otherwise cost you an evening. Double quotes expand variables; single quotes do not.

| You write | You get |
| --- | --- |
| `"$cutoff"` | the date inside the string |
| `'$cutoff'` | the literal text `$cutoff` |
| `"it's fine"` | a quoting error, because the apostrophe ends the string |
| `'it''s fine'` | the text `it's fine` — inside single quotes, write a quote twice to escape it |

**Collections** hold several values, and there are two kinds you will meet immediately. An **array** is an ordered list, written with `@()` or just commas. A **hashtable** is a set of name-and-value pairs, written with `@{ }` — the same shape as the calculated property in section two, which is why that syntax looked familiar.

```powershell
PS> $folders = @('C:\Logs', 'C:\Archive')
PS> $report = @{
>>     Cutoff = $cutoff
>>     Folders = $folders.Count
>>     OldFiles = $old.Count
>>     Bytes = ($old | Measure-Object Length -Sum).Sum
>> }

PS> $report
```

```text
Name                           Value
----                           -----
Cutoff                         9/26/2025 6:14:22 AM
Folders                        2
OldFiles                       318
Bytes                          941720831
```

And there it is again: the hashtable printed as named rows, the same shape as the very first command you ran. It was never a special case.

### Then the file

Save this as `Find-OldLogs.ps1`. A script is just a text file with that extension, and a `param` block at the top is what turns it from something that works here into something that works for the next person:

```powershell
param(
    [string]$Path   = 'C:\Logs',
    [int]$Months    = 12,
    [switch]$Delete
)

$cutoff = (Get-Date).AddMonths(-$Months)
$old = Get-ChildItem -Path $Path -File -Recurse |
       Where-Object LastWriteTime -lt $cutoff

"Found $($old.Count) files older than $Months months in $Path"

if ($Delete) { $old | Remove-Item -WhatIf }
```

Now it takes arguments, has defaults, and the destructive part is opt-in: `.\Find-OldLogs.ps1` reports, and `.\Find-OldLogs.ps1 -Path D:\Archive -Months 6 -Delete` does the work. That `-Delete` is a **switch** — a parameter that is either present or absent, with no value to supply.

### 20 · `Get-ExecutionPolicy` — why won't my script run?

```powershell
Get-ExecutionPolicy [-List] [-Scope <Process | CurrentUser | LocalMachine>]
```

Reports the policy that decides whether scripts are allowed to run, and at what scope. Run your new script and the answer may be a refusal rather than a result. This is the most common wall for a Windows beginner, and it is mundane: many Windows machines ship with scripts disabled, so that a file you downloaded cannot run itself without your knowledge. On others the policy is already `RemoteSigned` and the script runs first time — which is exactly why you ask the machine rather than guessing at it.

```text
PS> .\Find-OldLogs.ps1
.\Find-OldLogs.ps1 : File C:\Users\you\Find-OldLogs.ps1 cannot be loaded
because running scripts is disabled on this system.

PS> Get-ExecutionPolicy -List
        Scope ExecutionPolicy
        ----- ---------------
MachinePolicy       Undefined
   UserPolicy       Undefined
      Process       Undefined
  CurrentUser       Undefined
 LocalMachine       Restricted
```

The four policies you will actually meet:

| Policy | What runs |
| --- | --- |
| `Restricted` | Nothing. A common default on Windows client machines |
| `RemoteSigned` | Local scripts, and downloaded scripts only if they carry a signature. The usual choice |
| `AllSigned` | Every script needs a signature, local ones included |
| `Bypass` | Everything runs, and nothing is logged. For automation, never for your own machine |

The scopes matter as much as the policies: `MachinePolicy` and `UserPolicy` come from group policy, `LocalMachine` covers everybody on the computer, `CurrentUser` covers only you, and `Process` lasts until this window closes. The effective policy is the most restrictive one that is not `Undefined`.

### 21 · `Set-ExecutionPolicy` — allow your own scripts

```powershell
Set-ExecutionPolicy [-ExecutionPolicy] <policy> [-Scope <Process | CurrentUser | LocalMachine>]
```

Changes the policy for a scope you choose:

```powershell
PS> Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

That one line is the ordinary fix when you need it, and you should prefer it over anything requiring an administrator. `-Scope CurrentUser` sets the policy for your account only, leaves group policy untouched, and needs no elevation. `RemoteSigned` allows the scripts you write while still refusing unsigned scripts that arrived from the internet — and if `Get-ExecutionPolicy` already reports `RemoteSigned`, you can skip this command entirely.

<Callout type="info">
Execution policy is a guard rail, not a security boundary, and Microsoft says so in its own documentation. Anyone who can open a shell can bypass it, and it is not a substitute for antivirus or for not running things you did not read. Its real job is to stop your own machine running a script by accident.
</Callout>

*The gate your script hits first: you run a script → the execution policy asks what this machine allows → `RemoteSigned` + your own file means the script runs, while `Restricted` blocks it with "running scripts is disabled." Nothing is wrong with your script; the machine is enforcing a rule that exists so a downloaded file cannot run itself — and the fix is one command scoped to your own account, not to everybody's.*

### It said done and it wasn't

Your script ran, printed a summary, and exited quietly. Two days later somebody asks why 318 files still exist, and the answer is that most of the deletes failed and the script never mentioned it.

This is the difference between a script that works and a script you can trust, and the cause is a design decision in the shell: an error is a value, and there are two kinds.

| Kind | What happens | Example |
| --- | --- | --- |
| **Non-terminating** | The command writes an error, then carries on with the next object. The statement finishes. | `Get-ChildItem C:\nope` |
| **Terminating** | The statement stops. Without a `try`, the rest of the script may still run. | `Get-Item -Path C:\nope -ErrorAction Stop` |

Non-terminating is the default for most cmdlets, and it is why `if` conditions keep running after something inside them failed. Two automatic variables tell you what just happened: `$?` is true or false for whether the last command succeeded, and `$LASTEXITCODE` holds the exit code when you call an ordinary program like `git` or `robocopy`, which is a separate mechanism because those tools know nothing about PowerShell errors.

**The pattern that makes failures loud.** If you take one thing from this section, take this shape. It is the difference between hoping and knowing:

```powershell
$ErrorActionPreference = 'Stop'          # any error ends the script instead of scrolling past

try {
    Copy-Item -Path .\report.csv -Destination \\fileserver\reports -ErrorAction Stop
    Write-Output 'copied'
}
catch {
    Write-Error "copy failed: $($_.Exception.Message)"
    exit 1
}
```

`try` runs the block; if something throws, `catch` receives the error as an object — `$_` again — with an `Exception` property carrying the message. `exit 1` tells whatever called the script that it failed, which is how a scheduled task, a pipeline, or another script finds out.

### 22 · `Get-Error` — what just went wrong?

```powershell
Get-Error [-Newest <n>]
```

Prints the most recent error in full, as a structured object rather than one line. Errors print as a wall of red text, and the useful part is usually the exception type and the call stack, which are not what fits on one line. `Get-Error` is new in PowerShell 7 and exists to solve exactly that.

```text
PS> Get-Item -Path C:\nope -ErrorAction SilentlyContinue
PS> Get-Error
Exception             :
    Type                 : System.Management.Automation.ItemNotFoundException
    Message              : Cannot find path 'C:\nope' because it does not exist.
    TargetSite           : ExpandMshGlobPath
TargetObject          : C:\nope
CategoryInfo          : ObjectNotFound: (C:\nope:String) [], ItemNotFoundException
FullyQualifiedErrorId : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
InvocationInfo        :
    MyCommand        : Get-Item
    ScriptLineNumber : 8
```

Look at how much comes back: the exception type, the message, the object the path was resolved against, the invocation line, the stack. That depth is the point — the useful part of an error is rarely its first line — and it is why having a *command* for errors beats printing one red sentence.

`-ErrorAction SilentlyContinue` suppresses the display while still recording the error, which is how you keep a console readable during a loop over a hundred machines; `Get-Error` then recovers the detail when you need it. The full history since the window opened sits in the `$Error` collection, newest first.

## Part 05 — More Than One Machine

### One machine isn't a fleet

The script works. Now do it on forty machines, and the honest answer is that you probably remote into each one, copy the file over, run it, and hope you did not skip the one at the bottom of the list.

Every part of that is a chance to make a mistake, and none of it is the work you were asked to do. PowerShell can run a block of code on other computers directly, sending the objects back to you.

### 23 · `Invoke-Command` — run it on other computers

```powershell
Invoke-Command -ComputerName <string[]> -ScriptBlock <block> [-ArgumentList <object[]>] [-ThrottleLimit <n>] [-AsJob]
```

Sends a script block to one or more remote machines and returns what they produced:

```text
PS> Invoke-Command -ComputerName srv-01, srv-02, srv-03 -ScriptBlock {
>>     Get-Service -Name Spooler | Select-Object Status, Name
>> }

Status   Name      PSComputerName
------   ----      --------------
Running  Spooler   srv-01
Stopped  Spooler   srv-02
Running  Spooler   srv-03
```

One command, three machines, one table. The script block ran *on* each remote machine, and `PSComputerName` was added to every object so you can tell which answer came from where — which is exactly the kind of thing you would otherwise be reconstructing by hand from forty separate windows.

Remoting has to be turned on at the far end. On an internal network with domain accounts, `Enable-PSRemoting -Force` in an elevated shell on the target does it; across workgroups or untrusted networks you use `New-PSSession -Credential` or `Enter-PSSession` for an interactive connection instead.

**The catch, and it is interesting rather than annoying.** Look again at the type of what came back. Those are not live `ServiceController` objects sitting in your session — they are copies, reconstructed on your side from a serialised form. PowerShell tells you so in the type name: `Deserialized.System.ServiceProcess.ServiceController`.

The properties survived the trip, because they are data. The *methods* did not, because running a method would mean reaching back across the network. So `Get-Member` on a remote result shows fewer members than the same command run locally — and now you know why, instead of being mystified by it.

*One machine sends a script block to three servers; each runs the block; objects come back from each. What arrives is a `Deserialized` copy of every object — properties, yes; methods, no. Remoting is the same idea at a different distance: the script block runs where the data is, and objects come back — serialised, then rebuilt.*

### Now other people need it

The script is on your desktop, hard-coded to `C:\Logs` and a twelve-month window. A colleague needs it, their logs live on `D:\Archive`, and their retention rule is six months. Sending them the file and telling them to edit line four is not a handover; it is a support burden with a delay attached.

You have already met the answer — the `param` block — and the next step up from a parameterised script is a **function**: a named block of code you can call from anywhere in a session, with parameters, which can be reused by the rest of a script without copying anything.

```powershell
function Get-OldFile {
    param(
        [Parameter(Mandatory)] [string]$Path,
        [int]$Months = 12
    )

    Get-ChildItem -Path $Path -File -Recurse |
        Where-Object LastWriteTime -lt (Get-Date).AddMonths(-$Months)
}

Get-OldFile -Path C:\Logs -Months 6 | Measure-Object -Property Length -Sum
```

`[Parameter(Mandatory)]` means the function refuses to run without a path rather than quietly using an empty one, which is the kind of detail that saves you at three in the morning. A file of functions like this saved with a `.psm1` extension is a **module**, and `Import-Module` makes its functions available to a session.

### 24 · `Get-Module` — what's available and what's loaded

```powershell
Get-Module [-ListAvailable] [-Name <string[]>]
Import-Module <name or path>
```

Lists modules, optionally every one installed on the machine rather than only those in use:

```text
PS> Get-Module -ListAvailable |
>>     Where-Object Name -like '*PSReadLine*' |
>>     Select-Object Name, Version, ModuleType

Name        Version ModuleType
----        ------- ----------
PSReadLine  2.3.5   Script
```

Two lists matter and they are different: `Get-Module` alone shows what is loaded in this session, and `-ListAvailable` shows what is installed and could be loaded. If a command from a tutorial does not exist on your machine, this is the first place to look — and the second is the gallery.

### 25 · `Install-Module` — pull one from the gallery

```powershell
Find-Module <name> | Install-Module [-Scope CurrentUser] [-Force] [-AllowClobber]
```

Downloads a module from the PowerShell Gallery and installs it for you or for the machine:

```text
PS> Find-Module -Name Pester | Select-Object Name, Version, Description
Name    Version Description
----    ------- -----------
Pester  5.7.1   Pester provides a framework for running unit tests…

PS> Install-Module -Name Pester -Scope CurrentUser
```

This is the part that makes PowerShell more than a Windows tool. Every major Microsoft product exposes itself as a module that emits objects into this same pipeline: `Az` for Azure, `ExchangeOnlineManagement` for Exchange, `ActiveDirectory` for on-premises directory work, plus VMware, AWS and a long tail of community modules for everything else.

Which means the pipelines you learned in section two are the same pipelines, unchanged, against all of it — `Where-Object`, `Select-Object`, `ForEach-Object`, all of it. Learning this shell is not learning Windows; it is learning the shape that every one of those tools agrees to speak.

<Callout type="info">
`Install-Module` and `Find-Module` come from PowerShellGet. PowerShell 7.4 and later also ship **PSResourceGet**, its successor, where the same work is spelled `Find-PSResource` and `Install-PSResource`. Both are present on a current install, so use whichever your other scripts already use.
</Callout>

## Part 06 — The Shape of It

### The whole language in one idea

Everything in the last twenty-five commands came from two decisions made when the language was designed.

Go back through the lesson and you will find there were really only two things to learn. The first is that **every command name is a verb and a noun**, so the name tells you what it does and `Get-Command` lets you find the family you have not met. The second is that **commands exchange objects, not text**, so the pipe carries structured data that the next command can filter, reorder, reshape or act on.

Everything else followed from those two. Properties came from the second — `Where-Object` needs named data to test. Calculated properties came from the second. `Invoke-RestMethod` handing you parsed JSON instead of a string came from the second. The `Deserialized.` prefix on remote results came from the second. The `-WhatIf` habit came from the first, because a verb that promises to change something also knows how to describe the change without making it.

| What you might have thought you were learning | What was actually going on |
| --- | --- |
| A list of commands to memorise | A naming convention you can search, so you only ever learn nouns and verbs |
| How to cut columns out of text | How to name a property, so the data is never cut at all |
| Windows administration | A pipeline that Azure, Exchange, Active Directory and VMware all feed into |
| A scripting language | An object shell that happens to be scriptable |

The tools change. The model does not. `Get-Process` on your laptop, `Get-Service` on forty servers, `Get-AzVM` against a cloud subscription and `Get-ADUser` against a directory all hand you objects, and the same four commands from section two will narrow, order, act on and summarise any of them. That is the whole reason to spend the time on the pipeline rather than on a longer list of commands.

### What to do tomorrow, in order

Pick one genuinely repetitive thing you do on this machine. Write it as a pipeline until it works in the console — that is where mistakes are cheap. Move it into a `.ps1` file once it works. Add `param` so the paths and thresholds are arguments instead of constants. Put `-WhatIf` on the destructive step and leave it there until you have read the list twice. Then, and only then, decide whether the failure case deserves a `try/catch`.

You can get a surprising amount of real work done with the twenty-five commands in this lesson and the help system. Everything past that — classes, advanced functions, DSC, workflows, the whole surface of Azure — is built out of the same two ideas, which you now have.

## Appendix B — Vocabulary

Every term this lesson leaned on, defined once so you can look it up without re-reading a chapter.

| Term | What it means |
| --- | --- |
| `shell` | A program where you type instructions as text and it answers. PowerShell is one |
| `terminal` | The window a shell runs inside. Windows Terminal can host PowerShell, cmd, and WSL |
| `prompt` | The text showing which shell you are in and where you are standing, waiting for input |
| `cmdlet` | A built-in PowerShell command, named Verb-Noun, like `Get-Process` |
| `verb` / `noun` | The two halves of a command name: what happens, and what it happens to |
| `parameter` | A named input to a command, written with a leading dash: `-Path`, `-Recurse` |
| `switch` | A parameter with no value that is either present or absent, like `-Recurse` |
| `alias` | A short alternative name for a command. `dir` is an alias for `Get-ChildItem` |
| `pipeline` | The chain of commands joined by `\|`, where each receives the objects the previous one produced |
| `object` | A structured thing with named data and behaviour, which is what every command hands over |
| `property` | One named piece of data on an object: `Id`, `Name`, `LastWriteTime` |
| `method` | An action an object can perform: `$process.Kill()` |
| `type` | The kind of object — `System.Diagnostics.Process` — shown by `Get-Member` |
| `provider` | An adapter that exposes a store through the usual commands: files, registry, certificates, environment |
| `PSDrive` | A named place you can navigate to, such as `C:`, `Env:` or `HKLM:` |
| `variable` | A named value, written with a leading `$`: `$cutoff = (Get-Date).AddYears(-1)` |
| `array` | An ordered list of values: `@('one','two')` or `1..5` |
| `hashtable` | Named pairs, written `@{ Name = 'value' }` — used for calculated properties and parameters |
| `script block` | Code in braces that can be passed around and run later, once per object in the pipeline |
| `$_` | Inside a pipeline block, the object currently being handled. Longer name: `$PSItem` |
| `subexpression` | `$( … )` — work out this part first, then use the result inside a string |
| `expansion` | Substituting a variable's value into a string, which happens in double quotes and not in single quotes |
| `execution policy` | The per-scope rule deciding whether scripts may run. A guard rail, not a security boundary |
| `profile` | The script that runs at the start of every session — where aliases and functions live permanently |
| `module` | A package of commands, loaded with `Import-Module`. How everything beyond the core is delivered |
| `PSGallery` | Microsoft's public module repository, reached with `Find-Module` and `Install-Module` |
| `remoting` | Running commands on another machine over WinRM or SSH, usually via `Invoke-Command` |
| `deserialized` | What remote results are: the properties crossed the network, the methods could not |
| `non-terminating error` | An error that is reported and then execution continues — the default for most cmdlets |
| `terminating error` | An error that stops the statement, and the only kind `try`/`catch` will catch unless you add `-ErrorAction Stop` |
| `$LASTEXITCODE` | The exit code of the last ordinary program you ran, like `git` or `robocopy` — separate from PowerShell errors |
| `-WhatIf` | Runs a changing command and prints what it *would* do, without doing it. The habit worth forming |
| `wildcard` | The `*` and `?` patterns used by `-Name`, `-Filter` and `-like`. `-match` uses regular expressions instead |
