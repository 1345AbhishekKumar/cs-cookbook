# Every term, recall-first.

Try to define each term from memory, then check yourself. This table is the lesson's canonical vocabulary.

## Canonical cheat sheet

| Term | Definition |
| --- | --- |
| commit | A set of changes tied to an author, time, and message — a full snapshot of the repo. |
| porcelain / plumbing | High-level daily commands (status, add, commit) vs low-level object tools (cat-file, hash-object). |
| config scopes | worktree → local (.git/config) → global (home dir) → system; most specific wins. |
| repository / .git | A project folder plus the hidden .git directory that holds the entire repo state. |
| file states | untracked (invisible to git, unsafe to delete) → staged (in the index) → committed (in history). |
| index / staging area | The list of exactly what the next commit will contain; built with git add. |
| hash (SHA-1) | Fingerprint of a commit's content + author + time + message + parent; deterministic, practically unique. |
| commit / tree / blob | Snapshot object / directory listing object / file-content object, stored compressed in .git/objects. |
| snapshot model | Each commit references a full tree; unchanged files keep the same blob hash, stored once. |
| branch | A mutable pointer (a file with a hash) to the tip commit of a line of work. |
| merge base | The nearest common ancestor of two branches; where merges and rebases start. |
| merge commit | The only commit with two parents; created when branches have diverged. |
| fast-forward | When the target's tip IS the merge base: the pointer slides forward, no new commit. |
| rebase | Check out the target, replay your commits onto its tip (new hashes), move your pointer. Never on public branches. |
| reset --soft / --hard | Rewind the branch keeping staged+worktree changes vs wiping both; untracked files always survive. |
| remote / origin / upstream | Another repo; origin = your authoritative push target; upstream = the original in a fork workflow. |
| fetch / pull / push | Download to origin/* / fetch + integrate (per pull.rebase) / upload one branch's commits. |
| pull request | GitHub's proposal to merge one branch into another; git itself doesn't know PRs exist. |
| fork | A copy of a repo in your GitHub account so you can push and open PRs; not a git command. |
| .gitignore | Pattern file of what git shouldn't track; / anchors, * wildcards, ! negates; .git/info/exclude for personal ones. |
| reflog | Journal of every HEAD movement — the safety net that recovers reset, rebase, and deleted-branch work. |
| merge conflict | Two non-parent commits modify the same line; git marks ours/theirs and asks you to decide. |
| ours / theirs | Merge: your branch vs incoming. Rebase: flipped — ours = target branch, because HEAD moves there first. |
| rerere | Reuse Recorded Resolution: replays your earlier fix for identical conflict hunks; opt-in. |
| squash | Melt several commits into one via git rebase -i; content identical, markers gone, needs force-push. |
| stash | LIFO stack of staged+unstaged changes; pop returns newest. Temporary parking, not storage. |
| revert | New commit applying the inverse of an old one — the safe undo for shared history. |
| cherry-pick | Copy one commit onto your current branch; same change, new hash. |
| bisect | Binary search over history between a good and bad commit to find the culprit; run automates testing. |
| worktree | Extra working folder sharing one .git; one branch per tree; prune cleans dead ones. |
| tag | Immutable pointer to a commit, used for releases; semver = major.minor.patch. |

# The questions everyone asks.

### Why do my hashes differ from the video's if we did everything the same?

The hash mixes in the author, timestamp, message, and parent commit — not just file content. Your clock and identity differ, so your SHA differs, even with byte-identical repos. A true collision needs every input identical. *Takeaway: content doesn't uniquely decide a hash — the whole moment does.*

### If commits store full snapshots, why isn't my repo gigantic?

Because blobs are content-addressed: unchanged files keep the same hash, so every commit just re-points at the existing object instead of storing a copy. Git also compresses objects and packs them for efficiency. *Takeaway: snapshots + deduplication by hash = full history at a fraction of the size.*

### Rebase or merge — which one should I use?

They solve the same integration differently: merge preserves true history with two-parent commits; rebase rewrites your branch into a straight line. The presenter's rule: always rebase your own local branch, fast-forward merge into main, never rebase a public branch. And accept that any policy you pick, someone will complain. *Takeaway: rebase private, merge public.*

### Why are ours and theirs backwards during a rebase?

Because rebase checks out the target branch first and then replays your commits onto it. During the conflict, HEAD sits on the target — so "ours" is main and "theirs" is your feature commit. It feels inverted but it's mechanically consistent. *Takeaway: anchor ours/theirs to "where HEAD is," not to "my work."*

### I ran git reset --hard with uncommitted work. Is it gone?

Tracked, uncommitted changes: effectively yes — the working tree was wiped. But commits themselves are recoverable through reflog, which journals every HEAD move; find the hash and cherry-pick or branch from it. Untracked files were never touched. *Takeaway: reflog is the reason "destroyed" work usually isn't.*

### Why commit early and often if I'm just going to squash?

Frequent commits are checkpoints — if something breaks badly, you roll back to the last known-good state instead of redoing hours of work. Before opening the PR, interactive rebase squashes them into the one commit your team wants. *Takeaway: commit often for safety, squash for storytelling.*

### When is stash the wrong tool?

When the work needs to outlive this session. Stash is a temporary LIFO tray; if you're labeling stashes or coming back next week, commit to a branch instead — you can rebase, edit, and push it, and it's far harder to lose. Or skip the juggling entirely with a second worktree. *Takeaway: minutes = stash; days = branch.*

### Do I need forks and PRs when I work alone?

No — the presenter skips both for solo projects: add, commit, push. Forks exist so people without write access can contribute; PRs exist so teams can review. Process for process's sake is red tape. *Takeaway: scale the ceremony to the team size.*

### What's the fastest way to find which commit broke the build?

git bisect. Mark the current commit bad, a known-good older one good, and answer good/bad as git walks the middle — each answer halves the search space, so thousands of commits take ~a dozen checks. bisect run even automates the answers with a test script. *Takeaway: sorted history is searchable — never linear-scan a regression.*

### Why does everyone dread merge conflicts if they're just markers in a file?

Because most people meet them mid-emergency without understanding the mechanics. A conflict is git honestly saying "two branches changed the same line and I won't guess." Read the ours/theirs blocks, keep what's right (both is allowed), add, and commit — or abort cleanly. *Takeaway: a conflict is a question, not an error.*

# Apply it

Three moves before you forget.

1. **Walk the object chain yourself.** In any repo: commit a file, then `git cat-file -p` the commit hash, cat the tree, cat the blob. Ten minutes of plumbing permanently demystifies git.
2. **Rehearse the recovery.** In a throwaway repo: commit, reset --hard, find the work via `git reflog`, cherry-pick it back. Practice makes the scary command boring.
3. **Run the team loop once.** Branch, three commits, `rebase -i` squash to one, push, open a PR against your own repo, merge. The whole workflow in twenty minutes.
4. **Real-world practice:** explain snapshot-vs-diff to a teammate using the [two-commits-one-blob diagram](/docs/developer-tools/git/01-foundations#module-10--foundations-git-stores-snapshots-not-diffs) — teaching it is the fastest way to own it.
