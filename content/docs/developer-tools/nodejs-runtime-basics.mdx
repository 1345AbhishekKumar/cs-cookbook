## Why do we need Node.js?

For a long time, **JavaScript lived exclusively inside web browsers**. You used it to animate dropdown menus, validate forms, and react to button clicks.

The only problem: **browsers cannot run server-side code or access your computer's files**. A browser cannot read a file from your hard drive, connect directly to a database, or listen for incoming web requests from around the world.

To build a full web application, developers had to write their frontend in JavaScript, but their backend in a completely different language — like Python, PHP, Java, or Ruby.

In 2009, Ryan Dahl created **Node.js**. Node took JavaScript out of the browser and gave it the power to run directly on your computer and on web servers. Now, developers can use a single language — JavaScript — across the entire stack.

<Callout type="info">
  **The big picture** Browser JavaScript brings web pages to life on a user's
  screen. Node.js runs JavaScript on your computer or server to build APIs,
  tools, and full backend services.
</Callout>

## What is Node.js?

**Node.js is not a programming language, and it is not a framework.**

It is an open-source **JavaScript runtime environment**. A "runtime" is simply the environment and engine that allows your computer to execute a program.

### The kitchen analogy

Imagine you are running a busy restaurant:

```
┌─────────────────────────────────────────────────────────────┐
│                       THE RESTAURANT                        │
│                                                             │
│   [ You ]  ────►  [ V8 Engine ]  ────►  [ libuv ]  ──────► [ OS ]
│  Writes JS        Translates JS         Takes orders &     Kitchen
│   recipes         to machine code       manages chefs      does work
└─────────────────────────────────────────────────────────────┘
```

1. **Your JavaScript code** is the recipe you write.
2. **The V8 Engine** (created by Google for Chrome) is the master chef who reads your recipe and translates it into ultra-fast machine instructions.
3. **libuv** (a C library) is the kitchen manager. When a task takes time (like baking bread or reading a file), libuv delegates it to background workers so the master chef never stops taking new orders.
4. **Node.js** is the entire restaurant packaging these pieces together with built-in tools for files, networks, and operating systems.

### Browser vs. Node.js

Both environments speak the same JavaScript language, but they have access to completely different tools:

| Feature                | Browser JavaScript                | Node.js                               |
| ---------------------- | --------------------------------- | ------------------------------------- |
| **Where it runs**      | Inside Chrome, Firefox, Safari    | On your computer or server terminal   |
| **Global object**      | `window`, `document`              | `global`, `process`                   |
| **User interface**     | Yes — HTML elements, buttons, CSS | No — output prints to the terminal    |
| **DOM manipulation**   | Yes (`document.getElementById`)   | ❌ No DOM exists                      |
| **File system access** | ❌ Blocked for security           | Yes (`node:fs` can read/write files)  |
| **Listen on ports**    | ❌ Cannot serve web traffic       | Yes (`node:http` creates web servers) |

## Running JavaScript with Node.js

To run Node.js on your computer, check that it is installed:

```bash
node -v
```

This should print your installed version, for example `v20.18.0`.

### 1. The interactive REPL

If you type `node` without any file name, you open the **REPL** (_Read-Eval-Print Loop_). You can test JavaScript expressions instantly:

```bash
node
```

```javascript
> 1 + 2
3
> const greeting = "Hello, Node!";
undefined
> greeting.toUpperCase()
'HELLO, NODE!'
> .exit
```

_(Type `.exit` or press `Ctrl + C` twice to exit the REPL)._

### 2. Running a script file

Create a file named `app.js`:

```javascript
// app.js
const user = "Alex";
console.log(`Welcome back, ${user}! Running on Node.js ${process.version}`);
```

Run it in your terminal:

```bash
node app.js
```

Output:

```bash
Welcome back, Alex! Running on Node.js v20.18.0
```

### 3. Automatic restart with `--watch`

In older versions of Node, developers had to install third-party tools like `nodemon` to restart their server when code changed. Modern Node.js (Node 18.11+) has this built right in:

```bash
node --watch app.js
```

Whenever you save `app.js`, Node automatically reloads it for you!

<Callout type="tip">
  **Loading `.env` files automatically** Starting in Node 20.6+, you can load
  environment variables directly from a `.env` file without installing external
  packages: ```bash node --env-file=.env app.js ```
</Callout>

## The blocking problem & asynchronous I/O

Why did Node.js become so popular for servers? Because of how it handles **waiting**.

### The traditional server (blocking)

In traditional web servers, each user request was often handled by a dedicated thread. If a user asked to read a large file or query a slow database, that thread stopped and waited:

```javascript
// ❌ Blocking: everything freezes until the file is completely read
import fs from "node:fs";

console.log("1. Starting to read file...");
const data = fs.readFileSync("large-database-dump.txt", "utf8");
console.log("2. Finished reading file!");
console.log("3. Ready to help the next user!");
```

While line 5 is reading from the hard drive, **the entire program freezes**. User 2, User 3, and User 100 have to wait in line. Creating more threads can help, but threads take up memory and are expensive for a server to maintain.

### The Node.js way (non-blocking)

Node.js is **single-threaded** for executing JavaScript, but it handles operations **asynchronously**:

```javascript
// ✅ Non-blocking: Node starts the task, moves on, and calls you back when ready
import fs from "node:fs/promises";

console.log("1. Starting to read file...");

fs.readFile("large-database-dump.txt", "utf8").then(() =>
  console.log("2. Finished reading file!")
);

console.log("3. Ready to help the next user immediately!");
```

Look at the console output:

```bash
1. Starting to read file...
3. Ready to help the next user immediately!
2. Finished reading file!
```

Node handed the file-reading job to the operating system in the background, immediately printed step 3, and only printed step 2 when the file finished loading.

<Callout type="warn">
  **Rule #1 of Node.js: Never block the main thread!** Because all your
  JavaScript runs on a single thread, running slow synchronous code (like
  `fs.readFileSync` or an infinite `while` loop) freezes the server for every
  single visitor. Always prefer asynchronous functions!
</Callout>

## The Event Loop made simple

How does Node.js know when background tasks finish? Through the **Event Loop**.

Think of the Event Loop as a polite manager running in an infinite circle, constantly checking different to-do lists:

```
   ┌──────────────────────────────────────────────┐
   │                                              │
   ▼                                              │
1. Timers (setTimeout, setInterval)               │
   │                                              │
   ▼                                              │
2. I/O Callbacks (reading files, network data)    │
   │                                              │
   ▼                                              │
3. Check Phase (setImmediate callbacks)           │
   │                                              │
   ▼                                              │
4. Close Callbacks (closing files, sockets)       │
   │                                              │
   └──────────────────────────────────────────────┘
```

1. **Timers Phase:** Checks if any `setTimeout()` or `setInterval()` timers have reached their countdown. If so, it runs their callbacks.
2. **I/O Phase:** Checks if any background operations (like reading a file from your SSD or waiting for a database response) have finished.
3. **Check Phase:** Runs callbacks scheduled with `setImmediate()`.
4. **Close Phase:** Cleans up closed connections (like closed database sockets).

### The VIP express lane: Microtasks

Before moving from one phase to the next, the event loop always clears the **Microtask queue**:

- **`process.nextTick()`** (runs first)
- **`Promise` callbacks** (`.then()`, `await`)

They get VIP priority and run immediately before the event loop continues to regular timers or file I/O.

### Seeing it in action

```javascript
// loop-demo.js
console.log("1. Synchronous log");

setTimeout(() => {
  console.log("4. Timer (setTimeout)");
}, 0);

Promise.resolve().then(() => {
  console.log("3. Microtask (Promise)");
});

process.nextTick(() => {
  console.log("2. Microtask (nextTick)");
});

console.log("Line finished!");
```

Output:

```bash
1. Synchronous log
Line finished!
2. Microtask (nextTick)
3. Microtask (Promise)
4. Timer (setTimeout)
```

**Why this order?**

1. All synchronous lines run first (`1. Synchronous log` and `Line finished!`).
2. Next, the VIP microtasks drain (`nextTick` first, then `Promise`).
3. Finally, the event loop picks up the timer in the timers phase.

## Modules: CommonJS vs. ES Modules

In modern development, code is split into multiple files called **modules**. Node.js supports two module systems:

1. **CommonJS (CJS):** The original system created for Node back in 2009. Uses `require()` and `module.exports`.
2. **ES Modules (ESM):** The official standard for all JavaScript (both browser and Node). Uses `import` and `export`.

### Comparison at a glance

| Feature               | CommonJS (CJS)                      | ES Modules (ESM)                                  |
| --------------------- | ----------------------------------- | ------------------------------------------------- |
| **Import syntax**     | `const math = require('./math.js')` | `import math from './math.js'`                    |
| **Export syntax**     | `module.exports = { add }`          | `export function add() {}`                        |
| **Default in Node**   | Default for `.js` files             | Default when `"type": "module"` in `package.json` |
| **File extension**    | `.cjs` or `.js`                     | `.mjs` or `.js` (with module type)                |
| **Directory info**    | `__dirname`, `__filename`           | `import.meta.dirname`, `import.meta.filename`     |
| **Top-level `await`** | ❌ Only inside `async` functions    | ✅ Allowed directly at top of file                |

### 1. CommonJS example

```javascript
// math.js
function add(a, b) {
  return a + b;
}

module.exports = { add };
```

```javascript
// app.js
const { add } = require("./math.js");
console.log(add(5, 3)); // 8
```

### 2. ES Module example (Modern & Recommended)

Add `"type": "module"` to your `package.json`:

```json
{
  "name": "my-node-app",
  "type": "module"
}
```

Now you can write modern standard imports:

```javascript
// math.js
export function add(a, b) {
  return a + b;
}
```

```javascript
// app.js
import { add } from "./math.js";
console.log(add(5, 3)); // 8
```

<Callout type="tip">
  **Recommendation for new projects** Always use **ES Modules** for new code. It
  is the modern JavaScript standard shared by Node, browsers, TypeScript, and
  frameworks like Next.js and Vite.
</Callout>

## Core built-in modules you'll actually use

Node.js comes with a rich standard library. You **do not need to run `npm install`** to use these modules — they are built directly into the runtime.

Always prefix built-in imports with `node:` (e.g., `node:fs` instead of `fs`). This makes it obvious that you're using Node's official tools rather than an npm package:

### 1. `node:fs/promises` (File System)

Read and write files easily with `async/await`:

```javascript
import fs from "node:fs/promises";

// Writing to a file
await fs.writeFile("notes.txt", "Learning Node.js is fun!");

// Reading from a file
const content = await fs.readFile("notes.txt", "utf8");
console.log(content); // Learning Node.js is fun!

// Creating a folder safely
await fs.mkdir("backups", { recursive: true });
```

### 2. `node:path` (Working with File Paths)

Windows uses backslashes (`\`) for folders, while macOS and Linux use forward slashes (`/`). `node:path` handles this for you so your code works on any computer:

```javascript
import path from "node:path";

// Safely combine directory names
const filePath = path.join(import.meta.dirname, "data", "users.json");
console.log(filePath);

// Extract the file name and extension
console.log(path.basename(filePath)); // users.json
console.log(path.extname(filePath)); // .json
```

### 3. `node:process` (Environment & Terminal Info)

The `process` object gives you information about the running program:

```javascript
// 1. Reading environment variables
const port = process.env.PORT || 3000;
console.log(`Server will run on port: ${port}`);

// 2. Reading command-line arguments (e.g., node app.js --env=production)
const args = process.argv.slice(2);
console.log("Passed arguments:", args);

// 3. Exiting gracefully with an error code
if (!process.env.DATABASE_URL) {
  console.error("Missing database URL!");
  process.exitCode = 1; // 1 signals an error to the operating system
}
```

## The EventEmitter pattern

Much of Node.js is built around events. Think of an **EventEmitter** like subscribing to a YouTube channel:

1. You click "Subscribe" (`.on('upload', callback)`).
2. When a new video drops, the creator emits an event (`.emit('upload', video)`).
3. Your callback runs automatically!

```javascript
import { EventEmitter } from "node:events";

const orderEmitter = new EventEmitter();

// 1. Listen for the 'orderPlaced' event
orderEmitter.on("orderPlaced", (orderId, customer) => {
  console.log(
    `📦 Sending confirmation email to ${customer} for order #${orderId}`
  );
});

orderEmitter.on("orderPlaced", (orderId) => {
  console.log(`🧾 Printing invoice for order #${orderId}`);
});

// 2. Trigger the event
orderEmitter.emit("orderPlaced", 101, "Alex");
```

Output:

```bash
📦 Sending confirmation email to Alex for order #101
🧾 Printing invoice for order #101
```

HTTP servers, file streams, and WebSockets in Node.js are all built on top of this exact pattern.

## Buffers & Streams: Working with data

When dealing with files, images, or network downloads, you encounter two key Node concepts: **Buffers** and **Streams**.

### What is a Buffer?

Computers store everything in binary: sequences of bytes (`0`s and `1`s). While JavaScript strings are made for human-readable text, a **Buffer** is a container for raw binary data (like an image file, an audio clip, or an encrypted packet):

```javascript
import { Buffer } from "node:buffer";

// Convert a string to raw bytes
const buf = Buffer.from("Hello");
console.log(buf);
// Output: <Buffer 48 65 6c 6c 6f> (hexadecimal representation of bytes)

// Convert bytes back to a string
console.log(buf.toString("utf8")); // Hello
```

### What is a Stream? (The water pipe analogy)

Imagine you want to move water from a lake into your house:

- **Without streams (`readFile`):** You try to carry the entire lake in one giant bucket. If the file is 4 GB, Node tries to load all 4 GB into your computer's RAM at once. Your app runs out of memory and crashes.
- **With streams:** You lay a garden hose. Water flows continuously, one small sip (chunk) at a time. Your memory usage stays tiny, no matter how huge the file is!

```
[ Big File: 2 GB ] ──(chunk 64KB)──► [ Water Pipe ] ──(chunk 64KB)──► [ Destination File ]
Memory used: only ~64KB at any given moment!
```

### Copying a file using a modern stream pipeline

```javascript
import fs from "node:fs";
import { pipeline } from "node:stream/promises";

// Efficiently stream data from source to destination
await pipeline(
  fs.createReadStream("large-video.mp4"),
  fs.createWriteStream("copy-video.mp4")
);

console.log("Video copied smoothly without maxing out RAM!");
```

## Building your first web server

You don't need any external packages to build a web server. Node includes the built-in `node:http` module:

```javascript
// server.js
import http from "node:http";

const server = http.createServer((req, res) => {
  // Check the URL requested by the browser
  if (req.url === "/api/user") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify({ name: "Alex", role: "Developer" }));
    return;
  }

  // Default response
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from your first Node.js server!\n");
});

// Start listening for connections on port 3000
server.listen(3000, () => {
  console.log("Server is running at http://localhost:3000");
});
```

### Running and testing it

1. Start your server:
   ```bash
   node --watch server.js
   ```
2. Open your browser and visit:
   - `http://localhost:3000` → Displays `Hello from your first Node.js server!`
   - `http://localhost:3000/api/user` → Returns `{"name":"Alex","role":"Developer"}`

<Callout type="info">
  **Frameworks in the real world** `node:http` is the low-level foundation that
  powers every Node web framework. In real-world projects, developers usually
  use frameworks like **Express**, **Fastify**, or **Hono** to get built-in
  routing, authentication, and cookie handling.
</Callout>

## When to use Node.js (and when not to)

Like any tool, Node.js has tasks it excels at, and tasks where other tools are better suited.

### Where Node.js shines 🌟

- **Web APIs & Microservices:** Fast at receiving requests, querying databases, and sending JSON responses.
- **Real-Time Applications:** Chat apps, live notifications, and multiplayer games using WebSockets.
- **Frontend Build Tools:** Vite, Next.js, ESLint, Prettier, and Tailwind CSS all run on Node.js.
- **I/O-Intensive Apps:** Streaming video, audio, or uploading files.

### Where Node.js struggles ⚠️

- **Heavy CPU Calculations:** Video encoding, 3D graphics rendering, or machine learning model training. Because JavaScript is single-threaded, a 30-second math loop would freeze the server for all other users!

### How Node handles heavy work: `worker_threads`

If you _do_ need to run heavy CPU computations in Node, you can use the built-in `worker_threads` module to spin up a background worker thread without blocking the main event loop.

## Common gotchas for beginners

### 1. `__dirname` is not defined in ES Modules

In CommonJS, `__dirname` gave you the folder path. In ES Modules, use `import.meta.dirname`:

```javascript
// ❌ CommonJS legacy (throws error in ESM):
console.log(__dirname);

// ✅ Modern ES Modules (Node 20.11+):
console.log(import.meta.dirname);
console.log(import.meta.filename);
```

### 2. Forgetting the file extension in ESM

In CommonJS, you could omit `.js`: `require('./utils')`. In modern ES Modules, **you must include the file extension**:

```javascript
// ❌ Error: Cannot find module
import { formatDate } from "./utils";

// ✅ Correct:
import { formatDate } from "./utils.js";
```

### 3. Accidentally using synchronous functions in servers

Never use functions ending in `Sync` (like `fs.readFileSync`) inside web server request handlers. It forces every incoming user to wait until that single file operation finishes. Always use `await fs.readFile()`.

### Key takeaways

- **Node.js is a runtime**, not a language. It lets you run JavaScript outside the browser.
- **V8** compiles JavaScript fast; **libuv** handles async tasks in the background.
- JavaScript in Node is **single-threaded**, but uses **non-blocking I/O** so it never has to sit idle waiting for files or networks.
- The **Event Loop** is the engine coordinating timers, I/O callbacks, and promises.
- **ES Modules** (`import` / `export`) are the modern standard for writing modular JavaScript.
- Node includes powerful built-in tools (`node:fs`, `node:path`, `node:http`) that don't require any third-party npm packages.
- Use `node --watch` during development to automatically reload your code when files change.
