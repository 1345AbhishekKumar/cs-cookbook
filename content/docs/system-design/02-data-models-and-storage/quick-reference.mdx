## 1. Storage Engine Architecture Comparison Matrix

| Feature / Metric | Append-Only Log + Bitcask | Classic B-Tree | LSM-Tree (Log-Structured Merge) | Column-Oriented (OLAP) |
| :--- | :--- | :--- | :--- | :--- |
| **Primary Data Structure** | Sequential log file + In-memory Hash Map | Hierarchical page tree ($4\text{ KB}$ pages, branching factor $\sim 500$) | In-memory MemTable (SkipList) + On-disk SSTables | Columnar vector files + Sparse min/max index |
| **Point Write Speed** | **$O(1)$** (Append to file, update RAM offset) | **$O(\log N)$** (WAL append + In-place page rewrite) | **$O(1)$** (WAL append + MemTable insert) | Batch write only (Appends to column parts) |
| **Point Read Speed** | **$O(1)$** (1 random disk seek) | **$O(\log N)$** ($1$–$2$ disk seeks with RAM page cache) | **$O(\log N)$** (MemTable $\rightarrow$ SSTables, gated by Bloom filters) | Slow for point reads (Must assemble row from 20 columns) |
| **Range Queries** | **Unsupported** (Hash map has no sort order) | **Exceptional** (Leaf pages are linked sequentially) | **Good** (Merge-iterators across sorted SSTables) | **Exceptional for aggregations** over few columns |
| **Write Amplification** | Low (Compaction of obsolete segments only) | **High** (Writing 20-byte change rewrites full 4KB page + WAL) | **Moderate to High** (Repeated merges across levels) | Low for batches; very high for single-row writes |
| **Storage Overhead** | Moderate (Append bloat until compaction) | **High** (Fragmentation, $50\%$–$70\%$ page fill factor) | **Very Low** (Contiguous compressed SSTables, no holes) | **Extremely Low** (RLE, Bitmaps, Vector compression) |
| **Concurrency Model** | Single writer append lock; multi-reader concurrent | Page latches / Lock manager (Two-Phase Locking) | Non-blocking MemTable CAS; background compaction | Read-only columnar chunks; immutable chunk merges |
| **Worst-Case Bottleneck** | Exhaustion of RAM (All keys must fit in memory) | Page split latches, random disk I/O under high write load | **Compaction stalls** under sustained write spikes | Updating or deleting individual rows |
| **Prominent Systems** | Riak (Bitcask engine) | PostgreSQL, MySQL (InnoDB), SQLite, Oracle | RocksDB, LevelDB, Cassandra, ScyllaDB | ClickHouse, Snowflake, Google BigQuery, Parquet |

## 2. Serialization & Schema Evolution Cheat Sheet

| Capability / Rule | JSON / XML | Protocol Buffers (v3) | Apache Thrift | Apache Avro |
| :--- | :--- | :--- | :--- | :--- |
| **Schema Definition** | Optional (JSON Schema) | Mandatory (`.proto` file) | Mandatory (`.thrift` file) | Mandatory (JSON-based schema) |
| **Field Identity on Wire** | String field name in every row | Numeric **Field Tag** ($1, 2, 3\dots$) | Numeric **Field Tag** | None (Matched by name via schema resolution) |
| **Wire Overhead** | High (Field strings repeated) | Very Low (1-byte tag header + varints) | Very Low (Numeric tags + varints) | **Minimal possible** (Raw values only) |
| **Adding a Field** | Add key; old code handles missing key | Allowed: must assign a **new unique tag**; field is optional | Allowed: assign new tag; field must be optional | Allowed: new field **must declare a default value** |
| **Removing a Field** | Remove key; handle gracefully | Allowed: **never reuse tag**; mark tag as `reserved` | Allowed: never reuse tag number | Allowed: removed field **must have had a default value** |
| **Renaming a Field** | Breaks readers looking for old key | **Safe** (Wire format uses tag numbers, not names!) | **Safe** (Wire format uses tag numbers, not names!) | Supported via schema `aliases` attribute |
| **Changing Field Type** | Risky (Type coercion bugs) | Risky (Only compatible wire types like `int32` to `int64`) | Risky (Type truncation or decoding crash) | Supported if type promotion rules apply (e.g., `int` to `long`) |
| **Primary Use Cases** | Public REST APIs, browser frontends | Internal microservice RPCs (gRPC) | Cross-language internal RPC | Kafka event streams, Hadoop, big data file formats |

## 3. Latency Numbers Every Systems Engineer Must Know

Published by Dr. Jeff Dean (Google Fellow & Senior VP of Research), these numbers govern every architectural choice in distributed systems:

| Hardware Operation | Actual Latency (approx.) | Human-Scale Equivalent (Scaled: $1\text{ CPU Cycle} = 1\text{ second}$) |
| :--- | :--- | :--- |
| **L1 CPU Cache Reference** | $0.5\text{ ns}$ | $1\text{ second}$ |
| **Branch Mispredict** | $5\text{ ns}$ | $10\text{ seconds}$ |
| **L2 CPU Cache Reference** | $7\text{ ns}$ | $14\text{ seconds}$ |
| **Mutex Lock / Unlock** | $25\text{ ns}$ | $50\text{ seconds}$ |
| **Main Memory Reference (DRAM)** | $100\text{ ns}$ | **$3.3\text{ minutes}$** |
| **Compress 1 KB with Snappy** | $2,000\text{ ns} = 2\ \mu\text{s}$ | $1.1\text{ hours}$ |
| **Send 2 KB over 1 Gbps Network** | $20,000\text{ ns} = 20\ \mu\text{s}$ | $11.1\text{ hours}$ |
| **Read 1 MB Sequentially from RAM** | $250,000\text{ ns} = 250\ \mu\text{s}$ | $5.8\text{ days}$ |
| **NVMe SSD Random Read** | $150,000\text{ ns} = 150\ \mu\text{s}$ | $3.5\text{ days}$ |
| **Read 1 MB Sequentially from SSD** | $1,000,000\text{ ns} = 1\text{ ms}$ | $23.1\text{ days}$ |
| **Datacenter Round-Trip (Same DC)** | $500,000\text{ ns} = 0.5\text{ ms}$ | $11.6\text{ days}$ |
| **Spinning HDD Seek** | $10,000,000\text{ ns} = 10\text{ ms}$ | **$7.7\text{ months}$** |
| **Read 1 MB Sequentially from HDD** | $20,000,000\text{ ns} = 20\text{ ms}$ | $1.3\text{ years}$ |
| **Cross-Continent WAN (SF to NYC)** | $65,000,000\text{ ns} = 65\text{ ms}$ | **$4.1\text{ years}$** |
| **Transatlantic Cable (NYC to London)** | $150,000,000\text{ ns} = 150\text{ ms}$ | **$9.5\text{ years}$** |

<Callout type="info" title="The Architect's Intuition">
Notice the staggering cliff between memory ($100\text{ ns}$) and network WAN ($100\text{ ms}$): a factor of **one million**!
If your code makes 10 unbatched sequential network calls inside a loop, you are forcing your user to wait for what feels like 40 human years of physical compute relative to the CPU clock.
</Callout>

## 5. Tail Latency Amplification Formula

For a request that fans out in parallel to $N$ independent backend microservices, where each microservice has a $p99$ response time threshold (meaning each has a failure/tail probability $p = 0.01$):

$$P(\text{At least one backend exceeds } p99) = 1 - (1 - p)^N$$

| Number of Fan-Out Calls ($N$) | Individual Tail Probability ($p$) | Chance End-User Hits Tail Latency |
| :--- | :--- | :--- |
| **1 call** | $1\%$ | $1.0\%$ |
| **10 calls** | $1\%$ | $9.56\%$ |
| **50 calls** | $1\%$ | $39.5\%$ |
| **100 calls** | $1\%$ | **$63.4\%$** |
| **200 calls** | $1\%$ | **$86.6\%$** |

<Callout type="warn" title="Tail-Tolerance Pattern">
In high fan-out systems (like TravelBuddy searching 50 airline partner APIs), **always use Hedged Requests**: if a downstream call has not responded within its $p95$ threshold, dispatch an identical duplicate request to a backup replica and take whichever response returns first.
</Callout>
