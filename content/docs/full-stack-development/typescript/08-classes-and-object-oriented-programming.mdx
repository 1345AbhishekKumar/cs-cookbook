TypeScript enhances ES6 JavaScript classes with static type-checking, access control modifiers, abstract classes, and interface contracts. While much of modern TypeScript is functional, classes remain central to backend design patterns (NestJS, TypeORM, Prisma repositories, and DDD).

## 1. Class Declarations & Parameter Properties

In traditional JavaScript, fields must be declared and assigned inside the constructor body. TypeScript offers a concise shorthand called **parameter properties**:

```typescript
// Traditional declaration
class StandardUser {
  public id: string;
  public email: string;

  constructor(id: string, email: string) {
    this.id = id;
    this.email = email;
  }
}

// Modern TypeScript Shorthand: Parameter Properties
class CompactUser {
  constructor(
    public readonly id: string,
    public email: string,
    private passwordHash: string
  ) {
    // TypeScript automatically creates and assigns this.id, this.email, and this.passwordHash
  }
}

const user = new CompactUser("usr_123", "alex@example.com", "hash_abc");
console.log(user.email); // "alex@example.com"
// console.log(user.passwordHash); // Error: Property 'passwordHash' is private.
```

## 2. Access Modifiers: `public`, `private`, `protected`, `readonly`

TypeScript provides three visibility modifiers and the `readonly` immutability modifier:

| Modifier | Accessible Inside Class | Accessible in Subclasses | Accessible Outside Instance | Runtime Enforcement |
|---|---|---|---|---|
| `public` (default) | Yes | Yes | Yes | None (visible in JS) |
| `protected` | Yes | Yes | No | Compile-time only |
| `private` | Yes | No | No | Compile-time only |
| `#privateField` (ES2022) | Yes | No | No | **Hard runtime privacy** (JS engine enforced) |
| `readonly` | Read only after construction | Read only | Read only | Compile-time only |

```typescript
class Account {
  public readonly accountNumber: string;
  protected balance: number;
  private internalAuditKey: string;
  #strictPin: string; // Native JavaScript private field

  constructor(accountNumber: string, initialBalance: number, pin: string) {
    this.accountNumber = accountNumber;
    this.balance = initialBalance;
    this.internalAuditKey = "audit_key_secret";
    this.#strictPin = pin;
  }

  public verifyPin(pin: string): boolean {
    return this.#strictPin === pin;
  }
}

class SavingsAccount extends Account {
  public addInterest(rate: number): void {
    // Accessible because 'balance' is protected:
    this.balance += this.balance * rate;

    // Error: 'internalAuditKey' is private to Account:
    // console.log(this.internalAuditKey);
  }
}
```

<Callout type="warning" title="TypeScript private vs Native #private">
TypeScript's `private` keyword is purely a compile-time check. After compilation to JavaScript, the property is still accessible at runtime via `account["internalAuditKey"]`. If you need strict runtime privacy (e.g. crypto keys, auth tokens), use native ECMAScript `#field` syntax.
</Callout>

## 3. Getters, Setters & Static Members

### Getters and Setters
Getters and setters intercept reads and writes to an object property, enabling validation or calculated values:

```typescript
class Temperature {
  private _celsius: number = 0;

  get celsius(): number {
    return this._celsius;
  }

  set celsius(value: number) {
    if (value < -273.15) {
      throw new RangeError("Temperature cannot be below absolute zero (-273.15°C).");
    }
    this._celsius = value;
  }

  // Computed getter (read-only)
  get fahrenheit(): number {
    return (this._celsius * 9) / 5 + 32;
  }
}

const temp = new Temperature();
temp.celsius = 25;
console.log(temp.fahrenheit); // 77
```

### Static Members
Static members belong to the class constructor function itself rather than instances of the class:

```typescript
class DatabaseConnection {
  private static instanceCount: number = 0;
  public static readonly DEFAULT_PORT = 5432;

  constructor() {
    DatabaseConnection.instanceCount++;
  }

  public static getActiveCount(): number {
    return DatabaseConnection.instanceCount;
  }
}

console.log(DatabaseConnection.DEFAULT_PORT); // 5432
new DatabaseConnection();
new DatabaseConnection();
console.log(DatabaseConnection.getActiveCount()); // 2
```

## 4. Inheritance & Method Overrides

Subclasses extend parent classes using `extends` and call the parent constructor with `super()`:

```typescript
class PaymentMethod {
  constructor(public readonly currency: string) {}

  public process(amount: number): boolean {
    console.log(`Processing generic payment of ${amount} ${this.currency}`);
    return true;
  }
}

class CreditCardPayment extends PaymentMethod {
  constructor(
    currency: string,
    public readonly cardNumber: string
  ) {
    super(currency); // Must call super before using 'this'
  }

  // The 'override' keyword ensures this method actually overrides a parent method:
  public override process(amount: number): boolean {
    console.log(`Charging ${amount} ${this.currency} to card ending in ${this.cardNumber.slice(-4)}`);
    return true;
  }
}
```

<Callout type="tip" title="Safety with noImplicitOverride">
Always enable `"noImplicitOverride": true` in your `tsconfig.json`. This forces you to add the `override` keyword when replacing parent methods, preventing silent bugs if the parent method is later renamed.
</Callout>

## 5. `abstract` Classes vs. `interface` Contracts

One of the most important architectural decisions in TypeScript is choosing between `abstract` classes and `interface` contracts:

<Tabs items={['Abstract Class (Template Pattern)', 'Interface (Pure Contract)']}>
  <Tab value="Abstract Class (Template Pattern)">
    An `abstract` class cannot be instantiated directly. It can contain both implemented methods (shared behavior) and `abstract` method signatures that subclasses must fulfill:

    ```typescript
    abstract class BaseRepository<T> {
      constructor(protected readonly tableName: string) {}

      // Shared concrete implementation:
      public getTableName(): string {
        return this.tableName;
      }

      // Must be implemented by concrete subclasses:
      abstract findById(id: string): Promise<T | null>;
      abstract save(entity: T): Promise<void>;
    }

    class UserRepository extends BaseRepository<{ id: string; name: string }> {
      constructor() {
        super("users");
      }

      public async findById(id: string) {
        return { id, name: "Sample User" };
      }

      public async save(entity: { id: string; name: string }) {
        console.log(`Saving ${entity.name} to ${this.tableName}`);
      }
    }
    ```
  </Tab>

  <Tab value="Interface (Pure Contract)">
    An `interface` has **zero runtime presence** and provides purely structural contracts. A class can implement multiple interfaces:

    ```typescript
    interface Authenticatable {
      authenticate(token: string): boolean;
    }

    interface Auditable {
      logAudit(action: string): void;
    }

    class ServiceUser implements Authenticatable, Auditable {
      public authenticate(token: string): boolean {
        return token.startsWith("tok_");
      }

      public logAudit(action: string): void {
        console.log(`[AUDIT]: Action performed: ${action}`);
      }
    }
    ```
  </Tab>
</Tabs>

### Summary Comparison

| Feature | `interface` | `abstract class` |
|---|---|---|
| Runtime footprint | **0 bytes** (Completely erased) | Emits JavaScript constructor & methods |
| Method implementation | No (Signatures only) | Yes (Can mix concrete & abstract methods) |
| Multiple inheritance | Yes (`implements A, B, C`) | No (Can only `extends` one class) |
| Primary use case | Public API contracts, DTO shapes | Base classes, Template Method design pattern |

## 6. Stage 3 Decorators (TypeScript 5.0+)

Starting in TypeScript 5.0, TypeScript natively supports ECMAScript Stage 3 Decorators without needing the legacy `experimentalDecorators` flag.

Decorators allow you to wrap or customize classes, methods, getters, setters, and fields declaratively:

```typescript
// Method Logger Decorator
function loggedMethod<This, Args extends any[], Return>(
  target: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>
) {
  const methodName = String(context.name);

  function replacementMethod(this: This, ...args: Args): Return {
    console.log(`[CALL]: Entering ${methodName} with arguments:`, args);
    const result = target.call(this, ...args);
    console.log(`[RETURN]: Exiting ${methodName} with result:`, result);
    return result;
  }

  return replacementMethod;
}

class MathService {
  @loggedMethod
  public multiply(a: number, b: number): number {
    return a * b;
  }
}

const calc = new MathService();
calc.multiply(4, 5);
// Console output:
// [CALL]: Entering multiply with arguments: [4, 5]
// [RETURN]: Exiting multiply with result: 20
```

## 7. Production Guidelines: Classes vs Functional TypeScript

<Callout type="tip" title="When to Use Classes in Modern TypeScript">
- **Use Classes for:**
  - Domain-Driven Design (DDD) Aggregates and Entities where state and invariants must be encapsulated together.
  - Frameworks designed around OOP (NestJS controllers/services, TypeORM, Angular).
  - Custom Error hierarchies (`class DatabaseTimeoutError extends Error`).
  - State machines and complex stateful data structures (e.g. Graph, PriorityQueue).
- **Prefer Pure Functions and Plain Objects for:**
  - React components and Next.js Server Actions.
  - API DTOs, request payloads, and database query results.
  - Data transformations and stateless utilities.
</Callout>
