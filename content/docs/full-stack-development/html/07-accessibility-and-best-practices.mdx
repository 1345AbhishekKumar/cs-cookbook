Accessibility (abbreviated as **a11y**) ensures that websites, tools, and technologies are designed and developed so that people with disabilities can perceive, understand, navigate, and interact with the web.

---

## 1. The Core Principles: WCAG (POUR)

The **Web Content Accessibility Guidelines (WCAG)** are built upon four fundamental principles:

1. **Perceivable**: Information and user interface components must be presentable to users in ways they can perceive (e.g. text alternatives for non-text content, transcripts for audio).
2. **Operable**: Interface components and navigation must be operable (e.g. everything can be navigated via keyboard without getting stuck in a focus trap).
3. **Understandable**: Information and the operation of the interface must be understandable (e.g. predictable navigation, clear form error explanations).
4. **Robust**: Content must be robust enough that it can be interpreted reliably by a wide variety of user agents, including assistive technologies.

## 2. The First Rule of ARIA

**ARIA (Accessible Rich Internet Applications)** is a specification that provides attributes to enhance accessibility when native HTML falls short.

<Callout type="warn" title="The First Rule of ARIA">
**"If you can use a native HTML element or attribute with the semantics and behavior you require already built in, then do so instead of re-purposing an element and adding an ARIA role, state, or property to make it accessible."**
</Callout>

### Native Element vs Custom Div ARIA:
```html
<!-- BAD: Custom div pretending to be a button (Requires JS for Enter/Space keys, tabindex, focus) -->
<div role="button" tabindex="0" onclick="handleClick()">Submit</div>

<!-- GOOD: Native semantic button with built-in accessibility & keyboard triggers -->
<button type="button" onclick="handleClick()">Submit</button>
```

## 3. Essential ARIA Attributes

When custom widgets (e.g. modals, accordion dropdowns, tabs) require ARIA, use these core attributes:

| Attribute | Purpose | Code Example |
| :--- | :--- | :--- |
| `aria-label` | Provides an invisible accessible name to screen readers. | `<button aria-label="Close dialog">✕</button>` |
| `aria-labelledby` | Associates an element with the `id` of visible heading/label text. | `<section aria-labelledby="billing-title">` |
| `aria-describedby` | Associates helper or error text with an input. | `<input aria-describedby="pwd-help-text" />` |
| `aria-hidden="true"`| Hides decorative elements (icons, graphics) from screen readers. | `<svg aria-hidden="true">...</svg>` |
| `aria-expanded` | Informs screen readers if a dropdown or accordion is open (`true`/`false`). | `<button aria-expanded="false" aria-controls="menu">` |
| `aria-live` | Announces dynamic updates without page reload (`polite` vs `assertive`). | `<div role="status" aria-live="polite">Cart updated</div>` |

## 4. Keyboard Navigation & `tabindex`

All interactive elements must be reachable and actionable using only the keyboard (`Tab`, `Shift + Tab`, `Enter`, and `Space`).

### The Three States of `tabindex`:

```html
<!-- 1. Normal Sequential Focus (tabindex="0") -->
<!-- Makes an otherwise non-focusable element (like a custom scroll container) focusable in tab order -->
<div tabindex="0" role="region" aria-label="Scrollable code output">...</div>

<!-- 2. Programmatic Focus Only (tabindex="-1") -->
<!-- Removes element from sequential tab order, but allows focusing via JavaScript (e.g. el.focus()) -->
<div id="modal" tabindex="-1">...</div>

<!-- 3. Positive Tabindex (tabindex="1", "2") — AVOID AT ALL COSTS! -->
<!-- Destroys the natural document tab flow and creates severe accessibility violations -->
<button tabindex="3">Do not do this</button>
```

## 5. Auditing & Testing Workflow

<Steps>
  <Step>
    #### Validate HTML Syntax (W3C Validator)
    Pass your pages through the [W3C Markup Validation Service](https://validator.w3.org/) to catch missing closing tags, unquoted attributes, and nested tag errors.
  </Step>
  <Step>
    #### Keyboard-Only Walkthrough
    Put your mouse away. Navigate your entire website using only the `Tab` key to move forward, `Shift + Tab` to move backward, and `Enter`/`Space` to activate controls. Verify visible focus outlines are never hidden (`outline: none` without replacement is a critical violation).
  </Step>
  <Step>
    #### Automated Audits (Lighthouse & axe)
    Open Chrome DevTools (`F12`), switch to the **Lighthouse** tab, and generate an Accessibility report. Install the **axe DevTools** browser extension to detect subtle contrast and labeling flaws.
  </Step>
  <Step>
    #### Inspect the Browser Accessibility Tree
    In Chrome DevTools, open the **Elements** panel and click the **Accessibility** sub-tab to inspect how the browser computes accessible names and roles for each element.
  </Step>
</Steps>

## 6. Full HTML5 Production Quality Checklist

| Area | Verification Checklist |
| :--- | :--- |
| **Document Structure** | Declared `<!DOCTYPE html>` and `<html lang="en">`. |
| **Headings** | Exactly one `<h1>` per page. Heading hierarchy is strictly sequential without skipping levels. |
| **Navigation** | All links use `<a>` with a valid `href`. External links include `rel="noopener noreferrer"`. |
| **Images** | Every `<img>` has an `alt` attribute. Decorative images use `alt=""`. Explicit `width` and `height` prevent layout shift. |
| **Forms** | Every `<input>`, `<select>`, and `<textarea>` has a dedicated `<label for="...">`. Error messages are linked with `aria-describedby`. |
| **Buttons** | Actions use `<button>`, navigation uses `<a>`. No `<div>` or `<span>` click handlers without full keyboard support. |
| **Tables** | `<caption>` provided. Header cells use `<th>` with appropriate `scope="col"` or `scope="row"`. |
