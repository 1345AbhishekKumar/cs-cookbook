In early versions of Python asyncio, coordinating multiple tasks using `asyncio.gather()` often led to **orphaned background tasks** and hidden exceptions if one task failed while others kept running silently.

Python 3.11 introduced **Structured Concurrency** through `asyncio.TaskGroup` and **Exception Groups** (`except*`), fundamentally transforming how production async software is written.

---

## 1. Structured Concurrency with `asyncio.TaskGroup`

The core principle of structured concurrency is simple:

> **Tasks spawned within a context must never outlive that context.**

If one task crashes, all other tasks in the group are **automatically cancelled**, and the exception is cleanly raised:

```python
import asyncio

async def worker(task_id: int, delay: float) -> str:
    print(f"[Worker {task_id}] Running...")
    await asyncio.sleep(delay)
    print(f"[Worker {task_id}] Complete!")
    return f"Result {task_id}"

async def main():
    # Guaranteed that when exiting the TaskGroup block, all tasks are finished!
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(worker(1, 0.5))
        t2 = tg.create_task(worker(2, 0.2))
        t3 = tg.create_task(worker(3, 0.4))

    # All results are safely available here:
    print("All tasks finished successfully:")
    print(t1.result(), t2.result(), t3.result())

asyncio.run(main())
```

Output:

```text
[Worker 1] Running...
[Worker 2] Running...
[Worker 3] Running...
[Worker 2] Complete!
[Worker 3] Complete!
[Worker 1] Complete!
All tasks finished successfully:
Result 1 Result 2 Result 3
```

## 2. Exception Groups & `except*` (PEP 654)

What happens if **two concurrent tasks fail at the exact same moment**?

Traditionally, Python could only raise one exception, silently dropping the other. With **Exception Groups**, Python captures all concurrent errors and lets you handle them selectively using `except*`:

```python
import asyncio

async def network_task():
    await asyncio.sleep(0.1)
    raise ConnectionResetError("Database connection lost")

async def disk_task():
    await asyncio.sleep(0.1)
    raise FileNotFoundError("Config file missing")

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(network_task())
            tg.create_task(disk_task())
    except* ConnectionResetError as eg:
        print("Handling network failures:", eg.exceptions)
    except* FileNotFoundError as eg:
        print("Handling missing files:", eg.exceptions)

asyncio.run(main())
```

Output:

```text
Handling network failures: (ConnectionResetError('Database connection lost'),)
Handling missing files: (FileNotFoundError('Config file missing'),)
```

Both exception blocks executed! Neither error was swallowed.

## 3. Async Iterators & `async for`

Just as standard iterators use `__iter__` and `__next__`, asynchronous streams use **`__aiter__`** and **`__anext__`**:

```python
import asyncio

class AsyncDataStream:
    """Simulates streaming real-time events over a WebSocket."""
    def __init__(self, limit: int):
        self.limit = limit
        self.current = 0

    def __aiter__(self):
        return self

    async def __anext__(self):
        if self.current >= self.limit:
            raise StopAsyncIteration
        await asyncio.sleep(0.2)  # Non-blocking delay
        self.current += 1
        return f"Event Payload #{self.current}"

async def main():
    async for event in AsyncDataStream(3):
        print("Received:", event)

asyncio.run(main())
```

Output:

```text
Received: Event Payload #1
Received: Event Payload #2
Received: Event Payload #3
```

### Question 1: Output Prediction (TaskGroup Cancellation Cascading)

Consider this `TaskGroup` scenario where one task crashes while another is sleeping:

```python
import asyncio

async def fast_failing_task():
    await asyncio.sleep(0.1)
    print("Failing task: raising ValueError")
    raise ValueError("Something went wrong!")

async def slow_task():
    try:
        print("Slow task started")
        await asyncio.sleep(1.0)
        print("Slow task finished")
    except asyncio.CancelledError:
        print("Slow task intercepted cancellation!")
        raise

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(fast_failing_task())
            tg.create_task(slow_task())
    except* ValueError as eg:
        print(f"Caught ExceptionGroup: {eg.exceptions}")

asyncio.run(main())
```

What is the exact console output, and does `"Slow task finished"` ever print?

<Accordions>
<Accordion title="Solution & Breakdown">
**Output:**
```text
Slow task started
Failing task: raising ValueError
Slow task intercepted cancellation!
Caught ExceptionGroup: (ValueError('Something went wrong!'),)
```

**Explanation:**

1. Both `fast_failing_task` and `slow_task` start concurrently. `"Slow task started"` prints immediately.
2. At `0.1s`, `fast_failing_task` raises `ValueError`.
3. The `TaskGroup` context manager immediately detects the unhandled exception and calls `.cancel()` on all other currently active tasks in the group (namely, `slow_task`).
4. `slow_task` is awakened at its suspension point (`await asyncio.sleep(1.0)`) with an `asyncio.CancelledError`.
5. It prints `"Slow task intercepted cancellation!"` and re-raises `CancelledError` to allow clean termination.
6. Once all sibling tasks have finished unwinding, the `TaskGroup` packages the unhandled error into an `ExceptionGroup`, which is caught by `except* ValueError`.
7. `"Slow task finished"` never prints!

### Question 2: Spot and Fix the Bug (Async Context Manager Exception Leaks)

The following asynchronous database connection pool context manager is supposed to release connections back to the pool even if an error occurs inside the `async with` block. However, in error conditions, the connection is leaked:

```python
class AsyncDBConnection:
    def __init__(self, pool, conn_id):
        self.pool = pool
        self.conn_id = conn_id

    async def __aenter__(self):
        print(f"Acquiring connection {self.conn_id}")
        return self

    async def __aexit__(self, exc_type, exc_val, exc_tb):
        if exc_type is not None:
            print(f"Error occurred: {exc_val}")
            # BUG: Returns None without returning connection!
            return False
        print(f"Releasing connection {self.conn_id} back to pool")
        self.pool.release(self.conn_id)
        return False
```

Identify the leak and write the robust `__aexit__` implementation ensuring cleanup occurs unconditionally.

<Accordions>
<Accordion title="Solution & Breakdown">
**The Root Cause:**
Because `self.pool.release(self.conn_id)` is placed inside an `else` branch (implied by returning early on `if exc_type is not None:`), any exception raised inside the caller's `async with` block skips connection release!

**The Robust Fix:**
Place cleanup logic in a `finally` block or execute it unconditionally before returning:

```python
class AsyncDBConnection:
    def __init__(self, pool, conn_id):
        self.pool = pool
        self.conn_id = conn_id

    async def __aenter__(self):
        print(f"Acquiring connection {self.conn_id}")
        return self

    async def __aexit__(self, exc_type, exc_val, exc_tb):
        try:
            if exc_type is not None:
                print(f"Logging transaction failure for conn {self.conn_id}: {exc_val}")
        finally:
            # Guarantees the connection is returned under all circumstances:
            print(f"Releasing connection {self.conn_id} back to pool")
            self.pool.release(self.conn_id)

        # Return False to re-raise the caller's exception:
        return False
```

### Question 3: Architecture Deep-Dive (ExceptionGroup vs Standard Multi-Catch)

Why was the `except*` syntax introduced in Python 3.11? Why couldn't traditional `try ... except (TypeA, TypeB)` handle concurrent task failures?

<Accordions>
<Accordion title="Solution & Breakdown">
**The Concurrency Problem:**
In synchronous sequential code, only **one** exception can be active and unwinding the call stack at any given moment. Therefore, a standard `try ... except TypeA: ... except TypeB:` block handles whichever single exception occurred first.

In concurrent programs (such as `asyncio.TaskGroup` or multi-threaded task engines), multiple tasks execute in parallel. If Task 1 raises `ConnectionResetError` and Task 2 simultaneously raises `ValueError`, **both errors happened concurrently**.

If Python used traditional `except`, it would have to discard one error to propagate the other!

**How `except*` Solves This:**

1. Python 3.11 introduced `ExceptionGroup('msg', [err1, err2, ...])`.
2. `except* ErrorType` allows matching **subsets** of the exception group.
3. Multiple `except*` clauses can execute for the **same** group:

```python
try:
    async with asyncio.TaskGroup() as tg:
        tg.create_task(db_call())   # raises DatabaseError
        tg.create_task(calc())      # raises ZeroDivisionError
except* DatabaseError as dbe:
    # Handles all DatabaseErrors in the group
    print("Database failed:", dbe.exceptions)
except* ZeroDivisionError as zde:
    # ALSO executes in the same try block!
    print("Math error:", zde.exceptions)
```

4. Any unhandled sub-exceptions in the group are automatically repackaged and re-raised.

</Accordion>

### Question 5: Code Challenge (Async Batch Window Stream Transformer)

Build an async stream processor function `async_batcher(stream, batch_size: int, max_wait_seconds: float)` that:

1. Accepts an arbitrary `AsyncIterator`.
2. Yields batches (`list`) of items as soon as `batch_size` items accumulate OR when `max_wait_seconds` expires (whichever happens first).
3. Flushes any remaining trailing items before completing.

**Test cases:**

```python
# If stream yields 5 items with 0.1s delay, batch_size=2, max_wait=0.5s:
# Yields [1, 2], [3, 4], [5]
```

<Accordions>
<Accordion title="Solution & Breakdown">
```python
import asyncio
import time
from typing import AsyncIterator, List, TypeVar

T = TypeVar("T")

async def async_batcher(
stream: AsyncIterator[T],
batch_size: int,
max_wait_seconds: float
) -> AsyncIterator[List[T]]:
batch: List[T] = []
stream_iter = aiter(stream)
last_flush = time.monotonic()

    while True:
        try:
            # Wait for next item with remaining timeout:
            time_since_flush = time.monotonic() - last_flush
            remaining_time = max(0.001, max_wait_seconds - time_since_flush)

            # asyncio.wait_for waits on anext:
            item = await asyncio.wait_for(anext(stream_iter), timeout=remaining_time)
            batch.append(item)

            if len(batch) >= batch_size:
                yield batch
                batch = []
                last_flush = time.monotonic()

        except asyncio.TimeoutError:
            # Timeout triggered: flush accumulated partial batch if any
            if batch:
                yield batch
                batch = []
                last_flush = time.monotonic()

        except StopAsyncIteration:
            # Stream ended: flush any remainder and exit
            if batch:
                yield batch
            break

# Verification

async def event*generator():
for i in range(1, 8): # 1-3 fast, 4 delayed, 5-7 fast
delay = 0.4 if i == 4 else 0.05
await asyncio.sleep(delay)
yield f"event*{i}"

async def main():
async for b in async_batcher(event_generator(), batch_size=3, max_wait_seconds=0.2):
print(f"Flushed batch ({len(b)} items): {b}")

asyncio.run(main())

```

## Summary Reference

- **`asyncio.TaskGroup`**: Modern structured concurrency manager; replaces `asyncio.gather()`.
- **Automatic cancellation**: If any task fails, all sibling tasks in the `TaskGroup` cancel safely.
- **`except*`**: Modern exception handling syntax that unpacks concurrent `ExceptionGroup` collections.
- **`async for`**: Consumes streams asynchronously using `__aiter__` and `__anext__`.
