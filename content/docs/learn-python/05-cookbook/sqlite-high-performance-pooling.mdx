Many developers mistakenly dismiss SQLite as a lightweight toy database. In reality, when properly tuned, SQLite can handle **thousands of queries per second** with sub-millisecond latencies.

The secret lies in configuring **WAL Mode (Write-Ahead Logging)** and building a thread-safe **Connection Pool**.

---

## 1. Essential Production PRAGMAs

By default, SQLite uses a rollback journal that locks the entire database file during writes, blocking readers. Enabling **WAL Mode** allows **unlimited concurrent readers to proceed uninterrupted while a writer writes**:

```python
import sqlite3

def configure_sqlite_connection(conn: sqlite3.Connection) -> sqlite3.Connection:
    conn.execute("PRAGMA journal_mode = WAL;")        # Write-Ahead Logging
    conn.execute("PRAGMA synchronous = NORMAL;")       # Safe with WAL, 3x faster
    conn.execute("PRAGMA busy_timeout = 5000;")        # Wait 5s on lock contention
    conn.execute("PRAGMA cache_size = -64000;")        # 64 MB memory cache
    conn.execute("PRAGMA foreign_keys = ON;")          # Enforce relational integrity
    conn.row_factory = sqlite3.Row                     # Return dict-like row objects
    return conn
```

## 2. Thread-Safe Connection Pool

SQLite connections cannot be safely shared across threads simultaneously. Instead, create a **Connection Pool** using Python's thread-safe `queue.Queue`:

```python
from contextlib import contextmanager
from queue import Empty, Queue
import sqlite3
import threading

class SQLiteConnectionPool:
    """Thread-safe connection pool for SQLite."""

    def __init__(self, db_path: str, max_connections: int = 5):
        self.db_path = db_path
        self.max_connections = max_connections
        self._pool: Queue[sqlite3.Connection] = Queue(maxsize=max_connections)

        for _ in range(max_connections):
            conn = sqlite3.connect(db_path, check_same_thread=False)
            configure_sqlite_connection(conn)
            self._pool.put(conn)

    @contextmanager
    def connection(self, timeout: float = 3.0):
        """Acquires a connection from pool, automatically returning it on block exit."""
        try:
            conn = self._pool.get(timeout=timeout)
        except Empty:
            raise TimeoutError("All database connections in pool are currently busy!")

        try:
            yield conn
        finally:
            self._pool.put(conn)

    def close_all(self):
        while not self._pool.empty():
            conn = self._pool.get_nowait()
            conn.close()
```

### Multithreaded Execution Example

```python
from concurrent.futures import ThreadPoolExecutor

pool = SQLiteConnectionPool("production.db", max_connections=4)

# Create table
with pool.connection() as conn:
    conn.execute("CREATE TABLE IF NOT EXISTS metrics (id INT, val REAL);")
    conn.commit()

def record_metric(worker_id: int):
    with pool.connection() as conn:
        conn.execute("INSERT INTO metrics VALUES (?, ?);", (worker_id, worker_id * 1.5))
        conn.commit()
    print(f"Worker {worker_id} recorded metric successfully.")

# Run 10 concurrent worker threads against the 4-connection pool:
with ThreadPoolExecutor(max_workers=10) as executor:
    list(executor.map(record_metric, range(10)))

pool.close_all()
```

Output:

```text
Worker 0 recorded metric successfully.
Worker 1 recorded metric successfully.
...
Worker 9 recorded metric successfully.
```

### Question 1: Output Prediction (WAL Mode Reader vs Writer Concurrency)

In traditional `DELETE` (rollback) journal mode vs `WAL` mode, what happens when Thread A begins a long transaction inserting 100,000 rows, and Thread B immediately attempts to read rows from the same table?

```python
# Thread A:
conn_a.execute("BEGIN IMMEDIATE;")
conn_a.execute("INSERT INTO logs SELECT ...")  # takes 3 seconds

# Thread B (at 0.5s):
rows = conn_b.execute("SELECT COUNT(*) FROM logs").fetchall()
```

Does Thread B raise `OperationalError: database is locked` or succeed?

<Accordions>
  <Accordion title="Solution & Breakdown">
    **Output / Behavior:** - **In Default Journal Mode (`DELETE`):** Thread B
    blocks and, after its `busy_timeout` expires, raises
    `sqlite3.OperationalError: database is locked`. Rollback journaling requires
    an exclusive file lock that halts all readers. - **In Write-Ahead Logging
    Mode (`WAL`):** Thread B **succeeds immediately without blocking!** In WAL
    mode, writes are appended to a separate `-wal` file while original database
    pages remain readable. Thread B reads the snapshot of the database from the
    exact point in time when its transaction began, completely unaffected by
    Thread A's ongoing uncommitted write.
  </Accordion>
</Accordions>

### Question 2: Spot and Fix the Bug (SQLite check_same_thread Violation in FastAPi/AsyncIO)

A developer initializes a global SQLite connection in a FastAPI application, but requests randomly crash with `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that thread`:

```python
import sqlite3

# Global connection initialized on main thread:
db = sqlite3.connect("app.db")

async def get_user_profile(user_id: int):
    # Running inside an asyncio worker thread or event loop:
    # BUG: Fails with ProgrammingError across threads!
    cursor = db.cursor()
    cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))
    return cursor.fetchone()
```

Explain why CPython enforces `check_same_thread=True` by default, and implement two proper solutions for web backends.

<Accordions>
<Accordion title="Solution & Breakdown">
**The Root Cause:**
By default, `sqlite3.connect()` enables `check_same_thread=True`. Because SQLite C handles maintain thread-local state and internal locks, sharing the exact same connection object across multiple concurrent threads simultaneously can cause C-level data corruption.

**Fix 1: Connection Pooling (Recommended for Multi-Threaded Sync/Worker Pools):**
Use `SQLiteConnectionPool` with `check_same_thread=False` where **only one thread borrows and uses a connection at a time**:

```python
pool = SQLiteConnectionPool("app.db", max_connections=10)

def get_user_profile(user_id: int):
    with pool.connection() as conn:
        cursor = conn.cursor()
        cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))
        return cursor.fetchone()
```

**Fix 2: Dedicated Async SQLite with aiosqlite:**
Use `aiosqlite`, which offloads SQLite calls to a dedicated background worker thread per connection and exposes non-blocking `async with aiosqlite.connect(...)` APIs.

</Accordion>

### Question 3: Architecture Deep-Dive (PRAGMA synchronous = NORMAL vs FULL vs OFF)

What are the trade-offs of the `synchronous` PRAGMA in SQLite? Why is `PRAGMA synchronous = NORMAL` considered 100% crash-safe in WAL mode, but not in traditional rollback journal mode?

<Accordions>
<Accordion title="Solution & Breakdown">
**`PRAGMA synchronous` Levels:**
- **`FULL` (Default):** The OS explicitly flushes disk buffers (`fsync()`) after every single transaction commit. Maximum safety, but physical mechanical disks/SSDs can only perform ~100 commits/sec due to disk write latency.
- **`NORMAL`:** Flushes sync buffers only at critical database checkpoints (WAL checkpointing).
- **`OFF`:** SQLite delegates syncing entirely to the operating system; fastest, but risks database corruption on power loss.

**Why `NORMAL` is Safe in WAL Mode:**

- In WAL mode with `synchronous = NORMAL`, commits only require writing to the sequential WAL file.
- Even if the machine loses power, the WAL file structure guarantees that uncheckpointed or partially written transactions are detected via checksums and cleanly rolled back. The main `.db` file remains 100% uncorrupted.
- This gives a **3x to 5x write throughput speedup** with zero risk of database corruption!
  </Accordion>
</Accordions>

### Question 4: Hands-On Challenge (Fast Batch Ingestion with Transactions)

Inserting 50,000 records row-by-row with individual `conn.execute("INSERT ...")` and default autocommit takes over 60 seconds!

Refactor the code below using `executemany()` and an explicit `with conn:` transaction block to execute in **under 0.2 seconds**:

```python
# SLOW BASELINE (60+ seconds):
for item in dataset:
    conn.execute("INSERT INTO items VALUES (?, ?)", (item.id, item.name))
    conn.commit()  # Each commit forces an fsync!
```

<Accordions>
<Accordion title="Solution & Breakdown">
```python
import sqlite3
import time

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE items (id INT, name TEXT);")

dataset = [(i, f"item_{i}") for i in range(50_000)]

# Optimized Batch Ingestion:

t0 = time.perf_counter()

# Wrapping in an explicit transaction forces ONE single commit/fsync:

with conn:
conn.executemany("INSERT INTO items VALUES (?, ?)", dataset)

elapsed = time.perf_counter() - t0
print(f"Inserted 50,000 items in {elapsed:.3f}s!")

# Verification:

count = conn.execute("SELECT COUNT(\*) FROM items").fetchone()[0]
assert count == 50_000

````
*Note: In benchmarks, this reduces execution time from ~60s down to ~0.08s (a ~750x speedup)!*

### Question 5: Code Challenge (Production SQLite Schema Migration Runner with WAL and Locks)
Build a minimal migration runner class `SQLiteMigrator` that:
1. Connects with WAL mode and `busy_timeout=5000`.
2. Creates a `_schema_migrations` tracking table if not present.
3. Applies a list of versioned migration SQL scripts atomically (`conn.execute("BEGIN IMMEDIATE;")`).
4. Automatically records the version and timestamp on success, and rolls back cleanly on error.

<Accordions>
<Accordion title="Solution & Breakdown">
```python
import sqlite3
import time
from typing import List, Tuple

class SQLiteMigrator:
    def __init__(self, db_path: str):
        self.conn = sqlite3.connect(db_path)
        self.conn.execute("PRAGMA journal_mode = WAL;")
        self.conn.execute("PRAGMA busy_timeout = 5000;")
        self._ensure_migration_table()

    def _ensure_migration_table(self):
        with self.conn:
            self.conn.execute("""
                CREATE TABLE IF NOT EXISTS _schema_migrations (
                    version INT PRIMARY KEY,
                    description TEXT,
                    applied_at REAL
                );
            """)

    def apply_migrations(self, migrations: List[Tuple[int, str, str]]):
        # migrations: [(version, description, sql_script)]
        for version, desc, sql in migrations:
            # Check if already applied
            cur = self.conn.execute(
                "SELECT 1 FROM _schema_migrations WHERE version = ?", (version,)
            )
            if cur.fetchone():
                continue

            print(f"Applying migration v{version}: '{desc}'...")
            try:
                # Use IMMEDIATE transaction to acquire write lock upfront:
                self.conn.execute("BEGIN IMMEDIATE;")
                self.conn.executescript(sql)
                self.conn.execute(
                    "INSERT INTO _schema_migrations VALUES (?, ?, ?);",
                    (version, desc, time.time())
                )
                self.conn.execute("COMMIT;")
                print(f"Successfully applied v{version}.")
            except Exception as e:
                self.conn.execute("ROLLBACK;")
                raise RuntimeError(f"Migration v{version} failed! Rolled back cleanly.") from e

# Verification
migrator = SQLiteMigrator(":memory:")

migrations = [
    (1, "Create users table", "CREATE TABLE users (id INT PRIMARY KEY, email TEXT);"),
    (2, "Add active flag", "ALTER TABLE users ADD COLUMN is_active INT DEFAULT 1;")
]

migrator.apply_migrations(migrations)

# Check state
applied = migrator.conn.execute("SELECT version, description FROM _schema_migrations").fetchall()
print("Applied Migrations:", applied)
assert len(applied) == 2
````

</Accordion>
</Accordions>

## Summary Reference

- **`journal_mode = WAL`**: Enables non-blocking concurrent reading and writing.
- **`busy_timeout = 5000`**: Eliminates immediate `sqlite3.OperationalError: database is locked` exceptions.
- **Connection Pool**: Reuses persistent SQLite handles across worker threads without connection renegotiation overhead.
