Welcome to **Stage 3: Transactions, Concurrency & Reliability** — the correctness core of the curriculum.

Fast is worthless if it is wrong. This stage is about the guarantees that let you reason about concurrent programs sharing mutable state: what ACID really means, which anomalies each isolation level permits (and the one almost everyone gets wrong — **write skew**), and how MVCC, locking, and the Write-Ahead Log cooperate to keep committed data safe across crashes.

---

## Pedagogical Philosophy

<Callout type="info" title="Concurrency Is Where Intuition Fails">
Single-threaded reasoning is reliable. The moment two transactions interleave, the outcomes stop matching the code you wrote. Every anomaly — lost update, phantom, write skew — is a *specific* interleaving that a *specific* isolation level allows. Learn the anomalies by name and you can spot the bug before it reaches production, and pick the level that forbids it.
</Callout>

By the end of this stage you will be able to:

- State precisely what Atomicity, Consistency, Isolation, and Durability each guarantee.
- Name and reproduce the classic anomalies: dirty read, lost update, non-repeatable read, phantom, **write skew**.
- Map the SQL-standard levels to what PostgreSQL *actually* does (hint: `REPEATABLE READ` = snapshot isolation).
- Explain MVCC snapshots, dead tuples, vacuum, lock modes, and deadlocks.
- Describe the Write-Ahead Log and how a database recovers after a crash.
