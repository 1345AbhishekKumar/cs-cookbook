Welcome to **Stage 2: Storage, Indexing & Query Optimization** — where SQL meets the metal.

A database is a machine that trades memory for disk. This stage explains *how*: how rows become 8 KB pages, why a B+ tree of height 3 can locate one row among a billion in three disk reads, and how a cost-based optimizer picks a plan you can inspect with `EXPLAIN`.

---

## Pedagogical Philosophy

<Callout type="info" title="Performance Is Mostly Physical">
Ninety percent of database performance comes down to three quantities: **how many pages must be read**, **how many must be written**, and **whether those reads are sequential or random**. Everything else — indexes, query plans, partitioning — is a strategy for moving those numbers in your favor. Learn to reason about pages and you can diagnose any slow query.
</Callout>

By the end of this stage you will be able to:

- Describe how a row is physically stored (heap file, slotted page, tuple header).
- Explain why a B+ tree is preferred over a hash table for general-purpose indexes.
- Design composite indexes that satisfy the **leftmost-prefix** rule — and know when PostgreSQL 18's **skip scan** saves you.
- Read an `EXPLAIN ANALYZE` plan and spot the actual bottleneck versus the estimated one.
