## What SQL Is

**SQL (Structured Query Language)** is the declarative language of relational databases. You describe the *result* you want as a set, and the engine works out how to compute it. SQL splits into four families:

| Family | Stands for | Statements | Purpose |
| :--- | :--- | :--- | :--- |
| **DDL** | Data Definition Language | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` | Define and change the schema |
| **DML** | Data Manipulation Language | `INSERT`, `UPDATE`, `DELETE`, `MERGE` | Change the data |
| **DQL** | Data Query Language | `SELECT` | Read the data |
| **TCL** | Transaction Control Language | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | Group statements atomically |

(Two more are sometimes listed: **DCL** — `GRANT`/`REVOKE` — for permissions, and **DXL** for session settings.)

SQL keywords are **case-insensitive** (`select` = `SELECT`); only the data inside string literals is case-sensitive. By convention, keywords are uppercase and identifiers lowercase.

## The Anatomy of a SELECT

Every query you will ever write is a variation of this skeleton:

```sql
SELECT   customer_id, COUNT(*) AS bookings      -- 5. which columns
FROM     bookings                                -- 1. which table(s)
WHERE    status = 'paid'                         -- 2. which rows
GROUP BY customer_id                             -- 3. how to group
HAVING   COUNT(*) > 1                            -- 4. which groups
ORDER BY bookings DESC                           -- 6. how to sort
LIMIT    10;                                     -- 7. how many
```

<Callout type="info" title="You Write It in One Order, the Engine Runs Another">
The engine evaluates **`FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`**. This is why a `SELECT` alias works in `ORDER BY` but not in `WHERE`. (Full explanation in [Stage 1 · Lesson 03](/docs/databases-sql/01-foundations-and-relational-modeling/03-queries-joins-and-aggregation).)
</Callout>

## Selecting Columns & Computing Expressions

```sql
SELECT
    id,                                    -- a column
    full_name,                             -- another column
    upper(full_name)        AS name_upper, -- function + alias
    created_at::date        AS signup_date,-- cast
    'TravelBuddy'           AS source      -- a literal
FROM customers;
```

| Expression form | Example |
| :--- | :--- |
| Column reference | `full_name` |
| Literal | `42`, `'paid'`, `true`, `NULL` |
| Arithmetic | `total_cents / 100.0` |
| String concatenation | `first_name || ' ' || last_name` |
| Function call | `lower(email)`, `now()` |
| Cast | `created_at::date`, `CAST(x AS integer)` |
| CASE expression | `CASE WHEN ... THEN ... ELSE ... END` |

### The `CASE` Expression (SQL's `if`)

```sql
SELECT
    flight_no,
    seats_available,
    CASE
        WHEN seats_available = 0         THEN 'sold out'
        WHEN seats_available < 10        THEN 'almost full'
        WHEN seats_available < 50        THEN 'filling up'
        ELSE                              'available'
    END AS availability
FROM flights;
```

`CASE` is an *expression*, so it can appear anywhere a value can — in the `SELECT` list, `WHERE`, `ORDER BY`, or inside an aggregate.

### `DISTINCT`

```sql
SELECT DISTINCT destination FROM flights;              -- unique destinations
SELECT DISTINCT origin, destination FROM flights;      -- unique route pairs
SELECT COUNT(DISTINCT customer_id) FROM bookings;      -- distinct count
```

## Filtering Rows with `WHERE`

`WHERE` keeps only rows for which the predicate is **`TRUE`**. `FALSE` and `UNKNOWN` both discard the row.

```sql
SELECT * FROM flights
WHERE departure_at >= '2026-07-01'
  AND departure_at <  '2026-08-01'
  AND seats_available > 0
  AND destination IN ('BCN', 'MAD', 'LIS')
  AND flight_no LIKE 'IB%';
```

| Operator | Meaning | Example |
| :--- | :--- | :--- |
| `=` `<>` `!=` | Equality / inequality | `status = 'paid'` |
| `<` `>` `<=` `>=` | Ordering | `seats_available > 0` |
| `BETWEEN a AND b` | Inclusive range | `price BETWEEN 100 AND 500` |
| `IN (...)` | Membership | `origin IN ('MAD','BCN')` |
| `LIKE` / `ILIKE` | Pattern (case-insensitive with `I`) | `email LIKE '%@gmail.com'` |
| `IS NULL` / `IS NOT NULL` | Null test | `phone IS NULL` |
| `AND` `OR` `NOT` | Boolean logic | `(a OR b) AND NOT c` |
| `IS DISTINCT FROM` | Null-safe inequality | `a IS DISTINCT FROM b` |

### Pattern Matching with `LIKE`

| Pattern | Matches |
| :--- | :--- |
| `'IB%'` | Starts with `IB` |
| `'%air'` | Ends with `air` |
| `'%los%'` | Contains `los` |
| `'_B248'` | Any single char, then `B248` |

<Callout type="warn" title="Case-Sensitive LIKE">
`LIKE` is case-sensitive; `ILIKE` is not. For any `LIKE '%...%'` that is not a prefix match, the engine cannot use a normal B-tree index — see **full-text search and `pg_trgm`** in Lesson 07.
</Callout>

## `NULL`: The Rule That Trips Everyone

`NULL` means **unknown**, not empty. Comparisons with `NULL` evaluate to `UNKNOWN`, and `WHERE` keeps only `TRUE`.

```sql
SELECT * FROM customers WHERE phone = NULL;       -- ❌ always empty
SELECT * FROM customers WHERE phone IS NULL;       -- ✅ correct

-- NOT IN with a NULL present returns zero rows! Use NOT EXISTS instead.
SELECT * FROM customers
WHERE NOT EXISTS (SELECT 1 FROM bookings b WHERE b.customer_id = customers.id);
```

| Want | Write |
| :--- | :--- |
| Null test | `IS NULL` / `IS NOT NULL` |
| Null-safe equality | `IS NOT DISTINCT FROM` |
| Null-safe inequality | `IS DISTINCT FROM` |
| Default value | `COALESCE(col, 0)` |
| First non-null of many | `COALESCE(a, b, c)` |

<Callout type="tip" title="`COALESCE` and `NULLIF`">
- `COALESCE(a, b, c)` returns the first non-`NULL` argument — the standard way to supply a default.
- `NULLIF(a, b)` returns `NULL` if `a = b`, else `a` — great for turning a sentinel like `0` into `NULL`: `total_cents / NULLIF(quantity, 0)` avoids divide-by-zero.
</Callout>

## Sorting with `ORDER BY`

```sql
SELECT flight_no, departure_at, seats_available
FROM flights
ORDER BY seats_available DESC,      -- primary: fullest first
         departure_at ASC;          -- tiebreaker: soonest first
```

| Feature | Syntax |
| :--- | :--- |
| Ascending (default) | `ORDER BY col ASC` |
| Descending | `ORDER BY col DESC` |
| Nulls last / first | `ORDER BY col DESC NULLS LAST` |
| Sort by expression | `ORDER BY lower(destination)` |
| Sort by alias | `ORDER BY bookings DESC` (alias defined in `SELECT`) |
| Sort by position | `ORDER BY 2 DESC` (discouraged — brittle) |

<Callout type="info" title="`NULL` Sort Order">
By default in PostgreSQL, `NULL`s sort as if **largest**: they appear last in `ASC` and first in `DESC`. Control it explicitly with `NULLS FIRST` / `NULLS LAST` when it matters.
</Callout>

## Limiting and Paginating

```sql
-- First 20 rows
SELECT * FROM bookings ORDER BY created_at DESC LIMIT 20;

-- Page 3 (rows 41–60)
SELECT * FROM bookings ORDER BY created_at DESC LIMIT 20 OFFSET 40;

-- ✅ Keyset pagination: O(log N) at any depth, no OFFSET scan
SELECT * FROM bookings
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

<Callout type="warn" title="`OFFSET` Gets Slower the Deeper You Page">
`OFFSET 100000` makes the engine produce and discard 100,000 rows before the ones you want. **Keyset (seek) pagination** — filtering on the last row you saw — is O(log N) regardless of depth. Use `OFFSET` only for shallow pages or small tables.
</Callout>

## Types, Casting & Coercion

```sql
SELECT
    42            :: text         AS as_text,       -- explicit cast
    CAST('123' AS integer)        AS as_int,
    '2026-07-04'  :: timestamptz   AS as_ts,
    total_cents / 100.0            AS dollars       -- int / numeric → numeric
FROM bookings
LIMIT 1;
```

| Cast | Notes |
| :--- | :--- |
| `x::type` | PostgreSQL shorthand |
| `CAST(x AS type)` | SQL standard |
| Implicit coercion | `'5' + 3` → works via numeric; be explicit to avoid surprises |

<Callout type="error" title="Integer Division Surprises">
`total_cents / 100` with two integers performs **integer division**: `4999 / 100 = 49`, silently dropping cents. Divide by a decimal (`100.0`) or cast: `total_cents::numeric / 100`.
</Callout>

## Comments, Identifiers & String Literals

```sql
-- single-line comment
/* multi-line
   comment */

SELECT "full_name" FROM customers;   -- double quotes = identifier (case-sensitive)
SELECT 'Ada Lovelace'  AS name;      -- single quotes = string literal
```

| Quotes | Meaning |
| :--- | :--- |
| `'text'` | String literal |
| `"Identifier"` | Identifier (table/column), case-sensitive |
| `$$text$$` | Dollar-quoted string (multi-line; used in functions) |

<Callout type="warn" title="Double vs. Single Quotes">
`SELECT "status"` refers to a **column named status**; `SELECT 'status'` is the **string** `status`. Mixing them up is a classic newcomer bug — identifiers get double quotes, values get single quotes.
</Callout>

## Practice Drills

Run these against the TravelBuddy schema.

```sql
-- 1. Full names of customers who signed up in 2026, newest first
SELECT full_name, created_at
FROM customers
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
ORDER BY created_at DESC;

-- 2. Flights with a "low seats" label, worst availability first
SELECT flight_no, seats_available,
       CASE WHEN seats_available < 5 THEN 'critical' ELSE 'ok' END AS level
FROM flights
WHERE destination LIKE '%'
ORDER BY seats_available ASC NULLS LAST;

-- 3. Distinct routes that depart from Spain
SELECT DISTINCT origin, destination
FROM flights
WHERE origin IN ('MAD', 'BCN', 'VLC');

-- 4. Customers with no phone on file
SELECT id, full_name FROM customers WHERE phone IS NULL;
```
