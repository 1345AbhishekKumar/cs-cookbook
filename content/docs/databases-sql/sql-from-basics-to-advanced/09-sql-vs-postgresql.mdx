## The Question Behind the Question

People ask *"SQL or PostgreSQL?"* as if choosing between two competing products. They are not competing — they are **different kinds of thing**:

> **SQL is a standard** (a published specification of a language). **PostgreSQL is a product** (one database that implements that language, with its own additions).

It is like asking "HTML or Chrome?". You do not choose one *instead of* the other. PostgreSQL **is** an SQL database. The real distinction is between **the standard** and **a dialect**.

| Name | What it actually is |
| :--- | :--- |
| **SQL** | The ISO/IEC 9075 language standard — a document, not software |
| **PostgreSQL** | An open-source relational DBMS **and** the dialect it speaks |
| **Postgres** | Just an informal short name for PostgreSQL |
| **`psql`** | PostgreSQL's *client program*; its `\d` commands are **not SQL** |
| **MySQL / SQL Server / Oracle / SQLite** | Other products, each with its own SQL dialect |

<Callout type="info" title="There Is No 'Plain SQL' Database">
Every engine you will ever touch speaks a **dialect**. A "portable core" genuinely exists — the 90% of SQL that behaves the same everywhere — but the edges (types, functions, upserts, pagination) differ from vendor to vendor. This lesson maps the line between the two.
</Callout>

## The Standard's Lineage

SQL has been standardized for nearly four decades. Knowing which revision introduced a feature tells you what you can safely expect elsewhere.

| Revision | Nickname | Notable additions |
| :--- | :--- | :--- |
| **SQL-86 / SQL-89** | First standards | The original `SELECT`/`INSERT`/`UPDATE`/`DELETE` |
| **SQL-92** | The big one | Joins, `CASE`, `COALESCE`/`NULLIF`, `EXCEPT`/`INTERSECT`, `GRANT` |
| **SQL:1999** | Recursion era | `WITH` / `WITH RECURSIVE`, **`LATERAL`**, triggers, `BOOLEAN` |
| **SQL:2003** | Analytics era | **Window functions**, **`MERGE`**, sequences, `GENERATED ... AS IDENTITY`, `FILTER` |
| **SQL:2008** | Pagination era | **`FETCH FIRST ... ROWS ONLY`**, `OFFSET`, `TRUNCATE` |
| **SQL:2011** | Temporal era | System-versioned (temporal) tables, `PERIOD` |
| **SQL:2016** | JSON era | **`JSON_VALUE` / `JSON_QUERY` / `JSON_EXISTS`**, row pattern matching |
| **SQL:2023** | Graph era | Property-graph queries, `ANY_VALUE`, `GREATEST`/`LEAST` |

<Callout type="warn" title="The Standard Is Not a Single Level">
The standard defines conformance levels — **Entry**, **Intermediate**, and **Full** — plus hundreds of numbered optional features. Crucially, **no database implements all of it**; vendors implement a core plus their own extensions. So "is it standard?" and "will it work in my database?" are two different questions.
</Callout>

## Where PostgreSQL Stands

PostgreSQL makes a serious effort at standards compliance, and it is honest about it — there is a whole appendix of the manual devoted to it.

> **PostgreSQL conforms to at least 170 of the 177 mandatory features required for SQL:2023 Core conformance.** No relational database currently meets full conformance.

So the accurate mental model is:

```text
SQL the standard          ████████████████████  (the specification)
PostgreSQL (SQL:2023)     ██████████████████░░  ~170/177 Core features + extensions
PostgreSQL extensions     ████░░░░░░░░░░░░░░░░  jsonb, arrays, ON CONFLICT, RETURNING, ...
```

PostgreSQL is simultaneously **one of the most standard-conformant databases** *and* **rich in non-standard extensions**. Both facts matter.

## The Portable Core

When you write these, you are writing *SQL* — and it will run essentially unchanged on PostgreSQL, MySQL, SQL Server, Oracle, and SQLite.

| Category | Portable syntax |
| :--- | :--- |
| Reading | `SELECT ... FROM ... WHERE ... ORDER BY ... GROUP BY ... HAVING` |
| Joins | `INNER` / `LEFT` / `RIGHT` / `FULL OUTER JOIN ... ON` |
| Set operations | `UNION [ALL]`, `INTERSECT`, `EXCEPT` |
| Conditional | `CASE WHEN ... THEN ... ELSE ... END`, `COALESCE`, `NULLIF` |
| Casting | `CAST(x AS type)` |
| Subqueries | Scalar, correlated, `EXISTS` / `NOT EXISTS`, `IN` |
| CTEs | `WITH name AS (...)`, `WITH RECURSIVE` |
| Analytics | Window functions (`ROW_NUMBER`, `RANK`, `SUM(...) OVER (...)`) |
| Writing | `INSERT`, `UPDATE`, `DELETE`, `BEGIN` / `COMMIT` / `ROLLBACK` |
| DDL | `CREATE TABLE` with `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, `NOT NULL` |
| Row limiting | `FETCH FIRST n ROWS ONLY` (SQL:2008) |

<Callout type="tip" title="Write to the Core by Default">
The portable core is not a compromise — it is usually **as good** as the dialect-specific version. Reach for a vendor extension only when it buys you something concrete (correctness, a large performance win, or a feature the standard lacks).
</Callout>

## Standard Features People *Think* Are PostgreSQL-Only

This is the biggest source of confusion. Many "PostgreSQL features" are actually **portable SQL** that other engines also implement:

| Feature | Standard since | Also available in |
| :--- | :--- | :--- |
| `LATERAL` joins | SQL:1999 | PostgreSQL, MySQL 8+, SQL Server, Oracle |
| `WITH RECURSIVE` CTEs | SQL:1999 | All major engines |
| Window functions | SQL:2003 | All major engines |
| `MERGE` (upsert-ish) | SQL:2003 | SQL Server, Oracle, PostgreSQL 15+, DB2 |
| `FILTER (WHERE ...)` on aggregates | SQL:2003 | PostgreSQL, SQLite |
| `GROUPING SETS` / `ROLLUP` / `CUBE` | SQL:1999 | PostgreSQL, Oracle, SQL Server 2008+, MySQL 8+ |
| `GENERATED ... AS IDENTITY` | SQL:2003 | PostgreSQL 10+, SQL Server, Oracle 12c+ |
| `FETCH FIRST n ROWS ONLY` | SQL:2008 | PostgreSQL, Oracle, SQL Server, DB2 |
| `JSON_VALUE` / `JSON_QUERY` / `JSON_EXISTS` | SQL:2016 | Oracle, SQL Server, MySQL, PostgreSQL 17+ |
| Ordered-set aggregates (`percentile_cont`, `mode`) | SQL:2003 | PostgreSQL, Oracle, others |

Training yourself to say *"that's standard, not Postgres"* makes your SQL far more portable.

## PostgreSQL Extensions Beyond the Standard

These are genuinely PostgreSQL-specific (or nearly so). They are excellent — and they are also what makes your SQL non-portable.

| PostgreSQL feature | What the standard does instead |
| :--- | :--- |
| `RETURNING` on `INSERT`/`UPDATE`/`DELETE` | Nothing standard (SQL Server's `OUTPUT` is also non-standard) |
| `INSERT ... ON CONFLICT DO UPDATE` (upsert) | `MERGE`, or a transaction with a check |
| `DISTINCT ON (col)` | `ROW_NUMBER() ... = 1` in a CTE |
| `LIMIT` / `OFFSET` | `FETCH FIRST n ROWS ONLY` |
| `ILIKE`, `~`, `~*`, `SIMILAR TO` (regex) | Vendor-specific everywhere |
| `x::type` cast shorthand | `CAST(x AS type)` |
| `Dollar-quoted strings` (`$$ ... $$`) | `'...'` with `''` escaping |
| Array types (`text[]`), `array_agg`, `unnest` | `ARRAY` types are SQL:2003, but operators/most functions are PG |
| `jsonb` (binary JSON) + operators | The standard defines a `JSON` type, not `jsonb` |
| Ranges, `EXCLUDE` constraints | Nothing standard |
| Full-text search (`tsvector` / `tsquery`) | Nothing standard |
| `COPY` for bulk load | `INSERT` (no bulk-load standard) |
| `CREATE EXTENSION`, `LISTEN`/`NOTIFY` | Nothing standard |
| Index types: `GIN`, `GiST`, `BRIN`, `SP-GiST` | The standard does not prescribe index implementations |
| `generate_series()`, `date_bin()` | Nothing standard |
| `SERIAL` (legacy auto-increment) | `GENERATED ... AS IDENTITY` (standard) |
| `uuidv7()` (PostgreSQL 18) | No standard UUID data type |
| `pg_catalog` internals | `information_schema` (which **is** standard) |

<Callout type="info" title="PostgreSQL 18 Keeps Closing the Gaps">
Recent releases have *absorbed* standard syntax rather than replacing it: `MERGE` arrived in PostgreSQL 15, the SQL/JSON functions (`JSON_VALUE`, `JSON_QUERY`, `JSON_EXISTS`) in 17, and temporal `WITHOUT OVERLAPS` constraints in 18. PostgreSQL tends to **add** the standard form, keeping its older extension too — so you often have both `LIMIT` and `FETCH FIRST`.
</Callout>

## Dialect Comparison: One Task, Four Engines

The same common tasks, side by side:

| Task | PostgreSQL | MySQL | SQL Server | Oracle |
| :--- | :--- | :--- | :--- | :--- |
| **Limit rows** | `LIMIT n` or `FETCH FIRST n ROWS ONLY` | `LIMIT n` | `SELECT TOP n` or `OFFSET … FETCH` | `FETCH FIRST n ROWS ONLY` |
| **Upsert** | `ON CONFLICT … DO UPDATE` | `ON DUPLICATE KEY UPDATE` | `MERGE` | `MERGE` |
| **Return changed rows** | `RETURNING` | — | `OUTPUT` | `RETURNING INTO` (PL/SQL) |
| **String concat** | `a \|\| b` | `CONCAT(a, b)` | `a + b` / `CONCAT` | `a \|\| b` |
| **Null default** | `COALESCE` | `COALESCE` / `IFNULL` | `COALESCE` / `ISNULL` | `COALESCE` / `NVL` |
| **Auto-increment** | `GENERATED … AS IDENTITY` | `AUTO_INCREMENT` | `IDENTITY` | `IDENTITY` / sequence |
| **Quote an identifier** | `"col"` | `` `col` `` | `[col]` | `"col"` |
| **Boolean type** | `boolean` | `TINYINT(1)` | `bit` | none (uses `NUMBER(1)`) |
| **Current time** | `now()` / `CURRENT_TIMESTAMP` | `NOW()` | `GETDATE()` | `SYSDATE` |
| **Truncate to month** | `date_trunc('month', ts)` | `DATE_FORMAT(ts,'%Y-%m-01')` | `DATETRUNC(month, ts)` (2022+) | `TRUNC(ts, 'MM')` |
| **Empty string vs NULL** | different | different | different | **`''` IS NULL** |
| **Unquoted identifier case** | folds to **lower** | depends on OS | case-insensitive | folds to **upper** |

### The Same Query, Three Ways

<Tabs items={['Standard (portable)', 'PostgreSQL', 'SQL Server']}>
<Tab value="Standard (portable)">
```sql
-- Pagination in standard SQL (SQL:2008)
SELECT customer_id, created_at, total_cents
FROM bookings
ORDER BY created_at DESC
OFFSET 40 ROWS
FETCH FIRST 20 ROWS ONLY;
```
</Tab>
<Tab value="PostgreSQL">
```sql
-- PostgreSQL's own (also accepts the standard form above)
SELECT customer_id, created_at, total_cents
FROM bookings
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;
```
</Tab>
<Tab value="SQL Server">
```sql
-- T-SQL: OFFSET/FETCH *requires* an ORDER BY
SELECT customer_id, created_at, total_cents
FROM bookings
ORDER BY created_at DESC
OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY;
```
</Tab>
</Tabs>

## The Porting Traps

If you move SQL between engines, these are what bite.

| Trap | Detail |
| :--- | :--- |
| **Identifier quoting** | `"col"` (SQL standard / PostgreSQL / Oracle), `` `col` `` (MySQL), `[col]` (SQL Server). Use **unquoted lowercase snake_case** to dodge the issue entirely. |
| **Case folding** | PostgreSQL folds unquoted identifiers to **lowercase**; Oracle folds to uppercase; MySQL depends on the OS. Quoted names become case-**sensitive** everywhere. |
| **`LIMIT` is not standard** | Prefer `FETCH FIRST n ROWS ONLY` if portability matters — PostgreSQL supports it. |
| **`''` vs `NULL`** | Oracle treats the empty string as `NULL`; PostgreSQL, MySQL, and SQL Server treat them as distinct. Logic that works in one can silently break in another. |
| **Strict `GROUP BY`** | The standard (and PostgreSQL) require every non-aggregated `SELECT` column to be grouped. Some engines historically allowed lax grouping. |
| **Implicit coercion** | MySQL silently coerces `'5' + 3`; PostgreSQL is strict and will error. Strictness is a feature — it catches bugs. |
| **Default `NULL` ordering** | PostgreSQL sorts `NULL`s last in `ASC` (as if largest); the default differs elsewhere. Always write `NULLS FIRST` / `NULLS LAST`. |
| **Date/time functions** | `date_trunc`, `date_bin`, `age` are PostgreSQL; `DATE_FORMAT`, `DATETRUNC`, `TRUNC` are others'. |
| **Catalogs** | `information_schema` is standard; `pg_catalog` is PostgreSQL-specific. |
| **Vendor types** | `jsonb`, arrays, ranges, `tsvector`, `uuid` have no portable equivalent. |

<Callout type="error" title="Strictness Is Your Friend">
When PostgreSQL *rejects* something MySQL silently accepts, it is usually protecting you from a bug (implicit string-to-number coercion, ambiguous grouping, `''` treated as `NULL`). Porting in that direction usually surfaces real errors — which is exactly what you want, early.
</Callout>

## Strategy: Portable, or PostgreSQL-First?

The honest answer is: **use the standard by default, and break it only on purpose.**

| Situation | Recommendation |
| :--- | :--- |
| Ordinary CRUD, reporting, joins, aggregation | Write **portable SQL** — it costs nothing |
| Pagination | Use `FETCH FIRST` / `OFFSET` if you want reach; `LIMIT` if you are committed to PostgreSQL/MySQL |
| Upserts, returning generated values | PostgreSQL's `ON CONFLICT` + `RETURNING` are worth the non-portability |
| Semi-structured data, arrays, search | `jsonb`, arrays, and full-text are decisive PostgreSQL advantages |
| Performance-critical indexing | Index types (`GIN`, `BRIN`, `GiST`) are inherently implementation-specific |
| Multi-database applications | Isolate all dialect-specific SQL behind a **repository/data-access layer** |

<Callout type="tip" title="Keep the Vendor-Specific Surface Small and Contained">
You will almost certainly never migrate off your database — it is one of the largest, riskiest projects in software. So do not cripple your design for hypothetical portability. Instead: **write the standard where it is equally good, embrace PostgreSQL extensions where they earn their keep, and keep those extensions in a small, documented, swappable layer.**
</Callout>

### Where an ORM Fits

ORMs and query builders smooth over dialect differences — until they leak. Prefer one with a real dialect layer, but remember:

- ORMs cannot hide differences in **transaction isolation, locking, or SQL types**.
- Generated SQL is still dialect-specific; a `LIMIT` becomes `TOP`/`FETCH` per engine, but `jsonb` operators will not.
- Raw escape hatches (`.raw()`, `queryRaw`) are where your PostgreSQL-specific SQL will live — keep them organized.

## Quick Check: Standard or PostgreSQL-Only?

Attempt each before revealing.

**1.** `LATERAL` joins

<details>
<summary>Reveal</summary>

**Standard** — SQL:1999. Available in PostgreSQL, MySQL 8+, SQL Server, and Oracle.
</details>

**2.** `RETURNING` on an `INSERT`

<details>
<summary>Reveal</summary>

**PostgreSQL-defined.** The standard has no equivalent; SQL Server's `OUTPUT` and Oracle's `RETURNING INTO` are different, non-portable mechanisms.
</details>

**3.** `WITH RECURSIVE`

<details>
<summary>Reveal</summary>

**Standard** — SQL:1999. Implemented by every major engine.
</details>

**4.** `MERGE`

<details>
<summary>Reveal</summary>

**Standard** — SQL:2003. PostgreSQL added it in version 15.
</details>

**5.** `INSERT ... ON CONFLICT`

<details>
<summary>Reveal</summary>

**PostgreSQL-defined** (SQLite has similar syntax, but it is not standard). The standard path is `MERGE`.
</details>

**6.** `FETCH FIRST 10 ROWS ONLY`

<details>
<summary>Reveal</summary>

**Standard** — SQL:2008. PostgreSQL accepts it as an alternative to `LIMIT`.
</details>

**7.** `jsonb`

<details>
<summary>Reveal</summary>

**PostgreSQL-defined.** The standard defines a `JSON` type; the binary `jsonb` variant and its operators are PostgreSQL's.
</details>

**8.** `\d bookings` in `psql`

<details>
<summary>Reveal</summary>

**Neither — it is not SQL at all.** `\d` is a `psql` client command that runs catalog queries for you. The server never sees it.
</details>

**9.** Window functions

<details>
<summary>Reveal</summary>

**Standard** — SQL:2003. That `<PostgreSQL feature>` you were avoiding is portable.
</details>

**10.** `DISTINCT ON (customer_id)`

<details>
<summary>Reveal</summary>

**PostgreSQL-defined.** The portable equivalent is `ROW_NUMBER() OVER (PARTITION BY ... ) = 1` in a CTE.
</details>

**11.** `GROUPING SETS` / `ROLLUP`

<details>
<summary>Reveal</summary>

**Standard** — SQL:1999. Also in Oracle, SQL Server, MySQL 8+.
</details>

**12.** `ILIKE`

<details>
<summary>Reveal</summary>

**PostgreSQL-defined.** Portable workaround: compare with `lower(col)` on both sides, or use `CAST`/`COLLATE`.
</details>
