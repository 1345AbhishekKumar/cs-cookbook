An **Operating System (OS)** is the middleman between apps/users and hardware. Your apps can't touch CPU, RAM, disk, or keyboard directly — the OS does it safely and fairly.

Why need it? Without OS, every app would fight over RAM, overwrite each other's files, and need its own printer driver. The OS gives each app its own memory, files, and CPU time. Jobs: **process, memory, file system, I/O, security.**

**Beginner mental model:** think of a restaurant kitchen:

- **Hardware** = stove, fridge, knives — raw resources
- **OS / Kernel** = head chef + manager — decides who uses stove when, who gets ingredients
- **Apps** = customers' orders — Chrome, VS Code, games just ask, never cook themselves
- **System calls** = order slips — the only way apps request things (`read file`, `make process`)
- **Shell / GUI** = waiter — takes your words/clicks and passes slips to kitchen

Use this page as quick reference: plain-English first, exact terms second. New? Read intro lines. Revising? Scan tables.

## OS in 30 seconds

These 8 words unlock everything else.

| Term | Beginner meaning | Example |
| --- | --- | --- |
| `OS` | Manager that shares hardware fairly + safely. | Linux, Windows, macOS, Android |
| `Kernel` | Core of OS, privileged, talks to hardware directly. | Linux 6.x, Windows NT, XNU (mac) |
| `Shell` | Text waiter that takes commands to kernel. | bash, zsh, PowerShell |
| `Process` | One live running program + its own memory. | Chrome tab group, `python app.py` |
| `Thread` | Mini-worker inside a process, shares memory. | Video player: one decodes, one plays audio |
| `System call` | App asks kernel to do privileged work. | `read()`, `write()`, `fork()` |
| `File system` | How disk organizes files. | NTFS, ext4, APFS |
| `Boot` | From power-on to usable OS. | POST → GRUB → kernel → systemd |

> App = recipe, process = cooking that recipe right now. Same recipe can cook twice = two processes.

## Kernel vs Shell vs User space

Kernel is privileged, apps are not. This wall keeps one crash from killing the machine.

| Layer | What it is + beginner note | Example |
| --- | --- | --- |
| `Hardware` | CPU, RAM, disk, NIC. Dumb without software. | Intel CPU, SSD |
| `Kernel` | Privileged core. Drivers, scheduling, memory. Monolithic + modules (Linux 6.x), hybrid (Windows NT), XNU (macOS). | `vmlinuz` on Linux |
| `System calls` | Door from user → kernel. Only legal entry. | `read, write, fork, exec, mmap, pipe` |
| `Shell` | Text UI over syscalls. Scriptable. | bash, zsh, PowerShell |
| `User space` | Where your apps/libs live. Unprivileged. Crashes here don't crash kernel. | Chrome, Python, `libc` |

Trace what apps ask kernel with `strace ls` on Linux — you'll see `openat`, `read`, `write` syscalls.

## Types of Operating Systems

Same idea, different promises: speed, sharing, or tiny size.

| Type | Beginner meaning | Example |
| --- | --- | --- |
| `Batch` | Collect jobs, run one-by-one, no interaction. | Old payroll systems |
| `Time-sharing` | Split CPU in ms slices so many users feel alone. | Linux server, Windows |
| `Distributed` | Many machines act as one. | Google Borg, cluster |
| `RTOS` | Real-time guarantee — must answer in X ms. | FreeRTOS in microwave, car airbag |
| `Mobile` | Battery + touch + sensors optimized. | Android (on Linux), iOS |
| `Embedded` | Tiny, router/appliance OS. | OpenWrt on router |

> Desktop = fair + fast. RTOS = on-time or fail. Miss a movie frame = glitch; miss an airbag deadline = disaster.

## Program vs Process vs Thread

Most confused trio in interviews. One line: program is dead, process is alive, thread shares.

| Term | Beginner meaning | Example |
| --- | --- | --- |
| `Program` | Dead code on disk. Does nothing until run. | `chrome.exe`, `./a.out` file |
| `Process` | Live program + own memory + PCB. Isolated. | Two Chrome windows = 2 processes |
| `Thread` | Light worker inside process. Shares heap/code, own stack. Crash one, all crash. | Word: one thread types, one spell-checks |

**House analogy:** program = house blueprint, process = built house with own address, threads = roommates sharing kitchen (heap) but with own bedrooms (stack).

Processes are safe but heavy (separate memory). Threads are fast but risky (share memory — need locks).

## Process states + PCB

A process is never just "running" — it waits for CPU or disk most of its life.

New → Ready → Running → Waiting → Terminated. That's the whole life:

1. **New:** just created via `fork()`.
2. **Ready:** wants CPU, waiting in queue.
3. **Running:** has CPU now.
4. **Waiting/Blocked:** stuck on I/O (disk, network, `input()`).
5. **Terminated:** done, waiting to be cleaned (`zombie` if parent didn't `wait()`).

**Context switch:** CPU freezes one process (save registers/PC), loads next. So fast (µs) it feels parallel. Too many switches = wasted time.

| PCB field | What kernel remembers per process |
| --- | --- |
| `PID` | Unique ID. `echo $$`, Task Manager. |
| `State` | New/Ready/Running/Waiting/Terminated |
| `PC + Registers` | Where to resume after switch |
| `Priority` | Who goes first |
| `Memory map` | Which RAM pages it owns |
| `Open files` | FDs, e.g. `0 stdin, 1 stdout, 2 stderr` |

> See live: `ps aux` or `top` on Linux, Task Manager on Windows. `kill -9 <PID>` = force kill.

## CPU Scheduling — who gets CPU next?

One CPU, 100 ready processes. Scheduler picks. Goal: fair + fast + no starvation.

| Algorithm | How it works + beginner analogy | Pros / Cons |
| --- | --- | --- |
| `FCFS` | First come first served. Grocery line. | Simple, but convoy effect — long job blocks all |
| `SJF` | Shortest job first. Express checkout. | Optimal avg wait, but needs future knowledge + starves long jobs |
| `SRTF` | Preemptive SJF — kick out if shorter arrives. | Better response, still starves |
| `Round Robin` | Each gets quantum 10-100 ms, then back of line. Card dealer. | Fair, great for time-sharing. Too small quantum = switch overhead |
| `Priority` | VIP first. + aging (wait longer = priority up) to stop starvation. | Urgent jobs fast, low ones may starve without aging |
| `MLFQ` | Many queues, like school grades. New jobs top queue, demote if CPU-hungry. | Balances interactive + batch. Used widely |
| `CFS` | Linux default. Virtual runtime — pick who had least CPU. | Fair, no magic numbers |

Interview line: Round Robin = fair, SJF = fastest avg but starves, Priority + aging = urgent without starvation.

## IPC — how processes talk

Processes can't see each other's memory, so OS gives postboxes.

| Method | Beginner meaning + speed note | Example |
| --- | --- | --- |
| `Pipe` | One-way, parent → child, dies with processes. | `ls \| grep txt` |
| `Named pipe (FIFO)` | Pipe with a file name, unrelated processes can use. | `mkfifo q; cat < q` |
| `Shared memory` | Fastest — both map same RAM. Needs semaphore lock. | Video editor frames |
| `Message queue` | OS holds list of messages. | Printer spool |
| `Sockets` | Talk over network or same machine. | Browser ↔ server, `localhost:3000` |
| `Signals` | Tiny notification, no data. | `Ctrl+C` = SIGINT, `kill -9` = SIGKILL |
| `Semaphore/Mutex` | Traffic light, not data — "only 1 in now". | Lock shared counter |

> Fastest = shared memory, easiest = pipe, cross-machine = sockets. If threads corrupt shared data, you forgot the lock.

## Deadlocks — four locks, zero progress

Two programs each hold what the other wants. Both wait forever. Needs all 4 Coffman conditions at once:

1. **Mutual Exclusion** — resource can't share (printer).
2. **Hold & Wait** — hold one, wait for another.
3. **No Preemption** — can't snatch it away.
4. **Circular Wait** — A waits B, B waits A.

| Strategy | Idea + example |
| --- | --- |
| `Prevention` | Break one condition. Order all locks, or ask for all at once. |
| `Avoidance (Banker's)` | Only grant if a safe sequence still exists. Like bank never lending its last cash. |
| `Detection + Recovery` | Let it happen, find cycle, kill one process. Used in DBs. |
| `Ostrich` | Ignore it. Restart. What most desktop OSes do. |

Classic: two friends, one fork + one knife each need both to eat. Fix: always pick fork first (ordering).

## Memory — paging, faults, thrashing

Every process thinks it has all RAM. MMU + paging fake it.

| Term | Beginner meaning | Example |
| --- | --- | --- |
| `Paging` | Split RAM into fixed 4KB pages. No external gaps. | Process gets pages 3, 9, 42 — scattered but looks contiguous |
| `Segmentation` | Split by meaning (code/stack/heap), variable size. | Causes external holes/gaps |
| `Demand paging` | Load page only when touched. Faster start. | Opening 1GB file loads only viewed part |
| `Page fault` | Touched page not in RAM — OS loads from disk. Minor (fast) or major (disk sleep). | First touch of new `mmap` |
| `LRU vs FIFO` | Evict Least Recently Used (good) vs First In (simple, suffers Belady — more RAM can mean more faults). | LRU ≈ "throw old toys first" |
| `Thrashing` | Σ working sets > RAM → constant paging, CPU ~0%. | 20 Chrome tabs on 4GB RAM |
| `MMU / TLB` | MMU translates virtual→physical. TLB caches it. Miss = slow walk. | Why locality matters |

> Fix thrashing: kill processes, add RAM, or reduce working set. More RAM doesn't always help FIFO — that's Belady's anomaly.

## File Systems — where bytes live on disk

Same USB, different format = different limits. Pick by who must read it.

| FS | Limits | Journal? + Use when |
| --- | --- | --- |
| `FAT32` | 4GB file, 2TB vol | No. Old USB/cameras. Works everywhere but no big movies |
| `exFAT` | 16EB | No (light). Shared USB Mac↔Win, SD cards >32GB |
| `NTFS` | 16EB | Yes (metadata) + ACLs. Windows default |
| `ext4` | 16TB file, 1EB vol | Yes. Linux default — best for servers |
| `APFS` | 8EB | Yes (COW, snapshots). macOS/iOS default, SSD-optimized |

Compat rule: need Windows+Mac+Linux USB? `exFAT`. Windows-only internal? `NTFS`. Linux-only? `ext4`. Mac-only? `APFS`. Need 5GB movie on FAT32? Impossible — reformat to exFAT.

## System calls + User vs Kernel mode

CPU has 2 rings so apps can't `rm -rf /hardware`.

| Mode | What code can do | Example |
| --- | --- | --- |
| `User mode` | No direct hardware. Must ask via syscall. Crash = kill app. | Your `printf()` → `write()` syscall |
| `Kernel mode` | Full hardware access. Crash = blue screen / panic. | Driver, scheduler |

Common syscalls: `fork()` make process, `exec()` run program, `read/write/open/close`, `pipe()`, `mmap()`, `exit()`. Shell `ls` is just many `openat + getdents + write` syscalls — prove with `strace ls`.

Why 2 modes? Safety + stability. Browser bug shouldn't format disk. Only tiny trusted kernel runs privileged.

## Booting — POST to login

Press power → usable desktop in seconds:

`POST → Firmware (BIOS/UEFI) → Bootloader (GRUB) → Kernel → systemd (PID 1) → login`

| Step | What happens |
| --- | --- |
| `POST` | Hardware self-check. Beep = fail. |
| `Firmware` | Find boot disk. BIOS (old) or UEFI (new). |
| `Bootloader` | Menu to pick OS/kernel. e.g. GRUB. |
| `Kernel` | Loads drivers, mounts root FS. |
| `systemd PID 1` | First process, starts all services. |

| Feature | BIOS + MBR | UEFI + GPT |
| --- | --- | --- |
| `Disk` | MBR, max 2TB, 4 partitions | GPT, huge disks, 128+ partitions |
| `Boot` | From MBR gap, no security | From ESP partition, Secure Boot checks signature |
| `Speed/UI` | Slow text | Fast, mouse, network |

> No bootable device? Firmware found no bootloader. Fix boot order or reinstall GRUB.

## CLI vs GUI + Permissions

GUI clicks, CLI types. CLI wins for servers: scriptable, remote, light.

Permissions are 3 bits: `r=4, w=2, x=1`. `ls -l` shows `rwxr-xr--`:

| Octal | Meaning + when used |
| --- | --- |
| `755` | `rwxr-xr-x` — dirs + scripts. You full, others run/read. |
| `644` | `rw-r--r--` — normal files. You edit, others read. |
| `777` | `rwxrwxrwx` — never! Anyone can overwrite = hacked. |
| `600` | `rw-------` — private keys like `~/.ssh/id_rsa` |

```bash
chmod 755 run.sh   # make executable
chmod 644 notes.txt
chown user:group file  # change owner (sudo needed)
sudo apt update    # run as admin once
```

## Beginner FAQs — quick doubts

- **Why two modes (user/kernel)?** So a buggy app can't touch hardware directly. App must beg via syscall; kernel checks permission first.
- **Why does my PC freeze with many tabs (thrashing)?** Total working sets exceed RAM. OS pages to disk nonstop, CPU waits on disk. Close tabs or add RAM.
- **Process or thread for my video server?** Processes for isolation (one crash ≠ all dead), threads for speed (share cache). Most servers: processes + thread pool inside.
- **Why can't I copy 5GB to FAT32 USB?** FAT32 max file = 4GB by design. Reformat to exFAT.
- **Why 755 not 777?** 777 lets anyone edit/execute — malware injects code. 755 = you write, others only run.
- **Where is PID 1?** `systemd` (or `init`). It starts everything; if it dies, kernel panics. Check with `ps -p 1`.
- **BIOS or UEFI?** New machine = UEFI+GPT+Secure Boot. Only pick BIOS/MBR for old hardware or 32-bit tools.
- **VM or Docker?** Need another kernel/strong isolation = VM. Ship same app fast = Docker container.

## Memory anchors

- **Kitchen model:** apps order, kernel cooks, syscalls are slips, shell is waiter.
- **Program/Process/Thread:** blueprint / built house / roommates sharing kitchen.
- **Life:** New → Ready → Running → Waiting → Terminated. PCB = ID + resume point.
- **Scheduling:** FCFS lines up, SJF express (starves), RR deals cards, Priority VIP + aging, Linux = CFS.
- **IPC speed:** shared memory fastest, pipe easiest, socket goes network. Locks = semaphores.
- **Deadlock = 4 together:** Mutual + Hold&Wait + NoPreempt + Circular. Fix: order locks or Banker.
- **Memory:** paging 4KB no gaps, fault = fetch from disk, thrashing = ΣWS > RAM.
- **FS:** FAT32 4GB limit, exFAT share USB, NTFS Windows, ext4 Linux, APFS Mac.
- **Boot:** POST → UEFI → GRUB → kernel → systemd PID1. UEFI+GPT wins over BIOS+MBR 2TB.
- **Perms:** r=4 w=2 x=1. 755 scripts, 644 files, 777 never. `PATH` finds commands.
