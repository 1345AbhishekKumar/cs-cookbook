## Plan on paper, pick a tool, ship something small

No good program starts with typing. The video insists that planning precedes the IDE, and its vehicle is pseudocode — plain-language steps with syntax stripped away. The analogy is a family drive to the Grand Canyon: you would not just start driving and improvise hotels, routes, and stops. You list where you will go, where you will sleep, what you will do there, and which highway earns its place. Pseudocode does the same for a divider program: prompt for the first number, wait, prompt for the second, define both, compute, return. It forces you to decide what the program accomplishes and how, before variable names and semicolons compete for attention. Flowcharts are the companion sketch: boxes and arrows that expose the path through one function so loops and branches become visible before they become bugs. Both are throwaway by design — scaffolding you discard once the real structure stands.

Then choose the tool. The video tours the landscape without snobbery: HTML for page content plus CSS for style (right-click Inspect on any site to see them working), scripting languages such as Perl, PHP, Ajax, and JavaScript for fast-to-write, portable, often web-enhancing tasks that run without separate compilation, and general-purpose languages such as Java, C++, and Python as the default workhorses with wide application. Hundreds of languages exist because tasks differ; inside a task, preference for a language's rules and simplification level legitimately decides. Applications close the course: websites, scripts that smooth daily work, general programs from games to utilities. Your next step is not to learn "programming" in the abstract but to convert one small annoyance into a planned, written, tested program in the language whose community and libraries sit closest to that annoyance. Plan it in pseudocode, draw the tricky function, write it, print through it, and you will have repeated — at small scale — everything this course taught.

### Step-by-step breakdown

1. Write pseudocode: inputs, waits, computations, outputs — no syntax.
2. Draw the risky function as a flowchart; confirm every branch ends somewhere sane.
3. Match task to family: page → HTML/CSS; quick portable → scripting; broad app → general-purpose.
4. Try two languages briefly; keep the one whose errors you understand faster.
5. Build one tiny application end to end rather than ten half-read tutorials.

- **Obvious** — Divider app pseudocode: ask first number, ask second, divide, show result.
- **Counter-intuitive** — Throwaway work (pseudocode, charts) speeds up "real" work by catching branch and I/O mistakes when they are cheapest.
- **Edge case** — Inspect Element on a plain page reveals sprawling HTML/CSS — simple tools compose into complex results.

```text
PSEUDOCODE divide:
  prompt "first number"; wait input A
  prompt "second number"; wait input B
  define A, B as numbers
  return A / B to user   # guard B != 0 (Module 4+5 thinking)
```

```python
# Python - the divider program end to end (pseudocode -> real code):
def divide(a, b):
    if b == 0:
        return "Cannot divide by zero"  # Module 4 thinking
    return a / b

# Try it with fixed values first (no typing needed):
print(divide(10, 2))  # 5.0
print(divide(10, 0))  # Cannot divide by zero

# Then with user input (the full Grand Canyon trip):
# a = float(input("first number: "))
# b = float(input("second number: "))
# print("Result:", divide(a, b))

# Mini-project combining Modules 3-8 in one script:
def is_even(n):
    return n % 2 == 0

scores = [88, 95, 70, 100]
for s in scores:              # loop + branch + function + list
    label = "even" if is_even(s) else "odd"
    print(s, "is", label)
```

Visual analogy — Road-trip plan vs driving: pseudocode is hotels, routes, and stops decided in daylight; code is night driving with headlights already aimed.

**✕ What people get wrong:** "Planning wastes coding time." Unplanned code pays the same planning cost later, with interest, in debugger hours.

**Why this matters:** This is the habit that separates a tutorial watcher from someone who ships: small plan, small build, real feedback.
