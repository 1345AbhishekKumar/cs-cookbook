## Find fast, and let functions call themselves — carefully

Storing is half the job; finding is the other. The video distinguishes sorted lists — ranked by ID, number, or alphabet like usernames — from unsorted piles with no order. Some methods need sorted input, usually the faster ones; others accept both but do more work. Efficiency is judged two ways: the worst-case number of checks for size n, and the average checks. That comparison language is Big O notation: a shorthand that takes the list size and returns a growth curve you can rank. Linear search is the familiar one — start at the top of the attendance sheet, compare each name, move down until found or exhausted. It works on sorted and unsorted lists, costs O(n) worst-case, and is honest, simple work. Binary search is the specialist: only for sorted lists, it repeatedly halves the remaining range using a recursive split, discarding the half that cannot contain the target (if Carl comes before the middle, drop the right side). Its worst case is O(log n), which for large n is dramatically smaller than O(n). The video's rule of thumb is blunt and correct in almost every sorted case: prefer binary.

Recursion is the engine behind that halving, and the video flags it as confusing but central. A recursive function calls itself on a smaller piece of the problem until a base case stops the chain. Without a base case you rebuild the infinite loop in fancier clothes: calls pile onto the call stack — imagined as stones stacked one atop another where you must lift the top before reaching the bottom — and never resolve, eventually exhausting memory. With a base case, the pile unwinds in reverse: the smallest answer returns, its caller finishes, and so on up to the original call. Factorial and binary search both fit this shape. Trace small inputs by hand — write the stack as a vertical list, cross off each return — and the mystery fades. You are not learning a trick; you are learning how programs manage unfinished work.

### Step-by-step breakdown

1. Ask: is the list sorted? If no, linear is your honest default.
2. Linear: scan top to bottom; count worst-case n, average ~n/2.
3. Binary: demand sorted; compare middle, keep the half that can hold the target.
4. Recurse or loop the halving until found or range empties; note O(log n).
5. For any recursion, write the base case first, then the smaller self-call.

- **Obvious** — Find your name on a sign-in sheet: linear scan from the top.
- **Counter-intuitive** — Binary needs sortedness, which can feel like a drawback — until you see log n beat n on 100,000 users.
- **Edge case** — Recursion without base: stones pile forever. Same disease as infinite loops, different ward (stack overflow).

```python
# Concept shapes (same as video):
linear:  for each x in list: if x == target: return index   # O(n)
binary:  while lo <= hi: mid=(lo+hi)//2; keep half          # O(log n)
def fact(n): return 1 if n <= 1 else n * fact(n-1)  # base + smaller call
```

```python
# Python - full runnable versions, paste into your IDE:
# Linear search: works on sorted AND unsorted
def linear_search(items, target):
    for i in range(len(items)):
        if items[i] == target:
            return i
    return -1

names = ["Zoe", "Ada", "Carl", "Mia"]
print(linear_search(names, "Carl"))  # 2
print(linear_search(names, "Bob"))   # -1 (not found)

# Binary search: needs SORTED list, O(log n)
def binary_search(sorted_items, target):
    lo, hi = 0, len(sorted_items) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if sorted_items[mid] == target:
            return mid
        elif sorted_items[mid] < target:
            lo = mid + 1   # target is right half
        else:
            hi = mid - 1   # target is left half
    return -1

sorted_names = ["Ada", "Bob", "Carl", "Mia", "Zoe"]
print(binary_search(sorted_names, "Mia"))  # 3

# Recursion: base case FIRST, then smaller self-call
def fact(n):
    if n <= 1:        # base case - stops the stones piling
        return 1
    return n * fact(n - 1)  # smaller piece

print(fact(4))  # 24  (4*3*2*1)
# fact without base = RecursionError (Python's stack overflow)
```

Visual analogy — Phone book: linear = read every page from A; binary = open middle, ask "before or after?", tear away the wrong half (in thought, not paper).

**✕ What people get wrong:** "Binary is always better." On unsorted data it is unusable until you pay to sort. Match method to order.

**Why this matters:** Big O is how you argue about scale before users arrive. The startup with 100,000 accounts feels the difference between n and log n daily.
