## Find the lie, then wrap the truth in a name

Debugging is not talent; it is procedure. The video's advice for logic errors — the ones with no red text — starts with making the invisible visible: add print statements and watch the console to learn where execution diverges from expectation. If a conditional surprises you, print the tested value just before it. If a loop misbehaves, print the counter. Then narrow: test small pieces in isolation, re-read the exact lines the output implicates, and question the operator you are most sure about, since `*` versus `+` is a classic silent swap. The attitude shift matters more than any tool: errors are normal, always present in real work, and best met with "which of the three types is this and what did I just prove?" rather than staring at the whole file.

Functions turn that hard-won correctness into reuse. A function is a wrapped segment of code with a name; calling the name unwraps and runs the contents, as many times and places as you like. The video separates functions along two axes that you should memorize: whether they take in arguments, and whether they return values. Arguments are inputs that vary each call — the Five Guys analogy where "get food" is the function and your order (fries, burger, soda) is the argument that changes what happens. The `max` function needs two integers to compare; call it with none and it complains, just as the cashier cannot serve an empty order. Return values are outputs handed back: calling alone does nothing visible unless you store or print the result. The familiar `print` itself is a function you have already been borrowing. Seeing functions as present-boxes — wrap once, label, unwrap on demand — prepares you to both borrow from libraries and build your own in Module 7.

### Step-by-step breakdown

1. Reproduce: make the wrong output happen on demand.
2. Reveal: print the suspect variable right before the suspect line.
3. Isolate: test the conditional, loop, or function alone with known inputs.
4. Name it: wrap the correct logic as a function with clear arguments and return.
5. Verify: call with at least two different argument sets and print both returns.

- **Obvious** — `max(3, 9)` returns 9. Different arguments, same function, different result.
- **Counter-intuitive** — A returning function called alone looks broken. The value was computed then discarded — you must catch it.
- **Edge case** — Five Guys with no order: a function requiring arguments errors when starved, which is correct behavior, not rudeness.

```java
// Generic shape:
int m = max(3, 9);   // m is 9
print(max(3, 9));    // also 9, now visible
max();               // error: missing arguments
```

```python
# Python - debug with prints, then wrap in functions:
# 1. Reveal: print the suspect before the suspect line
n = 9
print("DEBUG n =", n)  # see what the machine actually holds
if n % 2 == 0:
    print("even")
else:
    print("odd")

# 2. Wrap the correct logic: max needs 2 arguments
def my_max(a, b):
    if a > b:
        return a
    else:
        return b

m = my_max(3, 9)
print(m)            # 9 - stored
print(my_max(3, 9)) # 9 - printed directly
# my_max()          # TypeError: missing 2 required arguments
                    # Python's version of the Five Guys no-order error

# 3. Verify with two different argument sets:
print(my_max(10, 2))  # 10
print(my_max(-1, -8)) # -1
```

Visual analogy — Restaurant kitchen: the menu item is the function name, your ticket is the arguments, the tray handed back is the return. No ticket, no tray.

**✕ What people get wrong:** "Debugging means rewriting everything." Effective debugging shrinks the suspect area with prints before changing anything.

**Why this matters:** Functions are how 90 minutes of basics scale to real apps: prove a small piece, name it, and stop rewriting it.

Expandable misconception: "More prints mean worse code" — Temporary prints are scaffolding, not clutter. Add them to locate the lie, then remove or convert the useful ones into proper output or tests. Professionals do this daily.
