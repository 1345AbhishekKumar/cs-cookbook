<LessonIntro>
The most dangerous moment in an application's lifecycle is the transition between software versions. If you replace all servers simultaneously, a subtle bug immediately infects 100% of your users. Progressive Delivery replaces "big bang" updates with scientific, incremental rollouts: testing software against real production traffic while minimizing the blast radius of unexpected failures.
</LessonIntro>

## The "Big Bang" (Recreate) Disaster

In early web computing, systems used the **Recreate** strategy:

```mermaid
flowchart LR
    Step1["1. Terminate all Version 1 servers"] --> Step2["2. Downtime Window (Users see 503)"]
    Step2 --> Step3["3. Boot Version 2 servers"]
    Step3 --> Step4["4. 💥 Fatal Bug: 100% of users crash!"]
    
    style Step1 fill:#1e293b,stroke:#64748b,color:#f8fafc
    style Step2 fill:#451a03,stroke:#f59e0b,stroke-width:2px,color:#fef3c7
    style Step3 fill:#312e81,stroke:#6366f1,color:#e0e7ff
    style Step4 fill:#450a0a,stroke:#ef4444,stroke-width:3px,color:#fecaca
```

Every user experiences downtime, and if Version 2 contains an unhandled exception, 100% of your user base is impacted instantly.

## The Three Zero-Downtime Deployment Patterns

Modern infrastructure uses three primary progressive deployment strategies, each balancing resource cost against rollback speed:

### 1. Rolling Update

In a **Rolling Update**, old instances are gradually replaced by new instances one by one (or in small batches) behind the load balancer.

```mermaid
flowchart TD
    subgraph StepA["Step 1: 100% Version 1"]
        A1["Instance 1 (v1)"] --- A2["Instance 2 (v1)"] --- A3["Instance 3 (v1)"]
    end
    
    subgraph StepB["Step 2: 1 New Instance Added; 1 Old Terminated"]
        B1["Instance 1 (v1)"] --- B2["Instance 2 (v1)"] --- B3["Instance 3 (v2 ✨)"]
    end

    subgraph StepC["Step 3: Rollout Complete"]
        C1["Instance 1 (v2 ✨)"] --- C2["Instance 2 (v2 ✨)"] --- C3["Instance 3 (v2 ✨)"]
    end

    StepA --> StepB --> StepC
    
    style StepA fill:#1e293b,stroke:#38bdf8,color:#f8fafc
    style StepB fill:#312e81,stroke:#6366f1,color:#e0e7ff
    style StepC fill:#064e3b,stroke:#10b981,color:#d1fae5
```

- **Pros**: Zero additional server cost (you don't need a second duplicate cluster).
- **Cons**: Version 1 and Version 2 coexist simultaneously for several minutes; rollback is slow because you must roll back instance by instance.

### 2. Blue / Green Deployment

In a **Blue/Green Deployment**, two identical production environments exist:
- **Blue**: Currently active environment handling 100% of user traffic.
- **Green**: Idle standby environment.

```mermaid
flowchart LR
    Router["Load Balancer / Ingress Router"]
    
    subgraph Blue["Blue Environment (Active v1.0)"]
        B1["App Pod 1"]
        B2["App Pod 2"]
    end

    subgraph Green["Green Environment (Standby v2.0)"]
        G1["App Pod 1 (v2)"]
        G2["App Pod 2 (v2)"]
    end

    Router -->|100% User Traffic| Blue
    Router -.->|"0% Traffic (Smoke tested privately)"| Green
    
    style Router fill:#312e81,stroke:#6366f1,stroke-width:2px,color:#e0e7ff
    style Blue fill:#0284c7,stroke:#38bdf8,stroke-width:2px,color:#ffffff
    style Green fill:#064e3b,stroke:#10b981,stroke-width:2px,color:#d1fae5
```

When deploying Version 2:
1. Deploy Version 2 to **Green**.
2. Run internal smoke tests against Green using private internal endpoints.
3. Once verified, update the router configuration: **instantly switch 100% of user traffic from Blue to Green**.
4. **Instant Rollback**: If an issue is detected, flip the router back to Blue in 500 milliseconds.

### 3. Canary Release

Named after the canary birds miners took into coal mines to detect toxic gas, a **Canary Release** routes a tiny slice of real production traffic to the new version before general availability:

```mermaid
flowchart TD
    Traffic["100% User Requests"] --> Ingress["Ingress Traffic Splitter (Envoy / Istio / Cloudflare)"]
    
    Ingress -->|95% Traffic| Baseline["Stable Baseline (v1.0)<br/>95% of Users"]
    Ingress -->|5% Traffic| Canary["Canary Instance (v2.0)<br/>5% of Users"]
    
    Canary --> Telemetry["Real-Time Metric Comparison:<br/>1. HTTP 5xx Error Rate<br/>2. Latency P99<br/>3. Memory / CPU Saturation"]
    
    Telemetry --> Decision{"Canary Healthy?"}
    Decision -->|YES| Ramp["Increment traffic: 5% → 25% → 50% → 100%"]
    Decision -->|NO| Abort["Auto-Rollback: Route 100% back to v1.0 in seconds!"]
    
    style Traffic fill:#1e293b,stroke:#64748b,color:#f8fafc
    style Ingress fill:#312e81,stroke:#6366f1,color:#e0e7ff
    style Baseline fill:#0284c7,stroke:#38bdf8,color:#ffffff
    style Canary fill:#f59e0b,stroke:#d97706,stroke-width:2px,color:#000000
    style Telemetry fill:#1e293b,stroke:#64748b,color:#e2e8f0
    style Decision fill:#312e81,stroke:#6366f1,color:#e0e7ff
    style Ramp fill:#065f46,stroke:#10b981,color:#d1fae5

```

## Health Checks: Readiness vs. Liveness Probes

To execute zero-downtime deployments, your orchestrator (Kubernetes, AWS ECS) must know when a new container is ready to receive traffic.

<Tabs items={['Readiness Probe (Can it receive traffic?)', 'Liveness Probe (Is it alive?)']}>
<Tab value="Readiness Probe (Can it receive traffic?)">

Tells the load balancer whether the container has finished its startup tasks (connecting to database, loading cache, compiling JIT code).
- **If failing**: The container is NOT killed; it is simply removed from the load balancer pool so users never receive an error.

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 3
```

</Tab>
<Tab value="Liveness Probe (Is it alive?)">

Tells the orchestrator if the application has deadlocked, frozen in an infinite loop, or crashed.
- **If failing**: The orchestrator immediately kills and restarts the container.

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10
```

</Tab>
</Tabs>

## The Rollback Decision Tree

When production alerts trigger during a release, engineers often panic: *"Should we push a quick hotfix or roll back?"*

High-performing teams follow a strict algorithmic decision tree:

```mermaid
flowchart TD
    Alert["Production Alert Fires During or After Deploy"] --> Assess{"Is the root cause 100% understood<br/>AND fixable in < 5 minutes?"}
    
    Assess -->|NO| Rollback["🚨 ROLL BACK IMMEDIATELY 🚨<br/>Revert router traffic to previous known-good version.<br/>Investigate in staging, not in front of live users."]
    Assess -->|YES| Hotfix{"Can the fix be deployed<br/>through standard CI in < 5 min?"}
    
    Hotfix -->|YES| Fix["Roll forward with hotfix commit"]
    Hotfix -->|NO| Rollback
    
    style Alert fill:#450a0a,stroke:#ef4444,color:#fecaca
    style Assess fill:#312e81,stroke:#6366f1,color:#e0e7ff
    style Rollback fill:#7f1d1d,stroke:#ef4444,stroke-width:2px,color:#fee2e2
    style Hotfix fill:#312e81,stroke:#6366f1,color:#e0e7ff
    style Fix fill:#065f46,stroke:#10b981,color:#d1fae5
```

<LessonNote variant="why" title="The Golden Rule of Rollbacks">
**Restore customer service first; analyze root cause second.** Never debug an unknown failure in production while live customers are experiencing errors. Revert immediately to the previous immutable release, return metrics to baseline, and investigate in peace.
</LessonNote>
