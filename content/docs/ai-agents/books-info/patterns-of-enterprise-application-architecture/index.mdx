**Martin Fowler · 2002**

<Callout type="info" title="For humans">
The naming layer under almost every framework you use. Fowler catalogued the recurring structures of
enterprise applications — transaction script, table module, domain model, data mapper, repository, unit of
work, layers, session state, concurrency — so that discussions could be about *choices* rather than
preferences. Many of these are now invisible inside ORMs and web frameworks, which is exactly why it helps
to know what they are called and what they cost.
</Callout>

## What it argues

Enterprise applications keep rediscovering the same structures. If you name them, you can choose them
deliberately instead of accreting them accidentally: how complex will the domain logic be, and therefore
where should it live? How is persistence mapped to in-memory objects, and where does a transaction begin
and end? How are layers separated so presentation does not leak into domain logic? The book is not a
prescription — it is a catalogue with trade-offs, intended to make architecture a series of explainable
decisions rather than an accumulation of habits.

## Core ideas

- **Place domain logic deliberately** — transaction script, table module, or domain model, chosen by complexity.
- **Separate mapping from logic** — data mapper and repository keep persistence out of domain code.
- **Bound transactions explicitly** — unit of work and transaction boundaries are architecture, not plumbing.
- **Layer with intent** — presentation, application workflow, domain, and persistence have distinct jobs.
- **Be careful with concurrency** — optimistic versus pessimistic strategies are a design decision.
- **Distribution is expensive** — do not make objects remote without a reason that survives scrutiny.
