**Martin Fowler · 2nd ed. 2018**

<Callout type="info" title="For humans">
The book that made "improve the design of existing code" a safe, routine activity instead of a heroic
rewrite. Its contribution is not the catalog of transformations — it is the *discipline*: never change
structure and behaviour in the same step, keep each step tiny enough to verify, and let tests tell you
the instant you broke something. Read it if you have ever been afraid to touch working code.
</Callout>

## What the book argues

Refactoring is a behaviour-preserving transformation of internal structure. Because behaviour is held
constant, it can be done continuously — before a feature, while adding a feature, in review — and its
effects compound. The safety comes from mechanics, not courage: small steps, an explicit transformation,
and a test suite that runs after each one. Refactoring is therefore a normal part of daily work, not a
separate project you schedule once the code has become unbearable.

## Core ideas

- **Behaviour first, structure second** — never mix the two in one commit; if tests change, it was not a refactor.
- **Small, named steps** — extract, inline, move, rename; each step is reversible and independently verifiable.
- **Code smells as triggers** — duplication, long functions, feature envy, and primitive obsession point at the next move.
- **Tests are the safety net** — refactor under green; if you cannot test it, first make it testable.
- **Preparation over heroics** — refactor to make the change easy, then make the easy change.
- **Continuous, not periodic** — design improvement as daily hygiene rather than a scheduled intervention.
