**Vaughn Vernon · 2013**

<Callout type="info" title="For humans">
Where Evans explains what DDD means, Vernon's *Implementing* explains how it survives contact with a
database. It is the book that gives you opinions on aggregate size, repository design, domain events, and
how contexts actually talk to each other. Read it when the modelling is done and the hard part — making the
model work across a real system — has begun.
</Callout>

## What it argues

DDD fails when it is translated into object graphs that mirror the database. The aggregation chapter is the
heart of the book: keep aggregates small, reference other aggregates **by identity** rather than by object
link, protect each aggregate with a single transaction boundary, and accept eventual consistency between
them. Around that, use domain events for cross-aggregate and cross-context communication, repositories as
collections of aggregates, and hexagonal architecture to keep infrastructure outside the model. Integration
between contexts is designed deliberately — with a published language, and an anti-corruption layer where
the upstream model would otherwise leak in.

## Core ideas

- **Small aggregates** — one transaction, one invariant cluster; identity references instead of object references.
- **Consistency by design** — be explicit about what is immediately consistent and what is eventually consistent.
- **Domain events** — the mechanism for state changes that other parts of the system need to react to.
- **Repositories as collections** — persistence concerns hidden behind a domain-shaped interface.
- **Published language and anti-corruption layers** — integrating with a foreign model without polluting yours.
- **Hexagonal architecture** — the model in the middle; ports and adapters around it.
