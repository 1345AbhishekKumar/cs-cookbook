**John Ousterhout · 2018**

<Callout type="info" title="For humans">
The shortest useful answer to "why is this codebase miserable to change?" Ousterhout treats complexity
as the primary enemy and traces it to two causes: **dependencies** and **obscurity**. If you have ever
felt that a change "should" be local and watched it spread across nine files, this book names what you
were feeling and gives you a design vocabulary for it. It is a design book, not a style guide — read it
if you own module boundaries or API shape.
</Callout>

## What the book argues

Working code is not an acceptable stopping point. Every decision either adds or subtracts complexity
for the next reader, and "tactical" programming — patch now, think later — compounds into a codebase
nobody can reason about. Design is therefore continuous work, not a phase before coding. The unit of
success is **cognitive load**: how many facts must a developer hold at once to make a safe change.

## Core ideas

- **Deep modules** — a narrow interface over meaningful internal complexity. A wrapper that hides nothing is a shallow module and a net loss.
- **Information hiding** — volatile decisions (storage shape, protocols, file formats, workflow bookkeeping) belong inside the module that owns them, not in its interface.
- **Pull complexity downward** — a slightly harder implementation is worth it when it spares every caller from repeating the same reasoning.
- **Design errors out of existence** — reshape interfaces and invariants instead of forcing callers through defensive ceremony.
- **Comments are design** — document contracts, invariants, and rationale; never narrate code or excuse bad naming.
- **Strategic over tactical** — budget time for design on non-trivial work, and treat awkwardness as a signal rather than an obstacle.
