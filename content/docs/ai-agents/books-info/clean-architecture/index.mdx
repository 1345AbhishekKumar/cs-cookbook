**Robert C. Martin · 2017**

<Callout type="info" title="For humans">
A book about one idea, stated many ways: **dependencies point inward, toward policy.** Frameworks,
databases, and transport are details; the business rules are the system. Even if you find the ring diagrams
overdrawn, the dependency rule is the reason your domain logic can outlive an ORM migration. Read it if you
have ever watched a framework upgrade become a business-logic project.
</Callout>

## What the book argues

Architecture is the set of decisions that are expensive to change, so those decisions should be the ones
that matter — not your choice of web framework. The rule that makes systems survivable is that source-code
dependencies cross boundaries in one direction only, from volatile details toward stable policy. Business
rules must be testable and expressible without a database, a UI, or a vendor SDK in the room. Components
should be assembled behind interfaces so details can be replaced, and boundaries should be placed where
change is likely and costly.

## Core ideas

- **The dependency rule** — nothing in an inner, policy layer knows about an outer, detail layer.
- **Separate policy from mechanism** — entities and use cases must not import the framework.
- **Boundaries are interfaces** — crossing a boundary means an explicit contract, not a direct call.
- **Details are replaceable** — database, web, and messaging choices are plugins to the core.
- **Screaming architecture** — the top-level structure should announce the use cases, not the tooling.
- **Over-abstraction is also a failure** — add boundaries where they will pay for themselves.
